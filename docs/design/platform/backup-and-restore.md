## 2. What is backed up

### 2.1 The parts of a backup

A backup of an environment has these parts. **Design choice.**

| Part | What it holds | IDs |
| --- | --- | --- |
| The directory database | Each Organisation's code and where its database is; nothing else ([deployment.md](deployment.md) section 4) | DEC-093, `PRD-ACS-020` |
| Each Organisation database | All of that Organisation's records: masters, documents, movements, journals, approvals, audit and access records with their seals, stored-file records and attachments, the outbox and job rows, and `kernel.migration` | `PRD-MOD-001`, `PRD-SEC-012` |
| The file store | Every stored object of the bucket, already encrypted by the application ([imports-and-opening-data.md](imports-and-opening-data.md) section 11) | `PRD-IMP-002`, `POL-18.02` |
| The manifest | One per backup: what it holds and how to check it (3.2). No record data, no key | `PRD-SEC-012` |

- The unit of restore is one Organisation: its database, its objects in the file store and its keys. A whole environment is its directory plus every Organisation. One database per Organisation makes this possible (`PRD-MOD-001`). **Design choice.**
- So that one Organisation's objects can be found without reading its database, every object key in the file store starts with the Organisation's identifier. Approved by the product owner on 6 Oct 2026 (GC9-10); [imports-and-opening-data.md](imports-and-opening-data.md) 15.1 holds the rule, where the bucket key is fixed per stored file.

### 2.2 What a backup never holds

- No encryption key: neither an Organisation's data key nor the backup key (2.3). A backup and the key that opens it are never kept together (`PRD-SEC-006`, `POL-18.02`).
- No environment secret: database passwords, bucket credentials and the like stay in the environment's variables ([deployment.md](deployment.md) section 9).
- No plaintext of an encrypted field or file. Bank details, identity documents, salary and payroll data and authenticator secrets are encrypted before they reach PostgreSQL, and every stored file before it reaches the bucket (access-and-approvals section 6; imports-and-opening-data section 11). The backup copies them as they are.
- Logs. They are pino JSON on standard output (deployment section 9) and are not part of a backup (`PRD-SEC-014`).

### 2.3 Encryption and the keys kept apart

- **The backup is encrypted as a whole** (`POL-18.02`). The application backup of 3.2 encrypts each database dump and the manifest with a backup key before they leave the command, using authenticated encryption from Node's built-in crypto, so no dependency is added. File objects need no second layer: they are encrypted with the Organisation's key already. **Design choice.**
- **The backup key is not an Organisation key.** It opens backups only. An Organisation's data key opens its encrypted fields and files only. Holding one never gives the other. **Design choice.**
- **Key identifiers, not keys.** Every encrypted field and file records the identifier of the key version that encrypted it, and the manifest lists the identifiers each backup needs. A restore refuses before writing anything when a listed key version is not available (4.2). **Design choice.** It makes key rotation, which waits for production hosting (access-and-approvals section 6; D-1, RR-029), safe for old backups: a key version is kept while any backup still kept needs it.
- **The backup key is a key pair** (GC9-17; product owner, 10 Oct 2026). The environment holds only the public part, with which the backup command encrypts (X25519 key agreement and AES-256-GCM, both in Node's built-in crypto, so no dependency is added). The private part, which opens backups, is never an environment secret: it exists only in the custodian's kept copies and is handed to the restore command at the prompt, never echoed or logged. A stolen environment then cannot open a backup, and every restore, drills included, proves the kept copy (section 6). The cost, accepted: no restore runs without the custodian, and a lost private part cannot be made again from the environment. Not chosen: one secret key held in the environment, which anyone reading the environment's variables could use to open every backup.
- **Each backup is signed** (product owner, 12 Oct 2026). The backup key's public part, which seals a backup, is no secret, so anyone holding it could seal a planted backup. The backup command therefore signs each backup with a signing key held only by the backup runner, never by `app` or `worker` (Ed25519, in Node's built-in crypto, so no dependency is added). The restore verifies the signature with the signing key's matching public part and refuses an unsigned or badly signed backup before it reads anything else (4.2 step 1). What is signed is the backup's final statement, written after its manifest is read back: the backup's identifier, the manifest's name and hash, the result and its failures, and the signing key version's identifier (10.4). The signing key is never logged or stored by the application. **Decision** (product owner, 12 Oct 2026).
- **Copies of the keys are kept apart** (GC9-12). Copies of every key version, of each Organisation's data key, of the backup key and of the backup signing key (product owner, 12 Oct 2026), are kept outside Railway, apart from every backup, in a store that holds no backup and that Railway credentials do not open, by a named custodian. **Design choice.** This design names no custodian. On `dev` the product owner names the custodian before the drill (`S1-F14-T04`), and has done so (product owner, 9 Oct 2026; RR-236). On production, custody belongs to KDPS's Owner and Admin under policy 18 (`POL-18.02`; KDPS Owner question 62, RR-237); it blocks live use only, never building or testing. Losing every copy of a key loses what it opens (2.4), so the drill checks the copies too (section 6).
- Key storage, backup and rotation on production are designed with production hosting (D-1, RR-029; GC9-11).

### 2.4 Key recovery

What happens when a copy of a key is lost or damaged (`POL-18.02`). **Design choice** throughout, approved as written (GC9-18; product owner, 10 Oct 2026).

- **Every key version has an identifier.** The identifier is computed from the key and a fixed label (HMAC-SHA-256 of the label under a subkey derived from the key for identifiers alone, shortened; 10.4), so it names the key without revealing it. `access` keeps the identifiers of each Organisation's data key versions in its database (a `key_version` row: identifier, purpose, when it was first used; never the key), and each backup's manifest and `kernel.backup_record` keep the backup key's (2.3, 3.2). Every encrypted field and stored file names the identifier that encrypted it (2.3).
- **A wrong key is found before it is used.** At start, the server computes the identifier of each Organisation's data key in its environment and refuses to start when it is not a version that Organisation's database lists, naming the Organisation code and the identifiers, never the key ([deployment.md](deployment.md) section 9 already refuses a missing key). So a damaged or swapped key is never used to write data no one can open later. Where no version is listed yet, the key is proved against the data before it is recorded as the first version: a sample of the Organisation's existing encrypted values must open with it, and a key that cannot open them is refused, naming identifiers only (product owner, 12 Oct 2026; 10.4). The backup command checks the backup key's identifier against the last complete backup the same way and refuses on a difference, unless the operator states that a new backup key version starts.
- **The environment's copy lost or damaged.** The custodian gives the kept copy of that key version to the platform operator (on `dev`, both are the product owner; on production, KDPS's, RR-237), who puts it back as the environment secret. The start check then proves it by its identifier. Nothing in the database changes.
- **The record.** The operator then runs an operator command, like the recovery of a first user (access-and-approvals 3.2): never an API route, under the `setup` service identity. It asks at the prompt which key version was recovered (its identifier), why (lost, damaged, or a suspected leak), how it was found, and who gave the kept copy, and writes a `key-recovered` access record in the Organisation's database, or for the backup key in every Organisation database the key's backups cover ([numbering-and-audit.md](numbering-and-audit.md) 5.1; section 13). It never takes or records the key itself (`PRD-SEC-014`).
- **A kept copy lost or damaged**, with the environment's copy sound: the custodian makes a new kept copy from the environment's at once, checked by its identifier, and the operator records it with the same command. The backup key's private part (GC9-17) has no copy in the environment, so a lost kept copy is a lost key (below) unless the custodian holds a second copy; how many copies the custodian keeps, and where, is the custodian's under policy 18 (RR-236, RR-237).
- **A suspected leak** is not a loss: the key stays usable, and replacing it is rotation, designed with production hosting (GC9-11). Until then a suspected leak on test hosting is reported to the product owner, who decides what follows.
- **What the drill checks** (section 6). The restore uses the custodian's kept copies, never the environment's: every key version the manifest lists is taken from its kept copy and must match its identifier, and the drill record says so for each. A drill that had to use an environment copy fails that check.
- **As built** (`S1-F14-T02`, 12 Oct 2026): identifiers, the start check and the first version recorded at start are in 10.4. The restore takes every key version the manifest lists from its kept copy at its prompt, several versions of one Organisation included, and names each version used in the drill record (`S1-F14-T03`; 10.5). The operator command that records a key recovery is not built; no `S1-F14` ticket names it (RR-530).
- **What is lost if every copy is lost.**
  - *An Organisation's data key version:* every value and file it encrypted, in the live database, the file store and every backup: bank details, identity documents, salary and payroll data, authenticator secrets, restricted values kept in refused requests, receipt names and references, and every stored file's content. Records that are not encrypted are untouched, and each stored file keeps its content hash, which proves what was held. Recovery is by people: every user enrols the authenticator again (the operator's recovery of the first users, then the Admin's resets; access-and-approvals 3.2), and encrypted master values are entered again with their independent approvals. Each loss is raised as an exception with its evidence (`PRD-EXC-001`). A new key version is made for new data.
  - *The backup key version:* every backup it encrypted can no longer be opened. The live data is untouched. A new backup key version is made and a new application backup taken at once; the old backups are recorded as unopenable and are never offered for restore.

## 3. Two kinds of backup

### 3.1 Platform backups

- On `kdps-test`, Railway's scheduled PostgreSQL backups are turned on, and one restore is practised before the go-live drill ([deployment.md](deployment.md) section 4; `POL-18.03`).
- What they hold, how often they run, how long they are kept, whether they are encrypted at rest, and whether one can be restored into a new service rather than over the old one, are Railway's. None is verified (GC9-A1 to GC9-A3). A platform backup is restored with the platform's own tools and then proved with the checks of 5.1, which need nothing from the backup itself.
- Platform backups do not hold the bucket. The file store is copied by the application backup (3.2) or by the means production hosting chooses.
- The test setup makes no recovery promise; the `POL-18.01` targets apply to production (deployment section 4; DEC-028). The earlier POS stays the system of record, and a PT file already loaded into it is that system's record, so losing test data loses nothing official (DEC-053).

### 3.2 The application backup

An application backup is the backup this design builds and proves in stage 1. It is portable: it restores into any PostgreSQL 17 server and S3-compatible store, so it does not depend on a provider's restore tools. **Design choice.**

1. **One snapshot per database.** For each database the backup command opens a repeatable-read, read-only transaction, exports its snapshot, and runs PostgreSQL's own dump tool on that snapshot. So the dump and everything else read in that transaction see the same committed state (PRD Stack: Database). **Design choice.**
2. **Control totals in the same snapshot.** In that transaction, each module that holds records computes its control totals through the restore contract (10.1): named counts and sums over its own tables, in a fixed order, money as integer paise (`PRD-MOD-014`), and Unknown values counted apart, never as zero (`PRD-MOD-015`). For example, journals and the debit and credit totals of each book; movements and quantities of the stock ledger; stored files and attachments; allocations and the highest sequence number of each series. **Design choice.**
3. **The latest audit seal** of the Organisation is read in the same snapshot ([numbering-and-audit.md](numbering-and-audit.md) 4.4).
4. **Encrypt and store.** Each dump is encrypted with the backup key (2.3) and written to the backup store, with its hash.
5. **Copy the file store** after every database snapshot is taken (3.3).
6. **Write the manifest**, encrypted with the backup key: the backup's identifier; the environment it came from; the code commit that took it; for each database, the snapshot time, the last migration applied and the hash of its encrypted dump; for each Organisation, its control totals, its latest seal, the list of stored-file keys its snapshot references, and the key identifiers its data needs. **Design choice.**
7. **Check the backup** before calling it complete: every stored-file key the snapshots reference is present in the backup store, and every dump decrypts and matches its hash. A backup that fails is kept with its failure and never offered for restore. **Design choice.**
8. **Record it.** After the backup is complete, the command appends a row to `kernel.backup_record` in each Organisation database it backed up (section 11), so the operations view can show the last good backup (`PRD-SEC-013`). The record of a backup is therefore in the next backup, not in its own. The directory database gets no such row: it holds only routing facts (DEC-093).

- The command reads every row, so it needs a role that row-level security does not filter. The restore creates databases and loads them, so it needs the migration role in any case (4.2). The backup reads as the migration role on `dev` and `kdps-test`, the owner, which row-level security does not filter because no table forces it ([code-house-rules.md](code-house-rules.md) 5.1); the production hosting design chooses again, with its key storage (GC9-7; product owner, 10 Oct 2026; D-1, GC9-11). Nothing new is created and no Railway capability is needed, and the operator who runs the backup already holds this credential for `pnpm migrate` and the setup step. The alternative weighed for production is a separate read-only role with `BYPASSRLS`, so that a leaked backup credential cannot change data; only a role that already has `BYPASSRLS` can give it, which on Railway is not verified (GC9-A5).
- It is an operator command, like the setup step: never an API endpoint, never run by `app` or `worker`, and it holds credentials they do not hold (code-house-rules 4.3; access-and-approvals 9.11; DEC-112, CH-1). **Design choice.**
- **As built** (`S1-F14-T02`): `pnpm --filter @apparel-os/server backup`; the details settled while building it are in 10.4.

### 3.3 Database and files consistent

- A file is stored before the transaction that records it, never inside it (code-house-rules 8.3; `PRD-INT-006`). Its stored-file record is append-only and its object key is fixed ([imports-and-opening-data.md](imports-and-opening-data.md) 15.1; `PRD-MOD-011`). The application never overwrites an object, and deletes one only through the retention deletion of 8.5, after its record is gone. **Design choice**, a rule the file-store adapter enforces: the adapter used by every other path offers no delete (as built, `S1-F06-T05`).
- So every stored-file record in a snapshot names an object that was already in the bucket when the snapshot was taken, and is still there unchanged: retention deletes the record before the object (8.5), so an object a snapshot's record names is never gone before the copy. A copy of the bucket taken after the snapshots holds every object they reference. **Design choice:** the database snapshots come first, the file copy second (3.2).
- The copy may also hold objects no snapshot references: files stored after the snapshot, or by a transaction that rolled back. They are kept and listed, never deleted (section 8). After a restore they are reported in the drill record as objects with no record, with their store time, because one stored after the recovery point can be evidence of lost work (`POL-18.04`; 4.5).
- The copy is incremental: an object whose key is already in the backup store is not copied again, since keys are never reused for other content. Each copy is checked against the backup store's own object listing (GC9-A4).
- Whether the bucket can refuse overwrites and deletes by itself, through object versioning or object lock, is a Railway capability not verified (GC9-A4). The rule above does not depend on it.

### 3.4 Frequency and how long backups are kept

- **No value is set here.** How often backups run and how long each is kept follow from policy 18 and are KDPS's and the Admin's. Nothing has a default (DEC-105).
- **Production.** The recovery point and recovery time are the provisional targets of `POL-18.01`, subject to measured restore tests and KDPS's acceptance (V-12, RR-075). A backup taken now and then cannot meet a recovery point measured in minutes; production hosting needs continuous backup of each database and of the file store. How it is done is part of the production hosting design (D-1, RR-029; GC9-1).
- **How long backups are kept** is OPEN (GC9-2): KDPS Owner and Admin, with the CA where a backup outlives a record's retention period (8.4).
- **Test setup.** On `dev`, an application backup is taken on demand for each drill. On `kdps-test`, Railway's scheduled backups run with the options Railway offers (deployment section 4); an application backup there holds real KDPS data, so it is taken only after KDPS's agreement to real data (D-4, DEC-052) and is kept in the same hosting.
- **Drills.** The Admin conducts a restore drill before go-live and after major recovery changes; a quarterly drill after that is proposed and awaits KDPS Owner and Admin sign-off (`POL-18.03`, DEC-075). The restore operator, the pre-launch date and the cadence are OPEN (V-63, RR-123).

## 4. Restore

### 4.1 Into a fresh target

- A restore writes only into a fresh target: a PostgreSQL server with no Apparel OS database and an empty file store, with the migration and runtime roles created as the roles runbook says ([code-house-rules.md](code-house-rules.md) 5.1). It never writes over the source environment or into a database that already holds rows. **Design choice.** The restore refuses any server that already holds an Apparel OS database, not just a directory database that is not empty, and the source's own server (product owner, 12 Oct 2026; 10.5). Switching traffic from the source to the restored target is a separate, recorded step after reopening (4.3).
- A backup restores only into the environment it came from: a `dev` backup into a `dev` target, a `kdps-test` backup into a `kdps-test` target. The two are never mixed ([deployment.md](deployment.md) section 1). The manifest names its environment and the restore compares it with the target's. **Design choice.**
- Restoring onto production hosting from test hosting is never a switch: a Store switches only on production hosting, at its own switch count (`PRD-LIF-026`, DEC-028).

### 4.2 Steps

The restore command is an operator command, like the backup command (3.2). It writes each step with its start and end time to the drill record (section 6) as it goes. **Design choice.**

1. **Check before writing.** The backup's signature verifies, before anything else is read (2.3); the manifest is the one it signs and decrypts with the backup key; its environment matches the target's (4.1); the target is fresh (4.1); every key version it lists is available (2.3); the running code holds every migration the backup had applied. A backup taken by newer code is refused; older code's backup is restored, then migrated forward in step 3. Any failure stops the restore with nothing written.
2. **Restore the databases.** The directory database first when the whole environment is restored, then each Organisation database, from the dumps, as the migration role into databases it creates. Each dump's hash is checked before it is read.
3. **Apply the runner's database step and migrate.** The runner applies the database-level privileges to each restored database, as it does on every run and as the test helper does for copies ([code-house-rules.md](code-house-rules.md) 4.3, 11.3), then checks the recorded checksums and applies any newer migration.
4. **Compare the control totals and place the recovery hold.** Each restored Organisation's control totals are compared with the manifest's before anything is written to its database (5.2), and the hold is placed on it before any request reaches it (4.3).
5. **Point the directory at the target.** Where a restored Organisation's database is now found elsewhere, its directory entry in the target is written or changed to the new place, and the change is written to the drill record.
6. **Copy the file objects** of each restored Organisation into the target's file store.
7. **Run the restore participants** of section 10.1, in tier order: `access` ends sessions (4.4); `numbering` pauses every series (5.3); `files-imports` checks every stored file and attachment (5.1); every module that holds records checks its references and computes its control totals (5.1, 5.2); `audit` verifies the seal chain (5.4) and then records the outcome of every step as audit records under the restore's internal service identity (access-and-approvals 2.3; `PRD-SEC-018`).
8. **Report.** The drill record lists each check with its result, and the operations view shows the Organisation as restored and held (`PRD-SEC-013`).

Steps 1 to 8 run without people. What follows needs authorised people (4.3): reconciling series, raising and settling recovery gaps and failed checks, validating, and reopening.

- The order of steps 4 and 5, the hold placed and the totals compared before the directory names the restored database, is the product owner's (12 Oct 2026): the hold is in place before any request can find the database.
- **As built** (`S1-F14-T03`): `pnpm --filter @apparel-os/server restore`. The details settled while building it are in 10.5.

### 4.3 Recovery hold and reopening

- **The hold.** A restored Organisation is held: `kernel`'s command runner refuses every command except sign-in, session and access commands (revocations included, 4.4), reading, and the recovery commands below. A refused command names the hold as its reason. Jobs and outbox delivery wait too, except the participants' own steps. **Design choice**, implementing `POL-18.03`: Operations and Accounts validate stock, bills and financial totals before reopening.
- **Recovery commands.** Three commands act while the hold is on: reconcile a series, record a validation, reopen. Each runs as the acting user under Authorise and writes its audit record (`PRD-ACS-013`, `PRD-INT-004`). Reopening lifts the hold through `kernel`'s interface, a call down a tier, and the `recovery_event` row it appends is written as the runtime role (section 11). All three belong to `configuration`, which owns availability and already calls `audit` (GC9-8; product owner, 10 Oct 2026; module-map 4.4). Reconcile calls `numbering`'s reconcile operation: `configuration` and `numbering` are both tier 1, so this is a same-tier call that module-map 4.4 lists and `pnpm check:modules` allows (module-map section 3). One place and one screen hold everything a restore needs before reopening, and `numbering` stays a module that calls no one. Not chosen: reconcile in `numbering`, or in each module that owns series.
  - **Reconcile a series** after a restore, with its evidence (5.3), through `numbering`'s reconcile operation.
  - **Record a validation**: one by Operations and one by Accounts, each saying which of stock, bills and financial totals it compared, against what, and with what evidence (`POL-18.03`). Which of the three each validates is not split here; the policy names both. The evidence is text, since no file is stored while the Organisation is held (product owner, 12 Oct 2026).
  - **Reopen**: refused until both validations are recorded, every series the restore paused is reconciled, every recovery gap (4.5) has been raised as an exception that is resolved or accepted, and every failed check (5.1) has either passed when the checks ran again or been raised as an exception that is resolved or accepted (product owner, 12 Oct 2026). The settled exceptions take the place of an attestation by the person who reopens. Reopening lifts the hold and records the time, which ends the measured recovery time (section 6).
- **Who** holds the restore operator's role, the two validations and reopening is KDPS's. Whether one person holding both the Operations and the Accounts persona may record both validations, and who may reopen, are OPEN (GC9-6; V-63). On `dev` the drill uses synthetic users and labelled synthetic role assignments.
- **Any paused series blocks reopening** (product owner, 12 Oct 2026): every series the restore paused is reconciled before the Organisation reopens, so none is still paused after it. While held, a document that needs a paused series is unavailable, and Allocate refuses it ([numbering-and-audit.md](numbering-and-audit.md) 3.2).
- **Policy gates still apply.** Reopening switches on no policy-dependent operation: the availability check answers as it did before the restore (`PRD-SEC-017`).

### 4.4 Sessions, devices and service identities

- **Sessions.** A restore can bring back a session that was ended or revoked after the recovery point. So `access` ends every session of a restored Organisation, and everyone signs in again with the second factor (`PRD-SEC-001`, `PRD-SEC-008`). **Design choice.**
- **Revocations after the recovery point** of a device, a user or a service identity are lost with everything else after it. Before reopening, the restore operator applies again each revocation known from outside evidence, such as the incident record. Whether every outside service credential is replaced after every restore is OPEN (GC9-15).
- **Devices.** A restored server never lets a device continue a cloned or restored identity (`PRD-OFF-010`). How an offline counter's queued bills and series meet a restored server is the offline counter design (GC-8; `PRD-OFF-009`).

### 4.5 Outside systems and the recovery gap

- **The recovery gap** is the work done after the recovery point that the restored database does not hold. It is reconciled against counter, provider and Tally records; no transaction is silently lost or duplicated (`POL-18.04`).
- **Held outside deliveries.** No outbox row is delivered while the hold is on (4.3). After reopening, rows bound for a module inside the Organisation are delivered as usual; their consumers are idempotent on the event's identity, so a delivery made again changes nothing (`PRD-INT-008`). Rows bound for an outside system (Tally, GST, bank, messaging) stay undelivered until their outcome is reconciled with that system, because a delivery the restored database thinks pending may already have reached it after the recovery point (`PRD-INT-006`, `PRD-INT-007`). **Design choice.**
- **Repeated requests.** An idempotency key recorded after the recovery point is lost, so a client repeating that request runs it again; its first effect was lost too (`PRD-INT-002`). An offline bill uploaded again is matched by its device and number (GC-8; `PRD-OFF-009`).
- **Each gap is an exception.** A piece of outside evidence that the restored records cannot explain becomes an exception with an owner and evidence (`PRD-EXC-001`; access-and-approvals section 12), raised through a restore participant. **Design choice.** Once the exception-code series is reconciled, each gap after the recovery point, such as a stored file with no record stored after it, is raised as an exception, and reopening waits until each is resolved or accepted (product owner, 12 Oct 2026). As built, the module that owns the gap reports it through its check (`files-imports` for an object with no record), `kernel` keeps it, and `exceptions`' restore participant raises it, since the exception is `exceptions`' record and `exceptions` sits above the modules that find gaps (10.5).
- **Stage 1 sources.** In stage 1 the only gap sources are the number series (5.3) and objects in the file store with no record (3.3). Later designs add theirs through the restore contract: the offline counter's queues (GC-8, stage 4), card and UPI providers and IRN (stage 4), bank and Tally (stage 5).

## 5. The restore proof

### 5.1 Checks on every restore

These checks run on every restored Organisation, from an application backup or a platform backup alike. **Design choice.**

| Check | What passes | IDs |
| --- | --- | --- |
| Stored files | Every stored-file record names an object in the restored file store; the object decrypts with the key version it names; the hash of the plaintext equals the record's content hash, which was taken before encryption ([imports-and-opening-data.md](imports-and-opening-data.md) 3.1) | `PRD-IMP-002`, `PRD-ACP-019` |
| Attachments | Every attachment opens from its record: read through `files-imports` as a synthetic reader authorised for that record, it returns those bytes; a reader outside the record's scope is refused | `PRD-SEC-005`, `PRD-ACP-019` |
| Links inside a module | Every foreign key holds: the dump tool creates foreign keys after loading rows, so PostgreSQL checks every row again | `PRD-ACP-019` |
| Links across modules | No foreign key crosses schemas (code-house-rules 3.2), so each module checks, through the other module's interface, that every reference it holds to another module's record resolves | `PRD-MOD-002`, `PRD-ACP-019` |
| Numbering | Every series is paused (5.3) | `POL-18.04` |
| Audit | The seal chain verifies (5.4) | `PRD-SEC-007` |
| Module invariants | Each module's own checks: for example every journal balances, and stock balances equal the sum of their movements (stock-ledger 11.7) | `PRD-ACP-019` |
| Objects with no record | Listed with their store time; kept | `POL-18.04`, `POL-18.05` |

A failed check is shown in the drill record and the operations view, and the Organisation stays held. A check is never skipped to let a restore pass. A failed check does not block reopening for good (product owner, 12 Oct 2026): once its cause is put right, such as an object put back, the checks are run again (`restore --recheck`) and recorded as a new check run; a failure that remains is raised as a gap exception and resolved or accepted (4.3, 4.5). Every check run and every validation are recorded.

- **Attachments, as built.** An attachment's check reads its file through `files-imports`' own opening of the stored file, and puts Authorise's own rule to two synthetic readers held in memory. A read through `files-imports` as a synthetic reader written into the restored data is not made: it needs a user, a role and a role assignment written into a real Organisation's records, which would stay there, append-only, and would let a person sign in as the synthetic reader while the Organisation is held. Row-level security on the attachment, the other half of what a reader meets, is proved by the restore tests through the restored application, with real synthetic readers who sign in again (12 test 2). **Design choice** of the build, amending the Attachments row above with its reason, as the `S1-F14` review of 12 Oct 2026 asked.

### 5.2 Comparison with the backup's control totals

- For an application backup, each module computes its control totals on the restored database with the same function that computed them in the backup's snapshot (3.2). Every total must be equal. **Design choice.**
- For a platform backup there are no snapshot totals. The proof then rests on 5.1 and on the recovery gap (4.5), and the drill record says that no comparison was possible (`PRD-PRF-004`).

### 5.3 Number series

- After a restore every series is paused until it is reconciled against the counters' records and other evidence. Its next number is then set past the highest number known to be issued, and the skip is recorded with its reason ([numbering-and-audit.md](numbering-and-audit.md) 3.6; `POL-18.04`). This design runs it, as that section says.
- **Pause.** `numbering`'s restore participant pauses every open series and writes a series event for each (numbering-and-audit 6.1). It needs no caller from the owning module. **Design choice**; numbering-and-audit 3.7 lists it.
- **Reconcile.** An authorised person records, for one series, the evidence of the highest number issued: printed or uploaded bills, the counters' records, or a statement that no document left the system, with its reason. `numbering` sets the next number past the higher of that number and the highest allocation in the restored database, records the skip and the reason as the series event "reconciled after a restore", and releases the series. **Design choice** (4.3).
- A number is never given twice, including after a restore (`PRD-ACP-019`, `PRD-LIF-020`). A reconciliation never lowers a series' next number.
- **Import batch codes** come from a `numbering` series ([imports-and-opening-data.md](imports-and-opening-data.md) 15.1), so they are paused and reconciled like any other. A PostgreSQL sequence would restart from the snapshot after a restore and could give a code a second time, against `PRD-ACP-019`. Approved by the product owner on 6 Oct 2026 (GC9-9); it closes RR-204.

### 5.4 Audit seals

- `audit`'s restore participant recomputes the seal chain over every sealed block and reports any difference ([numbering-and-audit.md](numbering-and-audit.md) 4.4; `PRD-SEC-007`).
- For an application backup it also checks that the chain ends at the latest seal the manifest holds (3.2). The manifest is kept apart from the database and encrypted, so a chain rebuilt over altered rows would not end at that seal. **Design choice.**
- Rows recorded after the last seal are sealed by the sealing job after reopening, as usual.

## 6. The restore drill record

Every restore, drill or real, produces a drill record. **Design choice.**

- **Who and when:** the drill's purpose (a drill, or a real restore and its cause); who conducted it, and for a go-live drill the Admin who conducts it (`POL-18.03`); the restore operator; the backup used and its recovery point; the start and end time of every step of 4.2; the time each validation was recorded and by whom; the time of reopening.
- **Measured times:** recovery time, from the start of the restore, or for a real failure from the time it was declared, to reopening; and the data lost, from the recovery point to the time the failure was declared. On production they are compared with the `POL-18.01` targets; on the test setup they are measured, not promised (deployment section 4).
- **Results:** every check of 5.1 and 5.2 with its result and counts; every recovery gap and how it was settled; each series reconciled, with its skip and reason; the key versions used, by identifier, and confirmation that each came from its kept copy and matched its identifier (2.3, 2.4).
- **Where it is kept:** the restore command writes it as a structured file and a readable text, both kept beside the backup and handed to the person who conducted the drill. It is the evidence for the stage 1 exit check (`S1-F14`; [stage 1](../../plan/stage-1/README.md) exit checklist 7.1) and for the Admin's drills. The restored database also keeps the restore's history in `kernel.recovery_event` (section 11) and in its audit records (5.4).
- A drill record holds no record data, no restricted value and no secret (`PRD-SEC-014`).

## 8. Retention, deletion and legal holds

### 8.1 Retention schedules

- Retention is set by record class, including financial, stock, employee, customer and audit records, and validated against legal retention requirements (`POL-18.05`). The periods are OPEN (V-13, RR-076; KDPS Owner, Admin, CA). Nothing has a default (DEC-105).
- A retention schedule is a setting in `configuration`, versioned like any setting (module-map 11.2). It names a record class and, once KDPS sets it, its period and the date the period counts from. **Design choice.**
- Each module declares which of its record types belong to which class. A record type that belongs to no declared class is never deleted. **Design choice.**
- Customer consent and notices are designed with the stage 4 counter, and employee data with the stage 6 HR design (module-map MM-15, DEC-105; `PRD-SEC-009`, `PRD-SEC-010`).

### 8.2 Deletion

- **Nothing is deleted while no retention period is set** for its class (`POL-18.05`; [numbering-and-audit.md](numbering-and-audit.md) 4.6). Nothing is deleted under a legal hold (8.3).
- Deletion after retention runs only through a named retention function of the module that owns the records. The trigger on an append-only table admits that function alone ([code-house-rules.md](code-house-rules.md) 7.1; `PRD-MOD-011`). For audit and access records the function is designed: one sealed block at a time, recorded (numbering-and-audit 4.6).
- For every other class the owning module designs its function before a period for that class is enabled, including how its totals stay explainable once old rows are gone. OPEN (GC9-14); it blocks only the first deletion in that class.
- Stored files, their receipts and attachments, and the objects in the file store are deleted as 8.5 says.
- Retiring demo or synthetic data never deletes real business records (`PRD-LIF-023`). A synthetic Organisation on `dev` is a separate database; removing it is not retention.
- A restore deletes nothing, and objects in the file store with no record are kept (3.3).

### 8.3 Legal holds

- A legal hold overrides routine deletion (`POL-18.05`, `PRD-SEC-009`).
- A hold is a record in `configuration`: what it covers (record classes, and a legal entity, Site, party, date range or named records), its reason, who placed it and when; and, once released, who released it, when and why. A hold takes effect when it is placed. Every retention function checks holds before it deletes and skips what any hold covers. **Design choice.**
- Which records are under a legal hold today is KDPS's, with the CA (V-13; KDPS Owner question 7, CA question 12). Who may place and release a hold, and whether a release needs a different authorised person, are OPEN (GC9-4).
- Holds are built before the first retention deletion can be enabled, together with the schedules (section 10.2).

### 8.4 Backups, restores and retention

- A record deleted under retention stays in every backup taken before its deletion until that backup expires. So how long backups are kept (GC9-2) bounds how long a deleted record can still be recovered. The CA confirms that this is acceptable for each class (GC9-2). A backup is never edited to remove a record.
- A restore brings back records deleted after the recovery point. Retention runs again once the Organisation reopens, and deletes them again where their period has passed. While the hold is on, no retention function runs. **Design choice.**
- A legal hold placed after the recovery point is lost with everything else after it. Before reopening, the restore operator places it again from outside evidence; the reopen command asks for confirmation that this was done. **Design choice.**

### 8.5 Deleting stored files after retention

A stored file is one record of `files-imports` and one object in the file store, shared by every receipt and attachment of the same bytes, whatever records they belong to (the key is `<Organisation identifier>/files/<content hash>`; [imports-and-opening-data.md](imports-and-opening-data.md) 15.1). The records that point to it may belong to different classes with different periods. This section says how such a file, its record and its object are deleted once retention allows (`POL-18.05`). **Design choice** throughout (GC9-16; product owner, 10 Oct 2026). Nothing here is built in `S1-F14`; it is built before the first retention deletion can be enabled (10.2).

- **A file follows its records** (GC9-16; product owner, 10 Oct 2026). A stored file has no period of its own. It is due only when nothing points to it any more: every attachment to it has been deleted with its attached record, and every import batch whose stored original it is has been deleted, each under its own class's retention function. So a file is never deleted while any record still in its period, or under a hold, depends on it, and an attachment never points to a missing file. Not chosen: stored files as their own record class, which could take evidence from a record still in its period (`PRD-IMP-002`, `PRD-ACP-019`).
- **Attachments go with their record.** An attachment is a `files-imports` row, so the owning module never deletes it itself. The owning module's retention function (8.2), in its own transaction, calls `files-imports`' operation "delete the attachments of a record after retention", which deletes the record's attachments through `files-imports`' retention function and writes an audit record for each. The record and its attachments go together or not at all.
- **Only a named retention function deletes.** `files_imports.delete_after_retention` is the only path that deletes a `stored_file` or `file_receipt` row; the append-only trigger admits it alone ([code-house-rules.md](code-house-rules.md) 7.1), as `audit.delete_after_retention` for audit (numbering-and-audit 4.6). It is `SECURITY DEFINER` and runs in a job of the existing worker under its own internal service identity (`files-retention`; access-and-approvals 9.11a). **Design choice.** While no class has a period, nothing points to nothing, so it finds no file due and deletes nothing (8.2).
- **Holds first.** Every record that pointed to the file was checked against legal holds when its own retention function deleted it (8.2, 8.3). Before it deletes the file, the function also asks `configuration` whether any hold names the file itself, and skips it if one does (`POL-18.05`, `PRD-SEC-009`).
- **Record first, object second.** In one transaction the function locks the stored file, checks again that nothing points to it and no hold covers it, deletes its `stored_file` row and its receipts, and appends a `stored_file_deletion` row: the stored file's identifier, its content hash, its object key, the retention schedule versions and the hold check that allowed it, when, and the job. No name or reference of a receipt is kept (`PRD-SEC-009`). It writes an audit record of the deletion under the job's service identity (`PRD-SEC-007`). After the transaction commits, never inside it (code-house-rules 8.3; `PRD-INT-006`), the job deletes the object through a deleter only this job is given; every other path keeps the adapter with no delete (3.3). The deletion row then records the object's outcome: pending, succeeded or failed, retried until it succeeds (`PRD-INT-007`).
  - If the object's deletion fails, the object stays with no record, which is safe: the restore proof lists it as an object with no record (5.1) and the drill record names it with its deletion row, so it is not mistaken for lost work.
  - The other order, object first, could leave a record naming a missing object, which fails the stored-file check of 5.1.
- **The same bytes later.** Once the row is gone, the same content can be stored again as a new stored file, with a new identifier, under the same object key; the earlier deletion row stays.
- **Objects with no record** (3.3), stored by a transaction that rolled back, have no class and are never due. They are kept and listed for now (product owner, 10 Oct 2026). How they are removed is decided by the product owner before the first retention deletion (RR-492).
- **Backups.** The object stays in the backup store for every backup that references it until the last such backup expires (8.4; GC9-2). Backup copies are never edited. Because the file-store copy is incremental (3.3), an object in the backup store is removed only when no kept backup's manifest lists it; removing expired backups is designed with how long backups are kept (GC9-2).
- **Restores.** A restore from a backup taken before the deletion brings back the record, its attachments and the object (from the backup store), and 5.1 passes for them. Retention runs again after reopening and deletes them again, the deletion row of the restored database being gone with the recovery gap (8.4).

## 9. The complete export

### 9.1 What stage 5 builds

The complete export is built in stage 5 by `site-lifecycle`, with closure and relocation (`S5-F09`; module-map section 5). This section sets its scope; the stage 5 design sets the rest (GC9-13).

- **What it holds:** masters, documents, lines, stock and accounting movements, attachments, mappings and audit history, with relationships that can be rebuilt and totals that reconcile (`PRD-LIF-022`).
- **Identities kept:** every record keeps its UUIDv7 identifier and its business code, and references stay as identifiers, so the relationships rebuild. An export never gives a code to a new record and never reuses one (`PRD-ACP-019`).
- **Versions kept:** effective-dated versions with their dates, and the version each transaction used.
- **Attachments** with the content hash of each file, so the receiver can check every file.
- **Control totals** computed by the system, not copied from any source file, stated in a manifest beside row counts and file hashes (`PRD-LIF-022`). KDPS's own files disagree with their totals in many places ([prd-fit.md](../../data-notes/prd-fit.md) 3.3).
- **Access:** an export is restricted to the data the exporter may see (`PRD-EXC-011`, `PRD-SEC-005`). A restricted field the exporter's assignment does not grant is left out, and the manifest says which classes were left out (`PRD-ACS-008`). An export that includes any restricted field writes an access record ([numbering-and-audit.md](numbering-and-audit.md) 5.1; `PRD-SEC-007`).
- **Open for stage 5:** its scopes (whole Organisation, legal entity, Site at closure), its file format, how the package is protected in transit and at rest, and who may run it (GC9-13).

### 9.2 What stage 1 needs

- Every record keeps its identifier and business code, and nothing reuses one, including after a restore (5.3; `PRD-MOD-008`).
- Each module computes named control totals over its own records (10.1). Stage 5 reuses the same definitions where the export's totals are the same, read through declared read models (`PRD-MOD-003`). **Design choice.**
- Nothing else of the export is built in stage 1.

### 10.4 As built (`S1-F14-T02`, 12 Oct 2026)

What the backup's build settled where this design left it open. None is a KDPS value; none sets a frequency, a keeping period or a custodian.

- **Key version identifiers** (2.3, 2.4). An Organisation key version's identifier is HMAC-SHA-256 of the label `apparel-os/key-version` under the key's identifier subkey, its first 128 bits as lower-case hex. The identifier subkey is HKDF-SHA-256 of the key with info `apparel-os/key-version-identifier`, never the raw key: every other subkey's info is `apparel-os/<purpose>` with a one-word purpose, so the identifier's subkey is separated from every encryption and digest subkey (domain separation; `S1-F14` review, 12 Oct 2026; nothing was deployed, so the format changed). The backup key's is HMAC-SHA-256 of `apparel-os/backup-key-version` under its public point, so the private part gives the same identifier. Every encrypted value and stored file now names it: `access.second_factor.secret_key_version`, `files_imports.stored_file.key_version`, `files_imports.file_receipt.key_version`, `merchandise.party_bank_details.key_version` (migrations 0076 to 0078), and `keyVersion` beside a restricted value kept in a refused request. A `BEFORE INSERT` trigger, `kernel.require_key_version` (migration 0075), refuses a new row without one (`AO018`). It checks the identifier's form only, not that `access.key_version` lists it: the first version is recorded at the server's first start, after the setup step and the fixtures may already have written encrypted rows, and a `kernel` guard reading `access`'s table would cross the ownership of tables (code-house-rules 3.2). The start check (below) and the restore's checks (`access`: every authenticator secret's key version is listed; `files-imports`: every stored file opens with the version it names) prove it instead. Rows written before keep none: every one of them was encrypted by the Organisation's first key version, the only one before rotation (GC9-11), and append-only rows are never changed.
- **The start check** (2.4). `app` checks at start; `worker` holds no Organisation key and checks none. An Organisation whose database lists no key version yet, as every one did before this build and as a new one does until the server first starts after its setup step, has its environment key recorded as its first version at that start: until then nothing names a version to compare with. Before it is recorded the key is proved against the data (product owner, 12 Oct 2026): the oldest encrypted authenticator secrets, `access`'s own encrypted values, at most 20 (`FIRST_VERSION_SAMPLE`, a technical limit, not a KDPS value), must each open with it; otherwise the server refuses to start, naming the Organisation, the key's identifier and the rows' identifiers. An Organisation with no such value yet has nothing to prove the key against. Other modules' encrypted values are not sampled at start, since `access` reads only its own tables; the restore's checks open them. An Organisation the directory lists with no key in the environment is left as before: the key refuses when first needed. The check reads and writes the unscoped `access.key_version` before any actor exists, a fourth path of code-house-rules 6.3.
- **Signing** (2.3; product owner, 12 Oct 2026). `AOS_BACKUP_SIGNING_KEY` on the backup runner holds an Ed25519 private key (base64 of its PKCS #8 DER form); `AOS_BACKUP_SIGNING_PUBLIC_KEY` on the restore runner holds its public part (base64 of SPKI DER), set from the custodian's kept copy. The signing key version's identifier is HMAC-SHA-256 of `apparel-os/backup-signing-key-version` under its public point, 128 bits. After the manifest is written and read back, the command writes `backups/<backup id>/manifest.signature`: the statement (format `backup-signature/1`, the backup's identifier, the manifest's object name and the SHA-256 of the sealed manifest as stored, the final result and its failure kinds, the signing key version) and an Ed25519 signature over a fixed label and the statement's exact bytes, both in base64. The statement is the backup's final word: the manifest says what the checks of the dumps and objects found, and a manifest that fails its own read-back is recorded as failed in the signed statement and in `kernel.backup_record`, never left saying complete alone. A failed backup is signed as failed, so a restore refuses it as failed rather than as unsigned.
- **Sealing** (2.3). One backup makes one ephemeral X25519 key pair; its agreement with the backup key's public part, through HKDF-SHA-256, gives the backup's content key. Each object is the header (`AOSB`, format 1, the backup key version's identifier, the ephemeral public point, a nonce), the AES-256-GCM ciphertext and its tag; the header and the object's name are the associated data. The private part, given as base64 of its PKCS #8 DER form or as PEM, opens any object; nothing else does.
- **The check of 3.2 step 7.** The command never holds the private part (GC9-17), so "every dump decrypts" is checked with the backup's content key, which the command holds in memory for its run only: each dump and the manifest are read back from the backup store, their SHA-256 compared with what was recorded, and each decrypted whole and its tag checked. The private part opens the same objects (the tests prove both).
- **The backup store.** A bucket apart from the file store, reached with six variables of its own (deployment.md section 9). Layout: `backups/<backup id>/directory.dump`, `backups/<backup id>/organisations/<Organisation identifier>.dump`, `backups/<backup id>/manifest`, and `files/<object key>` for the file store's objects, shared by every backup. Every write refuses a key that is taken, so nothing is overwritten.
- **The file copy** (3.3). Every object under the Organisation's identifier is copied, whether a snapshot's record names it or not; one already in the backup store is not copied again.
- **The manifest** (3.2 step 6), format `backup-manifest/1`: the backup's identifier, environment, code commit (Railway's `RAILWAY_GIT_COMMIT_SHA` where set, GC9-A5), start and finish times, the backup key version, the result and its failures by kind, and for the directory and each Organisation the dump's object name, database name, snapshot time, last migration, SHA-256 and size; for each Organisation also its identifier and code, every participant's control totals, the latest audit seal (block number and hash), the object keys its records name and the key versions its data needs with their uses (null for values written before key versions were recorded).
- **Failed backups** (3.2 steps 7 and 8). A failed backup is recorded too: its manifest says `failed` with its failures, and each Organisation's `kernel.backup_record` row says `failed` with the kinds (`object-missing`, `dump-hash-differs`, `dump-does-not-decrypt`, `manifest-does-not-decrypt`, `dump-tool-failed`, `file-copy-failed`), so the operations view shows it beside the last complete one. A failed backup is never offered for restore.
- **The dump tool.** `pg_dump --format=custom --snapshot=<id>`, given the connection through libpq's variables, so no password is ever an argument: the user and password percent-decoded, the port 5432 when none is given, and every other connection parameter (`sslmode`, `sslrootcert`, `options` and the rest) passed through as its libpq variable; a parameter libpq has no variable for is refused, never dropped. Every database name is letters, digits and `_` of at most 63 characters before any tool is given it, so a name holding `=` or starting with `postgresql://` is never read as a connection string. It needs client tools of the server's major version (GC9-A5). A dump that fails is a failed backup, not a refusal. The real tools are tested against the tests' PostgreSQL 17, run inside its container.
- **Refusals before writing.** A connection that is not the migration role on a database it owns (so the runtime role cannot run it), a database name the tools cannot be given, a missing setting (the signing key among them), and a backup key version that differs from the last complete backup's without `--new-backup-key-version` (2.4). The directory is read once, in its snapshot: the Organisations checked before writing are the ones backed up. A refusal's reason names roles, databases and variables only; any other error, such as PostgreSQL's own words, is never made a reason, and the command logs only its class (`PRD-SEC-014`).
- **The source's server.** The manifest records PostgreSQL's system identifier of the server backed up (`pg_control_system()`, which the migration role may read), or null where it cannot be read, so a restore can tell the source's server (4.1).
- **The restore contract** (10.1). `kernel` keeps `RestoreRegistry`; the composition lists the participants (`apps/server/src/restore-participants.ts`), and a test proves that every table of the Organisation set's register has exactly one owner. Participants exist for every module holding records today, beyond the list of 10.2: `configuration`, `inbox`, `finance` · tax rules, `pos` and `site-lifecycle` too, and `kernel` for its own tables and pg-boss's `pgboss.job`, which exceptions name as `kernel.job` (code-house-rules 12.9). None of them holds an encrypted value, so none names a key version; no consumer main added reaches an outside system.
  - **Generic control totals**: for every table in name order, its rows; for every `_paise` or `_minor` column and every quantity column, its sum and its count of Unknown values, apart (`PRD-MOD-014`, `PRD-MOD-015`). Module totals beside them: the highest number allocated in each series (`numbering`), the debit and credit totals of each book (`finance` · books).
  - **Invariants**: every journal balances (`finance` · books); every balance equals its movements, Rebuild and compare's own reading (`stock` · ledger); the seal chain verifies (`audit`); every authenticator secret's key version is listed (`access`).
  - **References across modules**: the participant that owns a record declares it with the column names, or endings after `_`, that refer to it (code-house-rules 3.2: a reference column is `<record>_id`), such as `site_id`, `prepared_by_user_id` and `evidence_attachment_ids`; every other module's column with such a name is checked to resolve, and a column a foreign key covers is a link inside its module, which PostgreSQL checks.   - **Users and service identities** (product owner, 20 Oct 2026; RR-535; `S1-F14-T05`): a participant declares each column of its tables that names a user or a service identity as an actor reference, with the column that keeps its kind where the row has one: `kernel`'s `idempotency_key`, `outbox_event` and `recovery_event` `actor_id`, `access`'s `effective_grant.actor_id`, `audit`'s `audit_record.actor_id` (kind `actor_kind`), `exceptions`' `exception_event.actor_id`, and `files-imports`' `attachment.attached_by_id` and `file_receipt.received_by_id` (kinds `attached_by_kind`, `received_by_kind`). `access` marks which of its records is each kind of actor (`access.app_user`, `access.service_identity`). - **Links across modules, kept** (5.1; RR-541): a unit test checks that every declared record type, the types files are attached to, has a participant answering for it, except a named list of types to which no file is attached, each with its reason. - **Counts** (section 6): the stock ledger's check that balances equal the sum of their movements counts as checked every projection row it compares, each once, not the differences it found, so the drill record says how much was compared. Where a comparison covers only some rows of its table (a piece's place, from its last movement's in leg at its origin; a FIFO pool's layers; a layered transit value's layers), only those count for it; each table counts the union of what its comparisons cover.
- **Step 1 in the drill record** (4.2, section 6): the check before writing is recorded as the record's first step, `check before writing`, with its start and end. A refusal in it writes nothing, no drill record included, so it is recorded only once done.
- **Test data a restore cannot prove** is kept out of a world that is backed up: policy evidence written as a row with no object, and a scope naming a brand no catalogue record holds, are each reported by the checks of 5.1, as they should be.

### 14.2 The choices at a glance

Each is a **Design choice** where it is written, approved by the product owner (GC9-9 and GC9-10 on 6 Oct 2026, the rest on 10 Oct 2026); this list helps find them.

- The Organisation as the unit of restore (2.1); object keys by Organisation (GC9-10).
- Backups encrypted as a whole with a backup key apart from Organisation keys, as a key pair (GC9-17); key identifiers recorded; copies of keys kept apart (2.3; GC9-12).
- Key recovery: the start check, putting a kept copy back, its record, and the drill on kept copies (2.4; GC9-18).
- The application backup: one exported snapshot per database, control totals and the latest seal in that snapshot, an encrypted manifest, a completeness check, and `kernel.backup_record` (3.2); read as the migration role on `dev` and `kdps-test` (GC9-7).
- Database snapshots first, file copy second; the file-store adapter never overwrites or deletes; objects with no record kept and listed (3.3).
- Restore only into a fresh target of the same environment; refusals before writing; the steps of 4.2.
- The recovery hold, and the recovery commands in `configuration` (4.3; GC9-8).
- Every session ended after a restore (4.4); outside deliveries held until reconciled; each unexplained gap an exception (4.5).
- The checks of 5.1, the control-total comparison of 5.2, the pause and reconcile steps of 5.3, batch codes from `numbering` (GC9-9), and the manifest's seal check of 5.4.
- The drill record and what it holds (section 6); the temporary drill target on `dev` (section 7).
- Retention schedules and legal holds in `configuration`; record types mapped to classes; retention paused under the hold; holds placed again after a restore (section 8); stored files deleted only once nothing points to them, record before object (8.5; GC9-16).
- The restore contract (10.1), the units by module (10.2), the commands (10.3) and the tables (section 11).
