## 2. Folder layout

- A unit is `kernel` or a module, or a part of one, under `apps/server/src/modules/` (module-map 2.1 and 2.2). Its `index.ts` is its public interface. Another unit imports only that file, and only downward or along a same-tier call module-map sections 4 and 5 list (`PRD-MOD-002`). `pnpm check:modules` enforces both (`PRD-SEC-015`).
- Inside a unit:

| Path | Holds |
| --- | --- |
| `index.ts` | The public interface: the Nest module, the interface tokens and types, and the contracts the unit defines (module-map section 3, rule 6). Nothing else is exported |
| `<unit>.module.ts` | The Nest module. Every constructor injection names its token with `@Inject(...)` |
| `domain/` | The unit's own rules as plain functions and types. No database, network, clock or logger |
| `commands/` | One file per command: the steps of 8.1 for that command |
| `queries/` | Reads and the unit's declared read models (module-map section 3, rule 5) |
| `db/` | Drizzle table definitions (`schema.ts`) and the unit's SQL. Never exported from `index.ts`, so no other unit can name its tables |
| `http/`, `jobs/` | Controllers, and job and event consumers. Their rules are part B |

- Tests sit beside the code they prove: `*.test.ts` for unit tests and `*.int.test.ts` for integration tests. Tests that span units sit in `apps/server/test/`. Browser journeys sit in `apps/web/e2e/`; the counter's browser tests, such as its golden-case run, sit in `apps/counter/e2e/` (10.1; product owner, 6 Oct 2026).
- `packages/domain` holds only primitives every unit shares: money in paise, Unknown, UUIDv7 (`PRD-MOD-008`, `PRD-MOD-014`, `PRD-MOD-015`). A rule that belongs to one module stays in that module. `packages/calculations`, when it is created, follows [shared-calculations.md](../calculations/shared-calculations.md).
- Code under `src/` never imports from a test folder or a fixture (11.2).

## 3. Database layout

### 3.1 Two kinds of database

- One PostgreSQL database per Organisation, holding all its records (`PRD-MOD-001`). A directory database beside them holds only each Organisation's code and where its database is (DEC-093, `PRD-ACS-020`; [deployment.md](deployment.md) section 4).
- Each kind has its own migration set (4.1). No business table exists in both kinds, and no query joins the two. The one table both hold is the runner's own record, `kernel.migration` (4.3).

### 3.2 Schemas and tables

- Each module owns one schema, named after the module with `_` for `-`: `organisation`, `merchandise`, `files_imports`. A module's parts share its schema; each table belongs to one part, and only that part's code writes it. `kernel` owns the schema `kernel` (`PRD-MOD-002`; structure-and-masters 2.5).
- No foreign key crosses schemas. A reference to another module's record keeps its identifier, and the owner of the reference checks it through the other module's interface when it writes (structure-and-masters 2.5). Inside a schema, every reference has a foreign key.
- Names are lower-case `snake_case`; table names are singular (`journal_line`). A reference column is `<record>_id`.
- Every table has the primary key `id uuid`, a UUIDv7 made by the application through `@apparel-os/domain` (`PRD-MOD-008`). A partitioned table, such as the audit tables partitioned by recording month (numbering-and-audit 4.4), has the key `(id, recorded_at)`, because PostgreSQL requires a partitioned table's key to hold its partition key; its partitions are created ahead by restricted maintenance under the migration role, never with the runtime role's own rights: at an Organisation's setup and on a schedule, the schedule being a job of the existing worker that calls the migration role's `SECURITY DEFINER` function (12.9; DEC-118, RR-240). A failure to cover the coming months raises an alert, and an audit record is never silently dropped. The mechanism and how far ahead it reaches are specified with the first `audit` migration (DEC-112, CH-5), and written in numbering-and-audit 4.4: three months ahead, from the set's maintenance file (4.3). The register lists a partitioned table once, not each partition. No business number comes from a PostgreSQL sequence: a sequence gives numbers away on rollback, and numbers come from `numbering` (numbering-and-audit 3.2).
- Every object is written schema-qualified in SQL, and the runtime connection's `search_path` holds no application schema, so a name can never resolve to the wrong schema.
- Every table has an entry in the table register of its migration set (4.1). The entry gives its class, `scoped`, `self` or `unscoped` (6.1); the marks `append-only` (7.1), `versions` (7.3), `projection` and `locked` (a command locks its rows, 5.2) where they apply; and the section of the area design that sets the class. An `unscoped` entry names the section that says why. A table whose design does not say yet waits for that design before its migration merges.
- The register is reviewed with the migration that adds or changes the table, against the design section it names. The catalogue test compares the database with the register, not with anything the migration says about itself (10.4).
- **pg-boss** (PRD Stack: Jobs) keeps its own schema, `pgboss`, as a third-party schema. Its tables follow pg-boss, not 3.2 and 3.3: they keep their own keys, defaults and types. A migration installs and upgrades the schema at the version pinned in the lockfile; the runtime never installs or migrates it, and its queues are created by migration, because the runtime role creates no object. The register lists the schema as third-party, with the privileges the runtime role needs on it. This is checked against the pinned pg-boss version when part B adds jobs.

### 3.3 Column types

| Value | Column | Rule |
| --- | --- | --- |
| INR amount | `bigint`, name ends in `_paise` | Integer paise (`PRD-MOD-014`). Read into `Paise` through `@apparel-os/domain`, which refuses a value outside the safe integer range |
| Amount in another enabled currency | `bigint`, name ends in `_minor`, with a currency column beside it | That currency's configured integer minor unit, never paise (`PRD-MOD-014`, `PRD-MOD-015`). No such column exists until a currency other than INR is enabled; a currency-aware type is added to `@apparel-os/domain` first |
| Any amount | — | Never `numeric`, `real` or `double precision` |
| Rate, quantity with a fraction | `numeric` | Read and written as a decimal string, never as a JavaScript number |
| Unknown | A null in a nullable column | A value that means "none" is a stated value, never a null (structure-and-masters 2.4; `PRD-MOD-015`) |
| Event and recording time | `timestamptz` | Section 9. Never `timestamp` without a time zone |
| Business date | `date` | Section 9 |
| Effective dates | `daterange`, half-open `[start, end)` | 7.3 |
| State | `text` with a `CHECK` listing the state names | The names are those of [design-language.md](../ui/design-language.md) section 7. No PostgreSQL enum type |
| Payload snapshot | `jsonb` | Only for a payload whose shape a versioned Zod schema states, such as a staged import row. Never for a scope fact, an amount or a column a constraint needs |
| Code, name, text | `text` | A code is compared exactly (structure-and-masters 2.1) |

- No column has a default, except recording time (`recorded_at`, set by the database). A business value is always written by the command that knows it (`AGENTS.md`, "Never invent a value"; structure-and-masters 2.4).
- Every foreign key and every scope column has an index.

### 3.4 Database access in code

- Ordinary reads and writes use Drizzle's query builder over the unit's own table definitions (PRD Stack: Database access).
- Locking and reporting use raw SQL through Drizzle's `sql` template, always with bound parameters. SQL is never built by joining strings around a value.
- The Drizzle definitions mirror the reviewed migrations; they never create or change a table. An integration test compares each definition with the migrated database: columns, types and nullability (10.4).

## 4. Migrations

### 4.1 Two ordered sets

- `apps/server/migrations/directory/` is applied to the directory database; `apps/server/migrations/organisation/` to each Organisation database ([deployment.md](deployment.md) section 4).
- A file is named `NNNN__<unit>__<what>.sql`: a four-digit number unique and in order within its set, the unit that owns the change (`merchandise.catalogue` for a part), and a short description. One file changes one unit's schema only.
- Two branches that take the same number are fixed by the second to merge, before it merges. The runner refuses a set with a duplicate or missing number.
- Each set keeps its table register (3.2) beside its files, as `tables.json`. A set may also keep `maintenance.sql`: restricted maintenance that is no migration, such as creating the audit partitions of the coming months (3.2; CH-5). It must be safe to run any number of times. Nothing else belongs in the folder.

### 4.2 Writing a migration

- Migrations are SQL written by hand and reviewed in the pull request (PRD Stack: Database access; `PRD-SEC-015`). A migration that creates a table, in the same file:
  - adds the table's register entry (3.2);
  - grants the runtime role exactly the privileges of 5.2;
  - enables row-level security and creates the policy of 6.2 for a `scoped` or `self` table;
  - adds the guard of 7.1 for an `append-only` table and the constraint of 7.3 for `versions`.
- **Forward only.** There are no down migrations. A mistake is fixed by a new migration. A file is never edited after it has been applied anywhere outside a developer's machine; the runner refuses a file whose checksum differs from the one it recorded.
- **Compatible with the version running.** A deploy migrates before the new version takes traffic, and a failed one leaves the old version running ([deployment.md](deployment.md) section 4). So a migration never breaks the code already deployed: add first; remove or rename only in a later deploy, after no running code uses the old shape.
- **A planned brief interruption on `dev`** (product owner, 7 Oct 2026, DEC-120; RR-370, RR-400). `dev` holds only synthetic data, so a migration that is not compatible with the version running may be deployed there as a planned brief interruption: between the pre-deploy migration and the new version taking traffic, requests the old code serves may fail. The migration's header says so and names the decision (0018, 0020, 0022). `kdps-test` and production keep the rule above: add first, remove later.
- **Data.** A migration never changes or deletes rows of an append-only table (`PRD-MOD-011`). It may fill a new column of a projection, which is rebuildable.
- PostgreSQL extensions are created by a migration and only from this list: `btree_gist` (7.3), `pg_trgm` (PRD Stack: Search). Another extension needs a change to this list first.

### 4.3 The runner

- The runner lives in `kernel` and connects as the migration role (5.1). It applies the directory set to the directory database, then the Organisation set to each Organisation database the directory lists, in code order, and stops at the first failure.
- Each file runs in its own transaction, with its record, so a failing file leaves the database as it was before that file. A statement PostgreSQL refuses inside a transaction is not used.
- It records each applied file in `kernel.migration` of that database: file name, SHA-256 checksum, the time and the role that applied it. Before the first file for a database it takes a session-level PostgreSQL advisory lock, and holds it until the last file for that database has run, so two runs never migrate the same database at once.
- After the files, it applies the database-level privileges of 5.2 to that database, as its owner: it revokes `PUBLIC`'s privileges on the database and on schema `public`, and grants the runtime role `CONNECT`, and `USAGE` on `public`, where the extensions of 4.2 live. Then it reads the privileges back and fails if any differs, since a revoke PostgreSQL cannot apply only warns. They are not a migration: `CREATE DATABASE` does not copy a database's privileges or settings, so the runner applies them on every run, idempotently, and the test helper applies the same step to every copy it makes (11.3).
- After the files, and before the database step, it runs the set's `maintenance.sql`, if the set has one, in its own transaction, on every run; it is not recorded, and a failure stops the run.
- It runs as the pre-deploy step of each deploy ([deployment.md](deployment.md) section 4). The setup step of a new Organisation migrates that Organisation's new database with the same runner before it writes the first rows (`PRD-ACS-023`, DEC-101; access-and-approvals 9.11). The setup step is an authorised operator command that creates and migrates the database; ordinary users cannot run it (DEC-112, CH-1). **Design choice**, from the earlier proposal for CH-1: it holds the migration role's credentials for this and is never an API endpoint (access-and-approvals 9.11).

## 5. Database roles

### 5.1 Two roles

| Role | Name | What it is |
| --- | --- | --- |
| Migration role | `aos_migration` | Owns every directory and Organisation database, made with `CREATE DATABASE … OWNER aos_migration`, and every schema, table, function and trigger in them. Has `CREATEDB`, so that the setup step creates an Organisation's database with it (CH-1). Used only by the migration runner, the setup step, the partition maintenance of 3.2 (CH-5), test setup (10.1) and the local seed (11.2); the scheduled partition upkeep runs under its rights only through its one `SECURITY DEFINER` function (12.9). Not a superuser |
| Runtime role | `aos_runtime` | Used by `app` and `worker`. Owns nothing, cannot create or change any object, does not bypass row-level security (`PRD-SEC-005`; [deployment.md](deployment.md) section 4). Not a superuser; no `CREATEDB`, `CREATEROLE` or `BYPASSRLS` |

- Each role has its own password, held in the environment's variables and never in the repository ([deployment.md](deployment.md) section 9).
- The SQL that creates both roles is kept for tests and local use, and a runbook gives the same steps for Railway.
- Tables do not use `FORCE ROW LEVEL SECURITY`, so the migration role, as owner, is not filtered. It is never used by application code.
- Settings of the runtime role, such as its `search_path` (3.2) and the time limits of CH-3, are set on the role, not on a database, so they hold in every database, copies included.
- Time limits (DEC-112, CH-3). For runtime work on synthetic data, locally, in tests and on `dev`, the runtime role starts with `lock_timeout` 1 s and `statement_timeout` 5 s. A command that reaches one rolls back and reports the failure. Both are tuned after measurement. Longer limits for migration and maintenance, and the limits of `kdps-test` and production, are not set here; neither is any server-wide setting.
- A third role, read-only, exists only in isolated test databases with synthetic data (DEC-112, CH-4, harness decision H6). Tests use it for raw invariant queries after reading the read models first. It reads only, is created by test setup, and is never created by the runner, the local seed or the Railway runbook. Its name, its grants, and how it reads rows under row-level security (6.2) and in each database copy (4.3) are written with the stock harness (`S1-F10`; stock-ledger 15.4, approved by the product owner, 6 Oct 2026).

### 5.2 What the runtime role may do

- `CONNECT` on its databases, `USAGE` on each application schema and on `public`. Nothing on `kernel.migration`. `PUBLIC` holds no privilege on an application database, schema, table or function; the privileges PostgreSQL itself gives `PUBLIC` on `pg_catalog` and `information_schema` stay (10.4). A new database gives `PUBLIC` `CONNECT` and `TEMPORARY`, and `USAGE` on schema `public`, until the runner's database step revokes them (4.3).
- On each table, only the privileges its migration grants by name. No default privileges are set, so a new table grants nothing until its migration says so:

| Table class | Runtime privileges |
| --- | --- |
| `append-only` | `SELECT`, `INSERT`; and `UPDATE (id)` when it is `locked`, the guard of 7.1 refusing the update itself |
| `versions` | `SELECT`, `INSERT`, `UPDATE`; the trigger of 7.3 limits what an update may change |
| `projection` and other changeable tables | `SELECT`, `INSERT`, `UPDATE`; `DELETE` only where the table's design allows a delete |

- PostgreSQL takes a row lock, `FOR UPDATE` or `FOR SHARE` alike, only for a role holding `UPDATE` on at least one column of the table. So every `locked` table grants it, and an append-only one grants `UPDATE (id)` only.

- A function runs with its caller's rights. `SECURITY DEFINER` is used only where a design names the function, such as the audit retention function (numbering-and-audit 4.6), the audit sealing and seal check (4.4), the scheduled partition upkeep (4.4; DEC-118) and the stock ledger's "has this book held stock?" (`stock.book_has_held_stock`, stock-ledger 13.7, 14.3; DEC-116); such a function sets its own `search_path` to `pg_catalog, pg_temp` (pg_temp named last, so no temporary object stands in for a catalog one), and names every other schema in its body. `EXECUTE` on every function is revoked from `PUBLIC` and granted to the runtime role only where its code or a policy calls it.
- Tests prove that the runtime role cannot create, change or drop a table, and cannot update or delete a row a guard protects (10.4).

## 6. Row-level security

### 6.1 Which tables

- A `scoped` table holds rows that belong to a place, a legal entity or a brand. It carries those scope facts as columns: the identifiers of the Site, the Store and the business unit as they apply, the legal entity, the brand (access-and-approvals 7.2). A line that can be read on its own carries its document's scope facts too.
- A `self` table holds rows of one person, read through the self-service role (`PRD-ACS-022`). It carries the subject's user identifier.
- An `unscoped` table has no row-level security; Authorise alone guards it (access-and-approvals 7.1). Each area design says which of its tables are scoped; 6.3 classifies the tables that authentication reads.

### 6.2 The policy

- After Authenticate, `kernel` sets the actor at the start of every transaction, reads included, except on the paths of 6.3, with `set_config('aos.actor_id', <id>, true)`: local to the transaction, so a pooled connection never carries an actor into the next one (access-and-approvals 7.2). Nothing ever sets it for the session.
- `access` provides one SQL function for every policy: `access.row_visible(record_type, site_id, store_id, business_unit_id, legal_entity_id, brand_id, subject_id)`. It is `STABLE`, written in SQL, and answers whether one effective grant of the actor for that record type covers the row's facts, or, for a self-service grant, whether the subject is the actor (access-and-approvals 7.2). A policy reaches `access` only through this function; it never reads `access` tables itself.
- The function knows which scope facts each record type declares (access-and-approvals 5.3). A null in a declared fact is Unknown and is covered only by all-members scope in that dimension; a fact the record type does not declare is passed as null and not checked. The facts of `stock.balance` in the example are for the stock design to set.
- Stock rows follow three structural rules that are not Unknown, approved by the product owner, 6 Oct 2026 (stock-ledger SL-25 (b), (c), (e) and 14.3; RR-228): a row at a business unit that belongs to no Store, as `organisation` records, carries no Store and is matched by its Site and unit; a whole-book cost pool, whose `pool_mode` says so, carries no Site, so only all-members place scope sees its rows; the rows of a Site pool carry no Store or unit, so only a place scope that covers the whole Site, by a selected Site or wider, sees them. A reader who sees a pool row still sees its cost and value only with the cost field permission (access-and-approvals 6).
- The function takes one value of each scope fact. A record whose scope holds several values of one fact, such as a document with lines of several brands, or a transfer read from its source and its destination (access-and-approvals 5.3), does not fit it yet. For brands, CH-6 is answered (product owner, 6 Oct 2026, `DEC-117`): a row that can cover goods of several brands stores its brand set on the row, as an array column, and its policy calls a second `access` function that answers true only when the actor's one assignment covers every brand in the set (access-and-approvals 5.3): `access.row_visible_brand_set(record_type, site_id, store_id, business_unit_id, legal_entity_id, brand_ids, subject_id)`, `STABLE`, SQL, `SECURITY INVOKER`, the same as `access.row_visible` with the set `brand_ids uuid[]` in place of the one brand, every dimension checked inside the same effective grant. A null element of the set is a brand that is Unknown, covered only by all-members brand scope; an empty set records no brand, so only the place and the legal entity are checked (migration 0025; S1-F10-T01). The stock ledger's header rows use it (stock-ledger 14.1, SL-25 (d)). A unit anchor carries no brand and is matched by place only: its policy passes the empty set. Any other record whose scope holds several values of one fact, such as a transfer's source and destination, is not created until the rest of CH-6 is settled.
- A command must still respect rows its actor cannot see, such as a hold or a count freeze over goods of a brand outside the actor's scope. Its rechecks under lock read them through one narrowly authorised internal `stock` function (`SECURITY DEFINER`, owned by the migration role, schema-qualified, executable only by the runtime role) that sees every such row at the command's unit and returns only a generic refusal, never the hidden row's details (stock-ledger 14.3; `DEC-117`). As built, `stock.recheck_hidden` (S1-F10-T02; stock-ledger 13.9), asked once per request for count freezes and once for claims. A read that must say when it is partial asks, in the same way, a function that answers only that: `stock.rebuild_partial` for Rebuild and compare (stock-ledger 13.6, 13.9).
- A policy's expression runs with the rights of the role that queries, so the function runs with its caller's rights (`SECURITY INVOKER`). It reads a table, so PostgreSQL does not inline it and runs it for each row; each scoped table's policy is checked with `EXPLAIN` on volume data before the table's first feature is accepted. Every name in it is schema-qualified. The runtime role holds `SELECT` on `access.effective_grant`, an `unscoped` table (6.3), and `EXECUTE` on the function; `PUBLIC` holds neither.
- It reads the actor as `nullif(current_setting('aos.actor_id', true), '')`. A setting that was set earlier in the session reads as an empty string, not as null, after its transaction ends, so the empty string must count as no actor. With no actor, the function answers false and every scoped table shows no rows.
- Beside the actor, `kernel` sets the transaction's business date, `set_config('aos.business_date', <date>, true)`: today under the Organisation's timezone at the command's instant (section 9). The function admits a grant only while the grant's business days hold that date, read as `nullif(current_setting('aos.business_date', true), '')::date`; with no date set, as while no timezone is in force, it admits none. So an assignment's or a role version's start or end takes effect on its day, whether or not the grants rebuild has run (access-and-approvals 7.2; DEC-120, RR-390; migration 0022). The connection clears both settings before it goes back to the pool.
- Every `scoped` or `self` table has one policy for the runtime role, the same predicate for reading and writing:

```sql
alter table stock.balance enable row level security;
create policy row_scope on stock.balance for all to aos_runtime
  using (access.row_visible('stock.balance', site_id, store_id, business_unit_id, null, null, null))
  with check (access.row_visible('stock.balance', site_id, store_id, business_unit_id, null, null, null));
```

- So a command cannot write a row its actor could not read. A table whose design lets an actor write rows for a scope it cannot read names its own write rule in that design; 6.3 names the one this document needs.
- Row-level security is the backstop; the exact check is Authorise, one assignment per action (`PRD-ACS-004` through access-and-approvals 7.2). Restricted columns are protected by masking and encryption, not by these policies (access-and-approvals 6; `PRD-SEC-006`).
- Read models carry the same scope columns and the same policy (access-and-approvals 7.2).

### 6.3 Before an actor exists

- Three paths run with no actor set:
  - authenticating a request or a job step, which reads the session or the service credential and the actor's state to learn who the actor is (access-and-approvals 7.1 step 1);
  - sign-in, with a user's actions on their own credentials and sessions (access-and-approvals 3.1, 3.2);
  - the setup step of a new Organisation, until it acts under its service identity (access-and-approvals 9.11; `PRD-ACS-023`, DEC-101; CH-1).
- Every other query of a request or job runs after the actor is set.
- The first two paths read the directory database's `kernel.directory_entry` first, to find the Organisation's database from the code typed at sign-in or carried in the session cookie (access-and-approvals 3.1, 3.3). It is `unscoped`: it lies outside every Organisation, so no actor's scope can apply to it, and it holds only each Organisation's code and the name of its database (DEC-093). At run time only `kernel` routing reads it, as the runtime role, which holds `SELECT` on it and nothing else. The pre-deploy runner reads it as the migration role to list the Organisations it migrates (4.3); how the setup step reads and registers a code there is access-and-approvals 9.11's (CH-1).
- The tables of `access` these paths and Authorise read are `unscoped`: `app_user`, `password_credential`, `second_factor`, `session`, `device`, `service_identity`, `service_credential`, `role`, `role_permission`, `role_assignment`, `assignment_scope`, `assignment_scope_member`, `approval_limit`, `stand_in_grant` and `effective_grant`, with their versions, and `persona_held`, `role_assignment_withdrawal` with its versions, and the change rows naming the preparers of roles, assignments and withdrawals (access-and-approvals 13.1; `S1-F01-T11`). Only `access` code reads them (`PRD-MOD-002`). Passwords, credentials and session identifiers in them are held only as hashes, and second-factor secrets encrypted (access-and-approvals 6, 13.1). What anyone else sees of them comes through `access`'s interface and its read models, which are scoped.
- The evidence these paths write goes to `audit`: the access record of every sign-in attempt in a known Organisation (access-and-approvals 3.1; `PRD-SEC-007`) and the setup step's audit records. Those tables are scoped for reading (numbering-and-audit 4.5), so they carry two policies instead of the one of 6.2: reading through `access.row_visible`, and inserting admitted for any row (`WITH CHECK (true)`). A refusal there would lose the record of an attempt, and the rows are append-only (7.1). An insert on these paths asks for no row back (`RETURNING`), since reading the row back is refused with no actor. **Design choice.**
- Nothing on these paths sets an actor it has not authenticated.

## 7. Append-only rows and versions

### 7.1 Append-only

- Entries, status records, audit and access records, approval decisions, and the frozen payloads of documents are append-only (domain-model section 1; `PRD-MOD-011`, `PRD-SEC-007`). Each table is marked `append-only` and has two guards:
  1. the runtime role has no `DELETE` on it, and no `UPDATE` except `UPDATE (id)` on a `locked` table, which it needs to lock rows (5.2);
  2. a `BEFORE UPDATE OR DELETE` row trigger and a `BEFORE TRUNCATE` statement trigger call `kernel.refuse_change()`, which raises an error with a SQLSTATE of the class `AO`. The trigger also stops the owner. Taking a row lock fires no trigger.
- A delete a design allows, such as audit retention (numbering-and-audit 4.6), goes through that design's named function, and the trigger admits only it.
- A correction is its own linked record (`PRD-MOD-011`; domain-model section 1). A status that changes is a projection, kept apart from the rows it is built from.

### 7.2 Documents

- A document is a header row with its state, and version rows that hold its payload. A draft version takes changes until it is submitted; each change is also written to an append-only change row naming who made it and when. So the preparers of a version are everyone with a change row on it, including the one who submitted it (access-and-approvals 9.1; GC3-1, DEC-105). From submission the version row is frozen; a later change opens a new version, which needs a new approval unless the change is not material and the decision carries to it (access-and-approvals 9.6; `PRD-ACS-007`, `POL-02.12`). An approval names the version it decided (domain-model section 1).
- After approval the payload is frozen: no new version is accepted except as its design allows. The state is a projection on the header, rebuildable from the document's events.

### 7.3 Effective-dated versions

- A master or setting with versions has a companion table `<table>_version` with `valid_during daterange`, half-open, under business dates (structure-and-masters 2.2; `PRD-MOD-010`). A dated table, such as `role_assignment`, `approval_limit` or `business_unit_mapping` (access-and-approvals 13.1; structure-and-masters 6.1), holds its own `valid_during` on each row and follows the rules of this section as if each row were a version; its register entry is marked `versions` and names the overlap key. `role_assignment` may hold several assignments of one user at once; its overlap key is the actor, the role and the canonical form of the exact scope (access-and-approvals 4.3; DEC-112, CH-7). The form, settled with the migration that creates the table (`S1-F01-T11`), is the column `scope_key`: `own-records` for own-record scope, otherwise `legal-entity=<part>;place=<part>;brand=<part>`, where a part is `all`, `empty`, or `selected:` followed by the members sorted by code unit and joined by commas, a place member written `<type>:<id>` (`site`, `store`, `business-unit`). Two scopes are the same exact scope when their forms are equal. The application writes it with the assignment, the function `access.scope_key_of` makes the same form from the scope rows, and a deferred constraint trigger refuses, at commit, an assignment whose `scope_key` differs from its scope rows. The constraint excludes `(coalesce(app_user_id, service_identity_id), role_id, scope_key, valid_during)` over Approved, not withdrawn rows. **Design choice.** A dated table whose design names no key gets no exclusion constraint until its design names one.
- A version row records its decision: Awaiting approval until it is decided, then approved or Rejected (structure-and-masters 2.3). One more, for a role assignment only: Withdrawn, final, when the user it is for has their first version rejected while it waits, with its withdrawal document naming that decision (access-and-approvals 4.3; DEC-116, DEC-117; `S1-F01-T13`). A version superseded before it was decided keeps Awaiting approval; its approval request says Superseded (access-and-approvals 9.6).
- Approved versions never overlap: an exclusion constraint on the master's identifier, or for a dated table the key its design names (for `approval_limit`, the action and holder; for `business_unit_mapping`, the unit), and `valid_during`, using `btree_gist`, limited by a `WHERE` clause to approved versions that are not withdrawn, whatever their dates: Scheduled, In force and Ended alike. A state that changes with the date alone cannot be the condition of a constraint, and two approved versions that overlap would both be in force on the dates they share (structure-and-masters 2.2).
- The runtime role holds `UPDATE` on the table (5.2), and a trigger allows only four changes: to a version still Awaiting approval; recording its decision, once; recording its withdrawal, once, on an approved version (below); and, on an approved version, moving the end of `valid_during` earlier, to today or later and never to or before its start, either because a new version follows it on its own start date, or because an approved change ends it early, as for a role assignment ended early (access-and-approvals 4.3). It refuses every other change, including any change to an approved version's start or to a Rejected version.
- Where a module freezes a version when it is prepared, as `organisation` does (structure-and-masters 6.1), its trigger admits no change to a version Awaiting approval but recording its decision, once. Recording an approval may give an open-ended version its end in the same change, where an approved version of the same master starts after it: the version approved ends where that one starts, which keeps its own values (structure-and-masters 2.2; product owner, 8 Oct 2026).
- **Withdrawal before the start.** An approved version or dated row that has not started (Scheduled), such as a role assignment, may be withdrawn before its start through a prepared and independently approved change. Decided by the product owner, 6 Oct 2026 (RR-202), who approved the mechanism below and the state name Withdrawn the same day (CH-11):
  - The withdrawal is a document of its own (7.2): a header row in a companion table `<table>_withdrawal` of the same schema, naming the version it withdraws, and version rows holding its reason, frozen at submission. It is approved by an authorised person other than its preparer, as the product owner decided (RR-202), and under every other condition of the approval rule of the change it withdraws; a role-assignment change always needs independent approval (`PRD-ACS-006`; access-and-approvals 4.3, 9.11; structure-and-masters 2.3). The approval binds to the withdrawal's exact version (`PRD-ACS-007`), and the withdrawal is audited like any change.
  - The approved row is never deleted, and its payload, dates and decision never change (`PRD-MOD-011`). The decision's transaction locks the version row as its own record (8.2), rechecks under the lock that it is approved, not withdrawn and starts after today under the Organisation's timezone (section 9), then records the withdrawal on the version row: a column holding the identifier of the withdrawal's header, set once from null, with a foreign key to it. That is the only change the trigger admits to an approved version besides moving its end earlier, of the same kind as recording its decision once; the constraint's `WHERE` clause can see only the row's own columns, so this column is what frees the withdrawn version's dates for a replacement while the constraint stays sound. A version that has started cannot be withdrawn; it is ended early instead (above).
  - A withdrawn version is never in effect: no transaction uses it, reading a setting or a master on any date never returns it, and for `role_assignment` no effective grant comes from it (access-and-approvals 7.2). Its history stays readable with its withdrawal. It shows the state Withdrawn ([design-language.md](../ui/design-language.md) section 7; CH-11).
  - A withdrawal moves no other version's dates. An earlier version that was ended for the withdrawn one stays ended; a gap is filled by a new version. Where a master must always have a version in force (structure-and-masters 2.2), the withdrawal is refused unless the same approved change brings a replacement from the same start date.
- A version never starts on a past date (GC2-7, DEC-105). The command checks it against today under the Organisation's timezone (section 9); a `CHECK` constraint cannot see today.
- A transaction row stores the identifier of each version it used (`PRD-MOD-010`).

## 8. Commands, transactions and locks

### 8.1 The command runner

- Every state change is a command run by `kernel`'s command runner. One command is one database transaction; every module the command calls joins it and never opens or commits its own (`PRD-MOD-006`, `PRD-INT-004`; module-map section 3, rule 3).
- The runner follows module-map 6.1: Organisation and actor, the idempotency key, availability and authorisation, slow work before any lock, locks, rechecks under the locks, writes, commit, then the outbox. The idempotency key's form is part B; its row is kept in the command's transaction (`PRD-INT-002`; stock-ledger 10.1).
- Each interface operation that reads or writes takes the command's transaction context as its first argument. There is no hidden ambient transaction.
- Isolation is `READ COMMITTED`, with explicit row locks and the rechecks of stock-ledger 10.4. Under it a read is not stable: a row read without a lock can change, and the change commit, before the command commits. So every fact a command rechecks under the locks is read after the locks are held, from a row the command has locked; from rows that change only under an exclusive lock of such a row, such as its versions or an assignment's scope rows; or from rows that never change once written, such as a frozen version's change rows (7.2, 8.2). A statement run after a lock is granted sees every change committed before it. A read-only query runs in a `READ ONLY` transaction, with the actor set as for a command.
- With the lock order of 8.2, and exclusive locks that leave foreign-key checks free, a deadlock means one of these rules was broken. The command fails, the failure is logged as a defect, and a test is written that reproduces it. The runner does not retry it.
- An exception that must survive a rollback is raised in its own transaction after the rollback (module-map 6.3; SL-23, DEC-105).

### 8.2 Lock order

- Locks are taken only through `kernel`'s lock helper, once per step of stock-ledger 10.3, with every row of that step from every table the step covers. The helper takes them in ascending identifier order across the whole step: each run of consecutive rows from one table in one `SELECT … ORDER BY id FOR NO KEY UPDATE`, or `FOR SHARE` where the step says so: receipt origins only read (step 2), unit anchors except to start or end a count freeze (step 3), and the financial period row (step 7) (stock-ledger 10.3 and 14.3; SL-24, RR-227; MM-6, DEC-105). PostgreSQL locks such rows after sorting them.
- **Foreign keys.** Inserting a row that references another takes `FOR KEY SHARE` on the row it references, outside the helper. That lock waits for `FOR UPDATE` but not for `FOR NO KEY UPDATE` or `FOR SHARE`, so the helper never takes `FOR UPDATE`. This is safe because no command changes a column of a unique index, such as an identifier or a code (structure-and-masters 2.1), or deletes a row another row references; either would take `FOR UPDATE` itself.
- **Rows of other modules.** A step can hold rows of several modules, such as a document and the `access` approval rows of step 1. A module whose rows another command locks offers them through its interface as lock targets, and the command passes all the targets of a step to the helper in one call. The helper refuses a call for a step no higher than one already called in the transaction, so a step's rows are never taken in two calls, and two commands can never take them in different orders (`PRD-INT-003`).
- **Authority first.** Step 0 of stock-ledger 10.3 locks the rows the command's authority rests on: the acting user or service identity, the role assignment Authorise returned, the role that assignment grants (DEC-118, RR-360), the approval limits and the stand-in grant relied on, including the limit an approval decision used. A command that relies on them takes them in shared mode, so such commands never wait for each other. A command that changes one of them, such as disabling a user, ending an assignment, a limit or a stand-in grant, making a role version take effect, or revoking a service identity, takes it in exclusive mode at the same step. Under them the command rechecks that the user is still Active, or the service identity still enabled, as well as the assignment, the role's version in force, scope and limits (access-and-approvals 7.1 step 4; stock-ledger 10.4). So a change of authority waits for the commands already relying on it, and a command that locks after it commits sees it: a user who is disabled posts nothing after the disabling commits (access-and-approvals 2.1; `PRD-INT-003`). The lock target is the identity row, not its versions. A command that needs one row in both modes takes it exclusively.
- **Missing rows.** Step 3 first creates the unit anchor and balance rows that do not exist yet, and step 6 the cost pool and transit value rows, empty, with `INSERT … ON CONFLICT DO NOTHING` in ascending key order, by code unit and never by a locale's collation, then makes its lock call. Creating a row locks it. A new pool takes its formula, pool mode and cost-setting version from the cost setting the command read before any lock (stock-ledger 14.2). These empty rows are the only write before every lock is held; nothing that records the command's effects is written until then (stock-ledger 10.3; amended by the product owner, 6 Oct 2026, RR-227).
- Every table the helper locks is marked `locked` in its register, so the runtime role holds the `UPDATE` privilege every row lock needs (5.2).
- **Number series.** A command locks every series it will draw numbers from, its own document series and the journal series of each book it posts to, in one call as step 8, before its first write. `numbering` offers the series rows as lock targets, and Allocate draws only from a series the transaction holds (numbering-and-audit 3.2; books-and-posting 5.4).
- A command that changes no stock or money locks its authority rows as step 0, its own record rows as step 1, and any number series as step 8. A row that stock-ledger 10.3 already places keeps its step: a financial period row is step 7 and a series row step 8, even when it is the command's own record, as for locking a period (books-and-posting 4.5).
- A later module's rows take the step its design names; stock-ledger 10.3 is updated then (module-map 6.1).

### 8.3 No outside call inside a transaction

- Nothing inside a transaction calls an outside system: file storage, messaging, GST, bank, Tally, AI or any other network service (`PRD-INT-006`). Such work runs before the transaction, as a stored file referenced by its identifier is, or after the commit through the outbox.
- The runner marks the work it runs as inside a transaction, and every adapter for an outside system refuses to run while that mark is set. A test proves the refusal.

## 9. Time

| Time | Column | Set by |
| --- | --- | --- |
| Event time | `occurred_at timestamptz` | The command, from when the thing happened: the device's time for an offline bill, the server's time for an online action |
| Recording time | `recorded_at timestamptz` | The database, as the transaction's time, so every row of one command has the same one |
| Business date | `business_date date` | The command, under the Organisation's timezone (`PRD-MOD-009`) |

- The server and the database run in UTC. A business date is never taken from the server's or the database's time zone.
- The Organisation's timezone is an Organisation setting in `configuration` (domain-model 3.6), with no default. An operation that needs a business date is unavailable until it is set (`PRD-SEC-017`). **As built** (`S1-F01-T10`; RR-231): its versions are kept in `configuration.organisation_timezone_version`, dated by instants (`tstzrange`) instead of business dates, since a business date is worked out under the timezone and so cannot date it; otherwise they follow 7.3. The setup step writes the first version, in force from the step's start (access-and-approvals 9.11). `configuration` provides the kernel's timezone contract from a global module the app and the worker import; without it the kernel's source answers not set. **Design choice.** User versions in `access` are dated by instants the same way, so a disabling takes effect at its decision, not the next business day (`PRD-SEC-019`; DEC-118; access-and-approvals 9.5). So are the versions of the settings of `access`, so a change to the throttling, the password rules or the session limits may take effect at its decision (DEC-118; access-and-approvals 3.3; `S1-F01-T25`).
- Screens show event and recording times in the Organisation's timezone, whatever the device's, and every business date is the Organisation's (`PRD-MOD-017`; product owner, 7 Oct 2026, DEC-118, RR-310). Timestamps are stored in UTC (`timestamptz`); the session read carries the Organisation's timezone for the web app to format with `Intl`.
- Code reads the time only through `kernel`'s clock, never `new Date()` or `Date.now()` in a command or in `domain/`. Tests set the clock.
- Dates under a timezone are worked out with the built-in `Intl` API. No date library is added.

## 10. Tests

### 10.1 Kinds of test

| Kind | Tool | Where | What it proves |
| --- | --- | --- | --- |
| Unit | Vitest | `*.test.ts` | Pure rules: `domain/` and packages. No database, network or clock |
| Integration | Vitest and Testcontainers | `*.int.test.ts` | Commands, constraints, triggers, policies and read models on real PostgreSQL |
| Concurrency | Vitest and Testcontainers | `*.int.test.ts` | Two or more transactions on separate connections (10.3) |
| Golden cases | Vitest; Playwright for the counter run | Case files; the counter run in `apps/counter/e2e/` | Shared calculations on server and counter (shared-calculations 12.1, 12.2) and the stock-and-posting stories |
| Browser journey | Playwright | `apps/web/e2e/`; the counter's in `apps/counter/e2e/` (product owner, 6 Oct 2026) | What one persona can and cannot see and do on the screens a change touches (`PRD-SEC-016`, `PRD-ACP-018`) |

- **Integration tests use the runtime role.** A test connects as `aos_runtime` and sets an actor exactly as the application does. Only test setup uses the migration role or the container's superuser. Raw invariant queries may also use the read-only test role of 5.1 (CH-4).
- **Journeys per persona.** A feature that adds or changes a screen adds one journey per persona that uses it (P-OWN … P-AUD, [personas.md](../access/personas.md)). The journey signs in as a synthetic user holding a synthetic role assignment for that persona, and checks both what it may do and what it is refused, with the refusal's reason.
- Tests are independent of each other and of their order, and test files run in parallel (11.3). The one exception is the pair of test files that proves two files at once never see each other's rows: each needs the other running at the same time (11.3). A test that passes only sometimes is a defect; the test runner never retries a failed test.

### 10.2 Naming and citing

- A test that proves a rule names its ID at the start of its title: `it('PRD-SEC-005 shows no scoped row when no actor is set', …)`. A test from a design's test table names that test too: `access-and-approvals 15 test 11`. So a search for an ID finds its tests.
- `describe` names the operation or the rule; `it` says the expected behaviour in plain words.

### 10.3 Concurrency tests

- Each transaction has its own connection. The test drives the order step by step: the first transaction takes its lock; the second starts and the test waits until PostgreSQL shows it waiting for that lock; then the first commits or rolls back. A test never relies on a sleep to order transactions.
- The cases are those of the area designs, such as stock-ledger 11.9.

### 10.4 Database checks run as tests

After migrating an Organisation database and a directory database, one test reads the catalogue and the table registers and fails when:

- a table is missing from its set's register, or the register lists a table the database does not have (3.2). A third-party schema, such as `pgboss`, is checked as one entry instead: the runtime role holds exactly the privileges its entry lists, `PUBLIC` holds none, and the bullets below on classes and 5.2 do not apply to its tables;
- a `scoped` or `self` table has row-level security off or lacks its policy for the runtime role (6.2);
- an `append-only` table lacks its triggers, or the runtime role holds `DELETE`, a table-wide `UPDATE` or a column `UPDATE` other than on `id` on it (7.1);
- a `locked` table grants the runtime role no `UPDATE` on any column (5.2);
- a `versions` table lacks its exclusion constraint, except a dated table whose design names no overlap key yet (7.3, CH-7);
- the runtime role owns an object, or holds a privilege beyond what 5.2 gives its register class and the database step of 4.3 gives it;
- `PUBLIC` holds any privilege on the database or on an application schema, table or function (5.2). The privileges PostgreSQL itself gives `PUBLIC` on `pg_catalog` and `information_schema` are not counted;
- a Drizzle definition differs from its table (3.4);
- a schema named in a test-only migration set (11.4) exists outside a test database.

### 10.5 What runs on every change

- Every push and pull request runs, through CI: lint, typecheck, the module check, unit tests, integration tests, the link check and the format check; then the golden cases and browser journeys once they exist (`PRD-SEC-016`). Nothing is skipped because of which paths a change touched.
- The pre-commit hook runs what `AGENTS.md` says it runs. A change is merged only with every check green.

### 10.6 Dependencies

- A dependency is added only when it implements a row of the PRD Stack, and its pull request names that row (`AGENTS.md`, "Stack"). Anything else needs a PRD change first.
- The QR code library of the PRD Stack's Authentication row (DEC-118) is the one dependency for the enrolment QR code: maintained, pinned by the lockfile, run only in the browser, and making no network call. **As built** (`S1-F01-T23`): `qrcode.react` (ISC licence, no dependencies), in `apps/web` only; it draws the code as inline SVG from the string it is given. Font files are committed, not installed (design-language 3).
- File storage (PRD Stack, Files: S3-compatible storage; `S1-F06-T05`): `@aws-sdk/client-s3` pinned to an exact version (3.1129.0, a month old when chosen), imported only by the file-store adapter, and only its put and get commands. The tests run MinIO through `@testcontainers/minio`; MinIO no longer publishes its community image to Docker Hub or Quay, so the test image is Chainguard's build of MinIO pinned by digest (`apps/server/test/support/minio.ts`).

## 11. Synthetic data and fixtures

### 11.2 Fixtures

- Fixtures live only in test folders and in the local seed command: `apps/server/test/fixtures/` (values and labels), `apps/server/test/support/` (helpers) and `apps/server/test/seed/` (the seed). Code under `src/` never imports them: lint rules refuse an import, static or dynamic, of a `test`, `e2e`, `fixtures` or `seed` folder from `apps/*/src` or `packages/*/src`.
- Every database test has two synthetic Organisations, each with its own database, so every test can show that one cannot see the other (`PRD-ACS-020`; [deployment.md](deployment.md) section 4). One helper makes them for a test file, beside a directory database, and drops all three at its end. The tests of the runner and of the seed start from empty databases instead, because migrating one is what they test.
- A fixture is built through the real interfaces once they exist, so it obeys the same rules as a user: the setup step for an Organisation (`PRD-ACS-023`), the real commands for its records. Until an interface exists, a fixture writes the fewest rows it needs directly, and is moved onto the interface when it arrives. For the two Organisations that is no row until Organisation routing adds the directory table, then their directory rows, until the setup step replaces them.

### 11.3 Speed and isolation

- A test run starts one PostgreSQL container and migrates a template database of each kind once. Each test file gets its own copies, made with `CREATE DATABASE … TEMPLATE` while no session is connected to the template, and drops them at its end. So two test files running at once never see each other's rows.
- Once migrated, each template is closed to connections, so no test can change it and no session can block a copy. Each copy has a unique name starting `syn_`.
- A copy does not inherit its template's database-level privileges or settings. Before any test connects to a copy as the runtime role, the helper applies the runner's database privilege step to it (4.3).
- Two test files prove the isolation: each writes rows in its own copies, waits until the other has written too, then reads back only its own rows, and neither drops its copies before the other has read. So integration tests run at least two files at once; a file whose partner's probe failed stops at once.

## 12. Part B: API and runtime

- Every technical choice this part marks **Proposed** was approved with it and reads as a **Design choice**. A rule that an ID or another design sets keeps that source beside it.
- It fixes how code does things. It sets no KDPS value and settles no business question. Each value it needs that KDPS or the product owner owns is **OPEN** in section 13, with its owner and what it blocks.

### 12.1 Routes and commands

- **One API.** REST/JSON under `/api`, served by `app` from the one origin of [deployment.md](deployment.md) section 3, with the session cookie: no second origin and no CORS (PRD Stack: API; DEC-093). After `/api`, a route's path names the unit that owns it, such as `/api/access/…` or `/api/merchandise/catalogue/…`; a `kernel` route, such as `/api/health`, names none. **Proposed.**
- **Controllers.** A controller lives in its unit's `http/` folder (section 2) and calls only its own unit's commands and queries, which reach other modules through their interfaces (`PRD-MOD-002`). A controller holds no rule of its own.
- **Reads** are `GET`. A read never changes a record and runs in a `READ ONLY` transaction with the actor set (8.1). A list is paged by a cursor, never by an offset; the largest page is a technical cap the builders set and document. A read of a read model returns its as-of time with the rows (`PRD-MOD-003`, `PRD-PRF-004`). Showing an encrypted field unmasked, and any export that includes a restricted field, are commands, not reads: each writes an access record (numbering-and-audit 5.1; `PRD-SEC-007`), and showing or exporting an encrypted field also asks for a fresh authenticator code (access-and-approvals 3.3). **Proposed.**
- **Commands** are `POST`. A command route runs exactly one command of 8.1, so one request has one outcome in one transaction (`PRD-MOD-006`). Its path names the record and the verb: `POST /api/access/role-assignments` makes a draft, and `POST /api/access/role-assignments/{id}/submit` submits it. No route uses `PUT`, `PATCH` or `DELETE`: an edit writes a change row or a new version, and no record is deleted (7.1, 7.2; `PRD-MOD-011`). **Proposed.**
- **Bulk approval** is the one route that runs several commands: one per item, each in its own transaction with its own rechecks (access-and-approvals 9.9). Each item runs under the request's idempotency key with the item's identifier added to its scope (12.4), and the answer gives each item's outcome.
- **Files.** A file is uploaded by its own route, which stores it after the intake checks of imports-and-opening-data 9.3 and before any command. A command names the stored file by its identifier (8.3). As built (`S1-F06-T05`): the route table carries JSON only, so the file travels as base64 in the body, and a command route may declare `bodyLimitBytes`, the most its body may hold, which `configureApp` applies to that path alone for a request whose cookie names an open session, checked by a read-only probe before the body is read (every other request keeps the ordinary body limit). The store-file route runs the intake checks and writes the object before the command that records it; the idempotency key covers the request as sent.
- **Access on every route.** Each route declares its access in the route table (12.2): `public` (sign-in and the health check only); `own` (a signed-in user's own credentials and sessions, which need no role assignment: access-and-approvals 3.2); or the action and record type that Authorise checks. A `public` route needs no session; an `own` route passes Authenticate only; every other route passes Authenticate, Available and Authorise (access-and-approvals 7.1; `PRD-INT-001`, `PRD-SEC-005`). A unit test fails on a route that declares nothing. The setup step is never a route (4.3, CH-1). **Proposed.**
- **Values on the wire.** Field names are camelCase. An INR amount is integer paise in a JSON number, which the schema refuses outside the safe integer range; a rate or a quantity with a fraction is a decimal string; Unknown is the stated `{ "kind": "unknown" }` shape of `packages/schemas`, never null and never zero (3.3; `PRD-MOD-014`, `PRD-MOD-015`). An event or recording time is an ISO 8601 timestamp in UTC; a business date is `YYYY-MM-DD` (section 9). **Proposed.**
- **Writes from another site.** A command requires the `Idempotency-Key` header (12.4), which a page on another site cannot send without a CORS preflight that the server never grants, and its `Origin` header must be the app's own origin. With the `SameSite=Lax` cookie of [deployment.md](deployment.md) section 3, another site cannot write under a user's session. **Proposed.** Built in `S1-F01-T08` (RR-245): every command, sign-in included, whose `Origin` is not exactly the origin the environment states in `AOS_PUBLIC_ORIGIN` is refused `invalid` with `kernel.cross-site-request` before anything else runs; behind Railway's proxy the server cannot see the origin the browser used, so each environment states it ([deployment.md](deployment.md) section 3).
- **No caching.** Every `/api` answer carries `Cache-Control: no-store`, so no browser or proxy cache keeps API data (`PRD-SEC-006`). The web app's query cache lives in memory only and is cleared at sign-out and when the session ends; input kept across a lock follows access-and-approvals 3.3. **Proposed.**
- **Compatible changes.** Paths carry no API version while the web app, the counter and the server deploy together ([deployment.md](deployment.md) section 3). A change stays compatible with the clients running, as a migration does (4.2): add first; remove or rename in a later deploy. The counter's offline sync gets its own versioned contract in the offline counter design (GC-8). **Proposed.**

### 12.2 Schemas, OpenAPI and the typed client

- **One route table.** `packages/schemas` holds a route table. For each route it gives the method and path; the Zod schemas of its path parameters, query, body and success answer; its access (12.1); whether it is a command; and the refusal codes it can answer (12.3). The server, the web app and the OpenAPI document are all made from it, so they cannot drift apart (PRD Stack: API). **Proposed.**
- **Every input parsed.** The server parses the path parameters, query and body of every request with the route's schemas before the command runs; nothing unparsed reaches a command. Objects are strict, so an unknown field is refused as `invalid` (12.3). **Proposed.**
- **Every answer checked.** The server encodes each success answer through the route's schema. An answer that does not match is a defect: the request fails (`failed`, 12.3), and the log names the route and the path in the schema, never the values (12.11). So a field the schema does not name is never sent, which keeps a restricted field out of an answer that has not declared it (`PRD-SEC-006`). **Proposed.**
- **No defaults in schemas.** No schema in `packages/schemas` supplies a value through `.default()`, `.catch()` or a transform that makes one up; a lint rule refuses them there (`AGENTS.md`, "Never invent a value"; 12.14). **Proposed.**
- **OpenAPI.** A build step generates the OpenAPI document from the route table with Zod's own JSON Schema output, so no generator library is added (10.6). The document is committed as `packages/schemas/openapi.json`, regenerated with `pnpm --filter @apparel-os/schemas generate:openapi`, and a unit test, which CI runs, fails when it differs from a fresh generation, so every API change shows in review (`PRD-SEC-015`, `PRD-SEC-016`). Each route lists the error envelope (12.3) under each status it can answer, with that status's refusal codes in `x-error-codes`: its own, and the shared ones its kind brings (every route: `kernel.invalid-request`, `kernel.timed-out`, `kernel.failed`; every keyed command adds the key codes of 12.4, and those of 12.5 and 12.6 where they apply). Its access (12.1) is in `x-access`. **Proposed.**
- **Secret fields in OpenAPI.** A field made by `secretString()` is a string with `format: password` and `writeOnly: true`; the generator finds such fields through `secretRegistry`. A secret shown once is described as 12.6 says (`PRD-SEC-014`). **Proposed.**
- **The typed client.** A small client over `fetch` in `packages/schemas`, generic over the route table, gives the web app and the counter typed calls. It sets the idempotency key and the version token where a route needs them (12.4, 12.7), and parses success answers with the route's schemas and errors with the envelope's. No client generator is added. **Proposed.** The web app compiles against it (`S1-F01-T05`).
- **Events and jobs.** The payload schemas of outbox events and jobs belong to the unit that publishes them and are exported from its `index.ts` (section 2). Only the live-update message (12.12) is in `packages/schemas`, since the browser reads it. **Proposed.**
- **The `S1-F01-T01` sketch** fits these rules: strict objects, `secretString()` and no defaults. It gains the route table and the envelope; the values of `decisionRefusalSchema` become reasons of `access` codes (12.3); `enrolmentStartResponseSchema` changes as 12.6 says.

### 12.3 The error envelope

Every answer that is not a success has one shape, `errorEnvelopeSchema` in `packages/schemas`. **Proposed.**

```json
{
  "error": {
    "kind": "not-authorised",
    "code": "access.scope-not-covered",
    "missing": [{ "kind": "scope", "dimension": "place", "id": "<identifier>" }],
    "next": "<next-action code>",
    "reference": "<correlation identifier>"
  }
}
```

| Kind | HTTP status | When | Kept under the idempotency key (12.4) |
| --- | --- | --- | --- |
| `invalid` | 400 | The path parameters, query or body fail the route's schema, or a required header is missing or malformed | No |
| `not-signed-in` | 401 | No session in force, or the session is locked (access-and-approvals 3.3) | No |
| `unavailable` | 403 | Available refuses: the capability, the policy, the configured values or the activity (access-and-approvals 7.1 step 2; `PRD-SEC-017`) | Yes |
| `not-authorised` | 403 | Authorise refuses, or a protected action lacks a fresh authenticator code (access-and-approvals 7.1 step 3 and 3.3) | Yes, except a wrong or stale code (12.5) |
| `not-found` | 404 | No record the actor may view has that identifier | Yes |
| `refused` | 422 | A rule of the operation refuses: what the area design lists under "Refuses when", or a state that no longer allows it | Yes, except a refusal caused by a secret (12.5) |
| `conflict` | 409 | The version token is stale (12.7); the key was used with other content, or the first request under it is still running (12.4); a replay whose secret cannot be compared (12.5) or whose first answer showed a secret or an unmasked restricted value (12.6; DEC-113, DEC-114) | A stale version: yes. A key conflict: no |
| `timed-out` | 503 | A time limit of 5.1 (CH-3) was reached and the command rolled back, so the same key may be sent again | No |
| `failed` | 500 | A defect or an unexpected error. Nothing is said of its cause. Also `kernel.outcome-unknown`: whether the transaction committed is not known, so the same key must be sent again (12.4) | No |

- **Fields.** `kind`, `code` and `reference` are always present; `missing` and `next` where the refusal has them; `issues` only on `invalid` (below). No other field is ever sent. A kept refusal answered again under its key carries the header `Idempotent-Replayed: true`, as a replayed success does (12.4). **Proposed**, settled while building `S1-F01-T04`.
- **Codes.** A code is `<unit>.<reason>`, the reason in lower-case words joined by hyphens, such as `access.self-preparation`. Each unit declares its codes in `packages/schemas`, each with its one kind, and the route table lists the codes each route can answer (12.2). `kernel` declares the shared ones: `kernel.invalid-request` (`invalid`: the path parameters, query or body fail the route's schema, or the body is not JSON), `kernel.not-found` (`not-found`: no route has that method and path), `kernel.idempotency-key-required`, `kernel.idempotency-key-reused`, `kernel.request-in-progress`, `kernel.stale-version`, `kernel.timed-out`, `kernel.failed`, `kernel.outcome-unknown` (12.4), and those of 12.5 and 12.6. **Proposed.**
- **What is missing** (`PRD-UXP-003`; access-and-approvals 7.1). An `unavailable` or `not-authorised` answer lists in `missing` what blocks the action, as identifiers and codes only: the action and the record type; the scope dimension, and the place, legal entity or brand not covered; the field class; the assignment that nearly covers it, where one does; the policy by number and what it lacks, its signature or its validated values; the setting not set; the capability that is off; the activity not granted (module-map 4.4; design-language 10.17). `next` names the next action as a code. The screen turns both into text from the message catalogue (12.13). **Proposed.**
- **Nothing that leaks.** An envelope never holds a restricted value, a secret, an input value or a database message (`PRD-SEC-006`, `PRD-SEC-014`). A `missing` item names only records the actor may view. A record the actor may not view is answered `not-found`, never `not-authorised`, so a refusal never confirms that a hidden record exists (`PRD-SEC-005`). An `invalid` answer gives the paths and the issue codes that failed, never the input, in `issues`: each `{ "path": ["body", "lines", 0, "sku"], "code": "too_small" }`, its path starting with `params`, `query` or `body`. **Proposed.**
- **One refusal where a design asks for it.** Where a design requires one refusal that does not say which part was wrong, as sign-in does (access-and-approvals 3.1), the answer has one code and no `missing`: `access.sign-in-refused`, kind `not-signed-in`. A slowed sign-in has its own code, `access.sign-in-slowed`, also with no `missing`; it is the same for a login that exists and one that does not (DEC-116), so it shows nothing of which logins exist (`S1-F01-T08`). This part sets no throttling value.
- **Reference.** `reference` is the request's correlation identifier (12.11). The error state shows a reference in design-language's display form (design-language 10.13), derived from this identifier so that it still finds the request's log lines: `ERR-` and the identifier's last six hexadecimal digits in capitals, which are random in a UUIDv7, so an operator searches the logs for an identifier ending in them, ignoring case; the element keeps the full identifier for copying. **Design choice**, settled with `S1-F01-T14`.
- **Database errors.** A command checks its rules before it writes, so a database constraint is a backstop. A violation the unit maps to one of its codes answers that code; any other database error is `failed`, logged with its SQLSTATE and constraint name only (12.11). An error of the `AO` class from `kernel.refuse_change()` (7.1) is always a defect. **Proposed.**
- **The `S1-F01-T01` sketch.** The values of `decisionRefusalSchema` become the reasons of `access` codes, each declared with its kind; for example, `access.no-reason-list-in-force` is `unavailable`. Done in `S1-F01-T13`: `decisionRefusalCodes` lists them; a wrong or used code on a decision is `access.authenticator-code-refused`, as on every protected action (RR-246).

### 12.4 The idempotency key

- **The header.** Every command carries `Idempotency-Key`: a UUIDv7 the client makes for one submission (`PRD-INT-002`; stock-ledger 10.1). The client sends the same key again after a lost answer, `timed-out`, `kernel.outcome-unknown` or `kernel.request-in-progress`. Once it has a definitive answer, a success or a kept refusal, a new submission gets a new key. A command without the header, or with a value that is not a UUID, is `invalid` with `kernel.idempotency-key-required` (`S1-F01-T05`). **Proposed.**
- **Sign-in is the one write without a key**, an exception to the rule that every write carries one (stock-ledger 10.1). Each attempt must be recorded as its own attempt, with its own access record (access-and-approvals 3.1; `PRD-SEC-007`), so an earlier answer must never stand in for it; and a replayed answer could not carry the session, since the database keeps only the identifier's hash (access-and-approvals 3.3). A repeated sign-in makes one more session and one more access record, both true records of what happened. Reads carry no key. **Proposed.**
- **Scope.** A key is unique within the Organisation's database for one actor and one operation, so it belongs to the Organisation, the actor, the operation and the key together, across that actor's sessions: a new session of the same actor recovers it, and no other actor or Organisation can reach it: the actor is the user or the service identity that sends it, and the operation is the command's name (stock-ledger 10.1). An item of bulk approval adds its identifier (12.1). A job step uses the job's identity as its key and the step as its operation; an outbox consumer uses the event's identity and its own name (12.8). An offline bill keeps the key of stock-ledger 10.1 under its device, through the offline counter design (GC-8), and an imported document keeps its source identity (imports-and-opening-data 7.1). **Proposed.**
- **What is hashed.** SHA-256 of a canonical form of: the operation, the path parameters as sent, and the body as the route's schema parsed it, which carries the version token (12.7), with every secret field left out and the names of the secret fields present added (12.5; access-and-approvals 3.2). The canonical form is JSON with sorted keys and no insignificant space. It has a version, kept beside the hash; a key whose row was made under another version is answered `conflict` saying so, and the two hashes are never compared, as for the setup step (access-and-approvals 9.11). **Proposed.**
- **Storage.** Three append-only tables of `kernel` (7.1), in each Organisation database. They are `unscoped`, because the helper must find a key at step 2 of module-map 6.1, before Authorise and before the record's scope is known. Kept answers hold no restricted value (below); a kept refused request is protected by encryption and by the read rule below, not by row-level security. Only the helper reads them, except kept requests in the operations view (below) (`PRD-MOD-002`):
  - `kernel.idempotency_key`: the actor, the operation, the key, the hash, the form's version, the names of the secret fields present (12.5) and the correlation identifier; unique on actor, operation and key;
  - `kernel.idempotency_result`: for one key row, the outcome's kind (a success, or a kept refusal of 12.3, of which the one kept `conflict` is a stale version), the answer as sent (except an answer that showed a secret or an unmasked restricted value, of which only the fact is kept, 12.6), and the identifiers of any credential the command wrote, which are never sent (12.5);
  - `kernel.idempotency_conflict`: a request refused for changed content (below).

  A command's success answer holds only identifiers, versions, states and version tokens, never a restricted value, so a kept answer holds none; the client reads the record again through its read route, which applies field permissions (`PRD-SEC-006`). A version token (12.7) names a record version and grants nothing; no kept answer ever holds a session identifier, a credential or any other authentication or bearer token, and no other answer holds one except the shown-once answers of 12.6, which are never kept. A command that shows a restricted value unmasked (12.1) keeps only the fact that a value was shown, and its identical replay is refused with `kernel.answer-not-repeatable` (DEC-114), so each showing is a new request with its own fresh code, authorisation and access record (`PRD-SEC-001`, `PRD-SEC-007`).
- **In the command's transaction.** At step 2 of module-map 6.1 the helper inserts the key row and sets a savepoint. On success, the result row is written with the command's other writes, and all commit together (`PRD-INT-004`). On a refusal the command decides (the kinds kept in 12.3), the command rolls back to the savepoint, which also releases every lock taken after it, writes the refusal as the result, and commits; so an identical replay gets the same refusal. On `invalid`, `timed-out` or `failed` other than `kernel.outcome-unknown`, the whole transaction rolls back and the key stays unused. **Proposed.**
- **An uncertain commit keeps the key.** A key is free again only when the rollback of its transaction is confirmed. When the server cannot tell whether the transaction committed, because the connection was lost or a time limit was reached while `COMMIT` was in flight, the answer is `failed` with `kernel.outcome-unknown`, never `timed-out` or anything else that would let the client treat the operation as not done. The client sends the same key again: if the transaction committed, its key row is there and the request is a replay; if it did not, the request runs once. So no uncertain outcome can lead to a second effect (`PRD-INT-002`, `PRD-INT-004`). Tests force a lost connection and a timeout during `COMMIT`, for a transaction that committed and for one that did not, and show one effect in each case.
- **Replay.** Same key and same hash: the kept answer, with the header `Idempotent-Replayed: true`, and no second effect, audit record or outbox row (`PRD-INT-002`), except the replays refused under 12.5 (a secret that cannot be compared) and 12.6 (an answer that showed a secret, DEC-113, or a restricted value unmasked, DEC-114). The helper recognises the key at step 2 of module-map 6.1, before the command's own checks, but answers a replay only after the access checks of access-and-approvals 7.1 that its route (12.1) or job kind requires have passed for this request: the actor is authenticated, by its session or a service identity's credential, and, for a route or job step that declares an action, the actor is still authorised, now, for that action on the records its kept answer names, within scope; an `own` route needs Authenticate only (`PRD-INT-001`, `PRD-SEC-005`; access-and-approvals 7.1). A replay that fails them is answered as any request that fails them would be (`not-signed-in`, `not-authorised`, or `not-found` for a record the actor may not view, 12.3), and the command is never run again. Authorising a replay only reads; it reruns no availability check, validation, lock or write.
- **Changed content.** Same key, another hash: `conflict` with `kernel.idempotency-key-reused`. In a transaction of its own, the helper keeps the refused request for investigation (`PRD-INT-002`; stock-ledger 10.1): the actor, the operation, the key, both hashes, the correlation identifier, and the request's canonical form with its field values, except secrets: passwords, temporary passwords and authenticator codes never enter it in any form (12.5). The value of every restricted field class (access-and-approvals 6), encrypted class or not, is kept only encrypted under the Organisation's key, and nothing else of the request is kept beyond what investigating the change needs. A kept request is shown in the operations view (module-map 4.1) only to a reader whose role assignment grants that view and whose scope covers the records the request names, checked through their owners' interfaces; within it, a value of any restricted field class is shown only when that same assignment grants the field class, and is otherwise masked (access-and-approvals 6; `PRD-SEC-005`, `PRD-SEC-006`, `PRD-SEC-010`). **Proposed.**
- **Two at once.** The key row's unique index makes a second request with the same key wait at its insert until the first commits or rolls back; it then replays, conflicts, or, after a rollback, runs itself. The wait comes before the command takes any lock, and a command holds one key, so it adds no deadlock (8.2; `PRD-INT-003`). A wait that reaches the lock limit of 5.1 is answered `conflict` with `kernel.request-in-progress`, and the client sends the same key again later. **Proposed.**
- **Retention.** How long these rows are kept is OPEN (CH-9). Until it is set, nothing is deleted from these tables: a temporary safeguard for development and test, not a retention policy. A key is answered for as long as its row exists.

**Replay at a glance.** Every row is answered only after the access checks above pass for the replaying request. No row holds a secret, and no row or log holds a restricted value in plaintext (12.11).

| Case | What is kept | What an identical replay gets | Lost-answer recovery |
| --- | --- | --- | --- |
| A success | The key row (actor, operation, key, hash of the canonical form without secret fields, its version, correlation identifier) and the answer: identifiers, versions, states and version tokens only | The kept answer, marked `Idempotent-Replayed: true`; no second effect | Send the same key and content again |
| A kept refusal (`unavailable`, `not-authorised` other than a wrong or stale code, `not-found`, `refused`; 12.3) | The key row and the refusal: kind, code and `missing`, as identifiers and codes only | The same refusal | Same key: the same refusal. After fixing the cause, a new submission with a new key |
| A request carrying a secret (12.5) | The key row; the names of the secret fields; the identifier of any credential the command wrote; never the secret in any form | An authenticator code is not compared and the first answer is returned, except an answer 12.6 refuses (DEC-113, DEC-114). A new password is verified against the credential the first run wrote while it is current: the first answer, or `conflict` when it differs. When it cannot be compared: `conflict` with `kernel.secret-not-comparable` | The same key and content while the credential is current; otherwise a new submission |
| An answer that showed a secret (12.6) | Only the fact that a secret was shown | `conflict` with `kernel.answer-not-repeatable` (DEC-113) | Start again with a new key: a new enrolment replaces the secret not yet confirmed; a service identity's secret is issued again only by revoking the old credential |
| An answer that showed a restricted value unmasked (12.1) | Only the fact that a value was shown, beside its access record | `conflict` with `kernel.answer-not-repeatable` (DEC-114) | A new request with a new key: a fresh code, authorisation and a new access record |
| The same key with changed content | The refused request: no secret; every restricted value encrypted under the Organisation's key | `conflict` with `kernel.idempotency-key-reused` | A new key for the new content |
| An outcome not known (above) | Nothing, or the committed rows, whichever happened | A replay if it committed; otherwise the request runs once | Send the same key again; never a new key |

### 12.5 Requests that carry a secret

This settles RR-207 for every request but the setup step, which keeps its own rule (access-and-approvals 9.11). Such requests are: creating a user, resetting another user's credential, changing one's own password, and every request carrying an authenticator code (access-and-approvals 3.2, 3.3). **Proposed**, with the two product choices of CH-8 answered by the product owner on 6 Oct 2026.

- **Nothing of a secret is kept.** The hash and a kept refused request hold no secret and no form of one: only the names of the secret fields present (12.4; access-and-approvals 3.2; `PRD-SEC-014`). A fast hash could be guessed offline from a copy of the database, and a keyed hash would need a key of its own and would outlive the credential in an append-only row (access-and-approvals 9.11), so neither is used.
- **An authenticator code proves presence; it is not content.** It shows that the person is there for a protected action (`PRD-SEC-001`; access-and-approvals 3.3) and changes nothing the command does. The first run verifies it. An identical replay is answered with the first answer without reading the replay's code, since a replay has no effect, except an answer 12.6 refuses (DEC-113, DEC-114), such as one that showed a restricted value unmasked. A wrong or stale code is answered `not-authorised` and is not kept under the key, so the person corrects the code and sends again. Attempts are counted by the throttling of GC3-5, never by the key. The product owner confirmed this reading of `PRD-INT-002` on 6 Oct 2026 (CH-8).
- **A password presented to unlock a locked session proves presence too** (access-and-approvals 3.3; `S1-F01-T09`). Every unlock request, a replay included, checks it before the command runs, as sign-in does, and a wrong one is answered with the sign-in refusal and never kept under the key; the command under the key holds no form of it, so a replay is never compared on it. In the route table it is a `presented-secret`, which only sign-in and the unlock carry. **Design choice.**
- **A new secret is compared while it still can be.** For a password or a temporary password that the request sets, an identical replay is answered from the first outcome:
  1. **A kept refusal.** A refusal caused by a secret, such as a password the password rules refuse (GC3-5), is never kept under the key, so a kept refusal did not depend on the secret. But nothing of the first secret is kept, so whether the replay's secret differs cannot be told, and `PRD-INT-002` rejects and keeps changed content. Decided by the product owner, 6 Oct 2026 (CH-8): the helper refuses it as changed content with `kernel.secret-not-comparable` and keeps it for investigation without the secret, and the client starts a new submission.
  2. **A credential still in force.** The result row names the credential the first run wrote (12.4). While that credential is still the login's current one, the replay's secret is verified against its Argon2 hash, as the setup step does (access-and-approvals 9.11). If it verifies, the first answer; if not, `conflict` with `kernel.idempotency-key-reused`, kept without the secret. `kernel` cannot read credentials, so its helper defines a contract for this check and `access`, which owns them, implements it (module-map section 3, rule 6).
  3. **A credential since replaced,** because the user set a new password or a reset replaced it: the secret can no longer be compared. Decided by the product owner, 6 Oct 2026 (CH-8): the helper refuses it as changed content with `kernel.secret-not-comparable` and keeps it for investigation without the secret, and the client starts a new submission.
- **Nothing leaks through the comparison.** A refusal says only that the content changed, never which field. Each verification is one Argon2 check against a credential the first run wrote; no new secret material is made (`PRD-SEC-006`).

### 12.6 A secret shown once

This settles RR-208. It applies to the authenticator secret at enrolment (access-and-approvals 3.2) and to a service identity's secret (access-and-approvals 2.3); its rule that the answer is never repeated applies also to an answer that showed a restricted value unmasked (12.1, 12.4; DEC-114). **Proposed.**

- **On the wire** the secret is a plain string. Its schema is a Zod codec between that string and the `Secret` wrapper, `shownOnceSecret()`: the server encodes the answer, revealing the value at that one place, and the typed client decodes it back into a `Secret`, so the web app's state, logs and error reports show only the placeholder until the screen shows it to the person. The fields of `enrolmentStartResponseSchema` change from `secretString()` to `shownOnceSecret()`, which registers them in `secretRegistry` as shown once.
- **In OpenAPI** it is a string with `format: password`, `readOnly: true` and the extension `x-shown-once: true`, so a reader of the document knows the answer cannot be had again.
- **Never again.** The answer carries `Cache-Control: no-store` (12.1). It is not kept in the idempotency result (12.4): the result row records only that a secret was shown, and a replay is answered `conflict` with `kernel.answer-not-repeatable`. `PRD-INT-002` says so since DEC-113: an answer that showed a secret is never repeated, and its identical replay is refused (`PRD-SEC-014`; access-and-approvals 3.2; CH-12). Since DEC-114 the same holds for an answer that showed a restricted value unmasked (12.1, 12.4). The client starts again with a new key. Starting enrolment again replaces the secret not yet confirmed, so no unconfirmed secret stays usable. A service identity's secret is issued again only by a new command that revokes the old credential (access-and-approvals 2.3).
- Neither secret appears in a log, an audit record, an error or a live update (`PRD-SEC-014`; numbering-and-audit 4.3).

### 12.7 The version token

- **What it is.** Every read of a record that a command can change returns `versionToken`: the identifier of the newest append-only row the record's current state was built from. For a draft version that is its latest change row, for a frozen version its version row, and for a header's state its latest status record (7.2). It is compared for equality only. **Proposed.**
- **Where it travels.** In the body, so a list carries one per row and a bulk request one per item. A command that changes an existing record sends back the token it read; a command that creates a record sends none. **Proposed.**
- **The check.** The command compares the token under the record's lock, with the other rechecks (8.1; `PRD-INT-003`). A difference is `conflict` with `kernel.stale-version`; the answer names the record and its current token, never its content. The screen keeps the person's input, reads the record again and shows what changed; it never merges silently (`PRD-UXP-003`). **Proposed.**
- **Not the approval's binding.** An approval binds to the exact version the approver reviewed, and Decide checks that separately (`PRD-ACS-007`; access-and-approvals 9.5). The token only stops a change made on a stale screen.
- The token is part of the idempotency hash (12.4).

### 12.8 Events and the outbox

Module-map section 8 sets the rules: an event is an outbox row saved in the transaction that caused it, named `module.fact`, carrying identifiers and versions only, delivered at least once, and consumers are idempotent on the event's identity (`PRD-MOD-006`, `PRD-INT-008`). This section says how. **Proposed.**

- **The row.** `kernel.outbox_event`, append-only (7.1), in each Organisation database. It is `unscoped`, because only `kernel` reads it, for the worker and the live-update stream (12.12), and each consumer then reads the record under its own authorisation. It holds:
  - `id`, a UUIDv7: the event's identity;
  - its type, such as `access.approval-decided`, and the version of its payload schema;
  - its event and recording times (section 9);
  - the actor, and the person on whose behalf a job acts (access-and-approvals 2.3);
  - the command's correlation identifier (12.11);
  - the subject: module, record type, record and version;
  - the subject's scope facts as identifiers (6.1), for the live-update filter (12.12);
  - the payload, identifiers and versions only, as the publishing unit's schema states (12.2): never an amount, a name, a restricted value or a secret (access-and-approvals 6).
- **Written with the command.** A command adds its events through the command context; they commit with its other writes, or none do (`PRD-INT-004`; 8.1). The payload is checked against its event type's schema, and a field the schema does not declare is refused, never silently dropped. At commit the command also sends a PostgreSQL notification on the channel `kernel_outbox`, as a wake-up only; the outbox stays the source. The worker does not listen for it yet and reads each outbox at its poll interval (RR-272).
- **Consumers.** A unit registers each consumer in its `jobs/` folder: a stable name, unique in the application; the event type and the payload version it reads (one version per consumer, as built in `S1-F01-T06`); the internal service identity it runs as; and its handler. The worker refuses to start with two consumers of one name, or with a consumer of an unknown type. It records each consumer in `kernel.outbox_consumer` of each Organisation database (name, event type, first registration; append-only, `unscoped`), and stops at a name already recorded for another event type: a renamed consumer is a new consumer. A new consumer receives the events recorded from its first deploy on, its first registration; giving it older events is an operator job.
- **Dispatch.** The worker's outbox processor reads, for each consumer, the events of its type recorded since its registration and not yet handed to it, in identifier order. For each it creates, in one transaction, a pg-boss job in that database and a row of `kernel.outbox_dispatch` naming the event, the consumer and the job. That pair is unique, so an event is handed to each consumer once, however many workers run (3.2: pg-boss's schema is in each database). One queue, `kernel.outbox-delivery`, carries every delivery; a job's data is the event's identity and the consumer's name, and the job carries the consumer's retry setting (12.9). The processor runs as the internal service identity `outbox` (access-and-approvals 2.3; 6.3), which the setup step writes (RR-271).
- **One effect.** A consumer runs as a command under its own internal service identity (access-and-approvals 2.3; `PRD-SEC-018`), with the same access checks as anyone (module-map section 3, rule 8). Its receipt is its idempotency key row (12.4), keyed by the event's identity and the consumer's name and committed with its effect. A second delivery, such as after a crash before pg-boss recorded the job done, finds the receipt and has no second effect (`PRD-INT-008`). A work item is also keyed by the owner's record, version and kind (access-and-approvals 11.1), and an exception by the event that raised it (access-and-approvals 12.1), so a replay makes neither twice.
- **No order assumed.** An event carries identifiers only, so a consumer reads the record's current version through its owner's interface and acts on that. A late or repeated event does no harm (`PRD-SEC-005`).
- **Failure.** A consumer's job follows the retry rule of 12.9.

### 12.9 Jobs and their retry rule

- **Where.** Jobs run on `worker`, the same build as `app` with another start command ([deployment.md](deployment.md) section 2), using pg-boss in each Organisation database the directory lists, one pg-boss instance per database. Queues are created by migration (3.2). A request never does a job's work; it enqueues only through the outbox, so a job exists only if its request committed, and no counter request waits on background work (`PRD-PRF-003`). **Proposed.**
- **A job kind** is registered in its unit's `jobs/` folder with its name; its payload schema, identifiers only, never a secret or a restricted value; the service identity it runs as (`PRD-SEC-018`; module-map section 10); its retry setting (below); and, for a posting job, the accounting book that keeps it one at a time (stock-ledger 10.6), through pg-boss's singleton key, which must hold a second queued posting job of the same book until the first ends, never drop it; this is checked against the pinned pg-boss version in `S1-F01-T06`. **Proposed.** Checked with pg-boss 12.35.1: a queue of pg-boss's `singleton` policy keeps a second job of the same singleton key created and unfetched until the first completes or fails, and drops neither (`job-queue.int.test.ts`); a posting queue uses that policy.
- **A job kind on an interval,** such as the audit sealing job, the seal check and the partition coverage check (numbering-and-audit 4.4; RR-241), is sent by the worker for each Organisation at the interval of its worker setting, one job per interval however many workers run (pg-boss's singleton slot). The audit job kinds run as the internal service identity `audit-jobs` (RR-271).
- **Each step is a command** of 8.1, keyed by the job's identity (12.4), so a step that runs again has one effect. Slow work comes before its transaction (stock-ledger 10.6), and an outside system is called only outside it (8.3). As built (S1-F01 review, DEC-118, RR-360): the step's first act in its transaction is Hold (`JobIdentities.hold`), which finds the assignment of the step's service identity that grants its action, takes step 0 of 8.2 for it (the identity row, the assignment and the role it grants, all shared) and rechecks under them that the identity is enabled, the role's version in force is the one seen before the locks and the same assignment still grants the action, as `holdAuthority` does for a route's command. A refusal is kept under the step's key and never retried; a role version that took effect while the locks were taken throws `StaleAuthority`, which the retry rule retries like a transient failure, since nothing was written. So a job step's own locks start at step 1. The outbox processor holds its authority the same way in each dispatch and in the registration of consumers, and leaves the rest of a pass to the next when it no longer holds. A replay's access check (12.4) stays a read and takes no lock.
- **The retry rule** goes by what failed. It is the job runner's rule that access-and-approvals 9.8 step 5 leaves to this document. **Proposed.**

| What failed | Retried by the runner | Then |
| --- | --- | --- |
| Something transient: a lost connection, a time limit of 5.1, the worker stopping | Yes, up to the job kind's attempts, with growing delays (CH-10) | Failed after the last attempt |
| A refusal under the locks: the version changed, the value is beyond the decision's limit or approved amount, or the state no longer allows it | Never | The record shows the refusal and, where access-and-approvals 9.8 step 5 says so, returns for renewed approval |
| A defect: a deadlock (8.1), an `AO` error (7.1), a schema mismatch, an unexpected error | Never | Logged as a defect (8.1); the job fails at once, whatever retries its setting allows |
| An outside system answered nothing, or its outcome is uncertain | Never blindly | The outcome stays unknown until reconciled (12.10; `PRD-INT-006`, `PRD-INT-007`) |

- **A failed job** stays failed, is never deleted while CH-9 is open, and is shown to authorised operators in the operations view (`PRD-SEC-013`; module-map 4.1). A failed posting job posts nothing, and its approval decision stays unused (DEC-097). A posting job that still fails after its retries raises an unfinished-operation exception (access-and-approvals 9.8 step 4; `PRD-EXC-001`) once `exceptions` exists (`S1-F08`). An authorised person may run it again under the same rules. An approval decision is used again only while the document version is unchanged and the value under the lock is within the decision's limit and the approved amount; otherwise the record returns for renewed approval (access-and-approvals 9.8 step 5; DEC-097).
- **Settings, no defaults.** The attempts and delays of each job kind are worker settings read at start. A job kind without them fails to register, so the worker does not start; none has a value in code. Their values are **OPEN** (CH-10). As built in `S1-F01-T06`, the worker reads them from `AOS_WORKER_SETTINGS`, JSON: `pollSeconds`, how often it reads the directory and each outbox and polls each queue; for each consumer and each job kind `retries` (after the first attempt), `retryDelaySeconds`, `retryBackoff` (growing delays) and `activeLimitSeconds` (how long an attempt may stay active before it counts as failed, as when the worker stopped under it); and for a job kind on an interval `everySeconds`. A consumer or job kind it does not set, or a name nobody registered, stops it. **Provisional values for synthetic and test work** (product owner, 7 Oct 2026, DEC-118 and DEC-119): for transient failures, five attempts in all (`retries` 4 after the first), the first retry after 10 seconds (`retryDelaySeconds` 10), then increasing delays (`retryBackoff`) with jitter; five minutes per attempt for ordinary jobs (`activeLimitSeconds` 300); polling every 5 seconds (`pollSeconds` 5); the sealing job every 15 minutes (`everySeconds` 900), the seal check, the partition coverage check and the partition upkeep hourly (3600). They live only in the labelled synthetic worker settings of local work, tests and `dev` (`apps/server/test/fixtures/worker-settings.ts` and `SYNTHETIC-worker-settings.local.json`, built in `S1-F01-T24`); they are no KDPS value, no value in code and no default for `kdps-test` or production (CH-10), and a unit test fails when a source under `apps/server/src` writes a retry, delay, limit or interval as a value. pg-boss 12.35.1's backoff adds its own jitter (each delay drawn at random between the doubled delay and twice that), so the worker adds none. Tests shorten only the waits they sit through (the first delay, the poll and the intervals), never the attempts. The grants rebuild runs every 60 seconds (`everySeconds` 60) for synthetic and test work (DEC-120, RR-390); it only refreshes the effective grants and publishes what changed, since Authorise and row-level security check every assignment's dates against today themselves (access-and-approvals 7.1, 7.2). Import and restore jobs get their own, longer active limits, set with those jobs (`S1-F06`, `S1-F13`, `S1-F14`; DEC-119); not built yet. A time limit never makes a committed action run twice: every step keeps its idempotency key, so an attempt counted failed after its commit runs again as a replay (12.4; `PRD-INT-002`, `PRD-INT-008`; `worker.int.test.ts`).
- **Nothing deleted before CH-9.** Every queue and every job is created with pg-boss's `deleteAfterSeconds` 0, its "never" for a completed, cancelled or failed job, and with `retentionSeconds`, how long a job may wait unrun, at the largest value its integer column holds, since pg-boss has no "never" for it (migration `0009`). The worker never reindexes, installs, migrates or creates a queue.
- **Jobs on dates.** A job that acts when a date passes, such as rebuilding effective grants (access-and-approvals 7.2), runs for each Organisation after its business date changes under its timezone (section 9), never at the server's midnight. How often the worker checks is a worker setting (CH-10). **Proposed.**
- **Maintenance under the migration role,** such as the audit partitions of CH-5, runs as restricted maintenance (3.2, 5.1). The scheduled partition upkeep is the one exception that runs from the worker, independently of deploys (product owner, 7 Oct 2026, DEC-118; RR-240): the job kind `audit.ensure-partitions`, sent for each Organisation under the `audit-jobs` service identity at the interval of its worker setting, calls `audit.ensure_partitions`, which stays owned by the migration role and runs with its rights as a `SECURITY DEFINER` function with its own `search_path`; the runtime role holds `EXECUTE` on that function alone. It only creates the missing partitions of the coming months and never drops, detaches or deletes anything. A failed run fails its job, which stays visible (above), and the coverage check still raises its alert (numbering-and-audit 4.4). **Design choice** of the mechanism: the worker keeps only runtime credentials (`PRD-SEC-018`).

### 12.10 Outside systems and simulators

Module-map section 9 names the owner of each adapter, [deployment.md](deployment.md) section 7 what each does on `kdps-test`, and [how-we-build.md](../../plan/how-we-build.md) section 4 the order in which each is built. This section says how the code does it. **Proposed.**

- **One contract, several implementations.** An adapter is an interface its owning module defines, with a simulator and a real implementation, chosen for each environment by a setting read at start. Replacing an implementation never changes what a completed record means (`PRD-INT-013`).
- **The request identity comes first.** An attempt record, with its request identity, is committed as pending before the call, and the call runs after that commit (8.3; `PRD-INT-006`). Where the outside system takes an idempotency key, the request identity is sent as that key, so a repeat is recognised there too.
- **Four outcomes.** The owner keeps each attempt's outcome as an append-only status record: pending, unknown, failed or succeeded (`PRD-INT-007`). A timeout or a lost answer is unknown, never failed and never succeeded. The screens show Awaiting outcome, Outcome unknown, Failed, or the record's done state (design-language section 7).
- **Reconcile before retry.** An unknown outcome is first looked up: a status lookup, such as the GSP's for an IRN with an uncertain result (`PRD-INT-010`), or Tally's acknowledgement (`PRD-INT-009`). Only a reconciled failure allows a new attempt, under the same request identity where the system allows it. No job retries an unknown outcome blindly (`PRD-INT-007`, `PRD-INT-008`).
- **Callbacks** reach a route that authenticates the caller by its service-identity credential or the outside system's signature (`PRD-INT-007`; access-and-approvals 2.3). Each is idempotent on the outside system's own event identity. A callback that disagrees with a settled outcome changes nothing; it is kept and shown for reconciliation.
- **Simulators first.** Each adapter's simulator is an in-process fake, scripted to answer success, refusal, a timeout whose outcome is unknown, a duplicate or late callback, and, where the system works in batches, partial success, so reconciliation is tested from the start. It lives beside its adapter in the owning module. What it returns says it is simulated, such as a reference beginning `SIM-`, so no simulated outcome can pass for a real one; such a label is not a synthetic code of 11.1. The server refuses to start where any adapter selects a simulator outside local work, tests and `dev`, so a simulator never ships as a fallback.
- **Stage 1.** File storage is the only outside system, and it is not simulated: MinIO locally and in tests, and the Railway bucket on `dev` and `kdps-test` (D-2, DEC-105). Nothing is sent by email, WhatsApp or SMS before stage 5, and `notifications` has no channel adapter until then (DEC-099).

### 12.11 Logs and the correlation identifier

- **pino JSON to standard output,** one object per line, read in Railway's log view ([deployment.md](deployment.md) section 9; PRD Stack: Diagnostics). Each line carries the time, the level, the service (`app` or `worker`), the environment and the correlation identifier; and, once known, the Organisation code (DEC-093), the actor's identifier, the route template or the job kind, and the unit. **Proposed.**
- **One correlation identifier per request.** The server makes it, a UUIDv7, when the request arrives, and never takes one from the client. It is sent back in the `X-Correlation-Id` header and in every error envelope (12.3), and kept in the command context, in each audit record (numbering-and-audit 4.1) and in each outbox event (12.8). A job logs the identifier of the event or request that caused it beside its own. When traces are added, their identifiers are logged beside it (PRD Stack: Diagnostics). **Proposed.**
- **What a request logs.** One line when it ends: the method, the route template, the status, the error code and the duration. Never the query string, the body or the answer. **Proposed.**
- **What never appears in a log** (`PRD-SEC-006`, `PRD-SEC-014`; access-and-approvals 3.1, 3.3 and 6):
  - a secret: a password or temporary password, an authenticator code or secret, a session identifier or cookie value, a service credential, an encryption key, or a connection string with its password;
  - a restricted value of any field class (access-and-approvals 6);
  - a request or answer body, or the input value of a validation issue;
  - a typed login that matched no user, or an Organisation code the directory does not list;
  - a file's content: only its hash and size (imports-and-opening-data 9.3);
  - a database error's detail or bound parameters: only its SQLSTATE, constraint and table;
  - a network address or a person's name, which logs do not need; the access record keeps the network address (numbering-and-audit 5.2).
- **How.** Four layers, each **Proposed**: nothing logs a body or an answer; the `Secret` wrapper prints a placeholder; pino redacts the known key names, as a backstop only; the logger keeps of a database error, or of one wrapping it, only its type, SQLSTATE, constraint, schema and table, with the message of the application's own wrapper (such as a failed migration naming its file), never the database's message, detail, query, parameters or stack (S1-F01 review); and a leak test runs sign-in, enrolment, the password change, a reset and user creation with marker secrets and fails if a marker appears in the captured log, an error envelope, or an audit or access record (`S1-F01-T08`).
- **Levels.** `info` for a request's line and a job's end; `warn` for a refusal an operator should see, such as `kernel.idempotency-key-reused`; `error` for `failed` and a failed job. The level is a setting read at start. **Proposed.**
- Failed jobs, stale data and integration failures reach authorised operators in the operations view, not only the logs (`PRD-SEC-013`; module-map 4.1).

### 12.12 Live updates

[deployment.md](deployment.md) section 5 sets the frame: Railway's limits on a stream, a heartbeat, reconnection with `Last-Event-ID`, and identifiers only (PRD Stack: Live updates). The rest is **Proposed**.

- **One stream per session:** `GET /api/live` on `app`, authenticated by the session cookie like any request.
- **A message** carries the outbox event's identity as its SSE `id` and its type as the SSE `event`; its data holds only the type and the subject: module, record type, record and version (module-map section 8). Its schema is in `packages/schemas` (12.2). It never carries a name, an amount, a restricted value or a secret (`PRD-SEC-006`; access-and-approvals 6).
- **Only what the actor may view.** Before it sends an event, the stream checks the event's scope facts against the effective grants of the session's actor for that record type, the same test row-level security makes (6.2; access-and-approvals 7.2). A work item goes only to those who may act on it (access-and-approvals 11.1). The grants are read again when `access.assignment-changed` names the actor (`PRD-SEC-005`).
- **Then an authorised refetch.** The browser marks the record's cached reads stale and reads them again through the owning unit's routes, under the reader's own authorisation (module-map 4.1).
- **Heartbeat and length.** A comment line is sent at an interval the builders set well inside Railway's 5-minute idle limit; the server ends each stream before Railway's 15-minute limit, and the browser reconnects at once. These follow the platform's limits; they are no KDPS value.
- **Reconnecting.** On `Last-Event-ID`, the server sends the events after it from the outbox, filtered the same way. If the outbox no longer holds that event, or the identifier is unknown, it sends `resync`, and the browser reads everything on screen again, so nothing is lost.
- **Revocation and lock.** Revoking a session closes its stream at once on `access.session-revoked`, and at the latest at the next heartbeat (`PRD-SEC-008`; access-and-approvals 3.3). A locked session's stream is closed and opened again after the unlock.
- **Several `app` instances.** Each follows the outbox of each Organisation database, woken by the notification of 12.8, so any instance serves any session.

### 12.13 Screen text

- **One catalogue.** Every string a screen shows comes from the message catalogue in `apps/web`: labels, state names, refusals, empty and error states, and alerts in My work (`S1-F01-T14`; design-language section 11). Code holds message identifiers, never text. **Proposed.**
- **English (India) first.** Hindi for the screens of stages 1 to 5 arrives in stage 5, and for stage 6 screens in stage 6 (`PRD-PRO-009`; `AGENTS.md`, "Delivery"). The catalogue has one file per language with the same identifiers; a test fails when an identifier used in code has no English entry, and Hindi entries are checked the same way from stage 5. **Proposed.**
- **Messages with values** take named parameters. Plurals use the built-in `Intl.PluralRules`; numbers, money and dates are formatted with `Intl` as design-language section 8 sets. No translation library is added (10.6). **Proposed.**
- **The server sends codes, not text.** Every refusal code (12.3), state name and live-update type has a catalogue entry; a test fails when a code declared in `packages/schemas` has none. A refusal shows its blocking reason and next action from `missing` and `next` (`PRD-UXP-003`). State names are those of design-language section 7. **Proposed.**
- **Words.** The PRD's "Words used" exactly; sentence case; the people and the rule named, not the system (design-language section 11).
- **Alerts before stage 5** reach people only as work items in My work and on the screen concerned; nothing is sent (`PRD-EXC-013`, DEC-099).
- Text the server writes into a file it makes, such as an export's headings, comes from a catalogue in the owning unit in the same way. **Proposed.**

### 12.14 KDPS-valued settings

- **A setting, never a constant.** A value KDPS owns, such as a limit, tolerance, name, date, reason, recipient, number format or retention period (DEC-105), is an effective-dated setting of its owning module (domain-model 3.6; 7.3; `PRD-MOD-010`). It has no default anywhere: no column default (3.3), no schema default (12.2), no fallback in code, and no environment variable that sets a business value (`AGENTS.md`, "Never invent a value").
- **Not set is a stated answer.** Reading a setting returns its version in force on the date, with the version's identifier, which the command stores (7.3), or "not set" as a kind of its own; never a null read as zero, and never a guess (`PRD-MOD-015`). **Proposed** shape: `{ kind: 'set', value, versionId }` or `{ kind: 'not-set' }`.
- **Unavailable until signed and valid.** An operation that needs a setting stays unavailable until its capability is on, its policy is Signed, its real values are validated, and its activity is granted where one applies; the refusal names what is missing (module-map 4.4; access-and-approvals 7.1 step 2; `PRD-SEC-017`). Each module registers its validity check with `configuration`.
- **Where a value came from.** Each setting version records its origin: KDPS's answer; a setting of the test setup on `kdps-test`, such as the session limits (DEC-102), the test role assignments (DEC-103) and the first reason list (DEC-105), none of which enables a gated action (DEC-071); or synthetic (11.1). Available refuses a synthetic version outside local work, tests and `dev`, and a test-setup version outside `kdps-test`. **Proposed.**
- **A missing security setting blocks.** Confirmed by the product owner, 7 Oct 2026 (DEC-118): while a required security setting (the Organisation's timezone, the sign-in throttling, the password rules, the office session limits) is not set, sign-in is unavailable and names it; nothing falls back silently. The setup step validates that each is present and refuses a request without them (access-and-approvals 3.1, 9.11).
- **An example is no value.** A value the PRD or a policy gives as an example is not a setting until a signed policy makes it one (`AGENTS.md`, "Never invent a value").
- **Technical settings** that are not KDPS's, such as the caps at intake (imports-and-opening-data 9.3) the worker's retry settings (12.9) and the test sign-in list `AOS_DEMO_SIGN_IN` (only with `AOS_ENVIRONMENT` `local` or `dev`; access-and-approvals 3.4; DEC-121), are environment settings read at start through one Zod schema. A missing one stops the service at start; nothing falls back to a value in code. Secrets come only from the environment's variables ([deployment.md](deployment.md) section 9) and are never logged (12.11). **Proposed.**
