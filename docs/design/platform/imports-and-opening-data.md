## 2. Records and words

The records are those of [domain-model.md](../architecture/domain-model.md) 3.9, with two added: the document inside a batch, and the comparison run.

| Record | What it is here | IDs |
| --- | --- | --- |
| Stored file | One original file or photograph, kept byte for byte, with every receipt of it: source system, uploader, time and the document reference claimed | `PRD-IMP-002` |
| Attachment | A link from a stored file to a record of any module | `PRD-SEC-005` |
| Layout | A recognised file structure for one source and document type, in versions (6.1) | `PRD-IMP-003`, `PRD-IMP-004` |
| Mapping | How a layout version fills one target's fields, in versions (6.2) | `PRD-IMP-003` |
| Mapping rule | A rule that turns a source word into an approved value, in versions (6.3) | `PRD-IMP-003`, `PRD-IMP-008` |
| Import batch | One stored file read with one layout version and one mapping version, of one kind, for one target | `PRD-IMP-010` |
| Document | One business document the batch's file holds, with its document reference. A file may hold several (6.6). **Design choice:** the document is the unit of duplicate control and of publishing | `PRD-IMP-011`, `PRD-IMP-012` |
| Staged row | One row of the file, kept with every original cell, and its normalised values with their origins (section 5) | `PRD-IMP-002`, `PRD-IMP-006` |
| Row issue | A problem found by validation, with the correction it needs (section 8) | `PRD-IMP-007` |
| Import outcome | What happened to a batch and to each of its documents, kept for failures as well as successes (7.4) | `PRD-IMP-012`, `PRD-IMP-013` |
| Comparison run | A reconciliation of two sets by a key, such as an opening manifest against the earlier POS's last SOH (10.3). **Design choice:** a part of `files-imports`, so every opening and side-by-side check uses one tool | `PRD-LIF-027`, `POL-14.07` |

- "Batch" here always means an import batch. A batch of goods with an expiry date is "batch and expiry", as in `PRD-MER-011`.
- PRD words are used as defined: SOH is a comparison source, never a count; Earlier POS, Side-by-side test, Switch and Switch count are as in PRD "Words used". A KDPS report titled "List of Sales Vouchers" is a brand report, not a Voucher.

## 3. The pipeline

### 3.1 Steps

```mermaid
flowchart LR
  A[Intake] --> B[Store original]
  B --> C[Read]
  C --> D[Detect layout]
  D --> E[Map and stage]
  E --> F[Validate]
  F --> G[Preview]
  G --> H[Review]
  H --> I[Publish through handler]
  I --> J[Outcome]
```

1. **Intake.** A person or an adapter hands in a file with its source system and, where known, a document reference (`PRD-IMP-002`). The file is read in memory first and checked for safety and size (9.3, `PRD-SEC-011`), and on `kdps-test` for customer-contact columns (section 11; DEC-112, GC6-6), which intake finds in memory with the Confirmed layout versions the file fits (section 11, "How intake finds customer-contact columns"; RR-203). A refused file is not stored, and the refusal is shown with its reason.
2. **Store the original.** The bytes are kept unchanged and stored encrypted (section 11) in file storage: on the test setup a Railway bucket, S3-compatible ([deployment.md](deployment.md) D-2, DEC-105). The stored file is identified by a hash of its content; each receipt keeps its own source system, uploader, time and claimed document reference (`PRD-IMP-002`). **Design choice.** Stored files and evidence attachments are built first, with `S1-F06-T05` right after `S1-F01`, so the stage 1 records that need evidence attach real files from the start (product owner, 6 Oct 2026; DEC-116). Each object key starts with the Organisation's identifier (GC9-10), and the app never overwrites or deletes a stored object (15.1).
3. **Read.** A format reader turns the file into a neutral grid (9.1). It evaluates no formula, runs no macro and follows no link (`PRD-SEC-011`).
4. **Detect the layout** from the grid's structure (6.5, `PRD-IMP-004`). The preparer chooses the layout version and the batch kind.
5. **Map and stage.** The mapping version turns each data row into a staged row: original cells kept, values normalised, every value marked with its origin (section 5; `PRD-IMP-003`, `PRD-IMP-006`). Rows are grouped into documents (6.6).
6. **Validate.** Field, row, document and file checks; references checked by the target module's handler through its own interface (13.2); control totals compared; duplicates and conflicts found (sections 7 and 8; `PRD-IMP-005`, `PRD-IMP-007`, `PRD-IMP-011`).
7. **Preview.** The target handler works out, without writing, what each document would create or change (13.2). The preview shows it beside the validation report (`PRD-IMP-005`).
8. **Review.** The review the handler requires for this kind and target (13.2): the preparer's submission after the preview, or an approval request in `access` bound to the exact batch version (`PRD-ACS-007`; access-and-approvals 9.1).
9. **Publish.** For each document chosen, the handler writes its own records in one transaction with the audit record and the outbox rows (module-map 6.2 flow B). A required document posts whole or not at all (`PRD-IMP-012`). A large document posts through a queued job (10.6; stock-ledger 10.6).
10. **Outcome.** The batch and each document keep what was accepted, rejected, pending and duplicate, with quantities and values, whether publishing succeeded or failed (7.4; `PRD-IMP-012`, `PRD-IMP-013`).

### 3.2 Batch states

The states are the DM-4 baseline: Staged, Validated, Published and Failed (DEC-105; [design-language.md](../ui/design-language.md) section 7). No other state is added. **Proposed** (GC6-15): a queued or failed publish keeps the batch Validated, as below.

| From | To | When |
| --- | --- | --- |
| — | Staged | The batch is started and its rows staged |
| Staged | Validated | Validation finished. The batch now waits for review |
| Validated | Staged | A staged value is changed, a document is excluded or put back, or the layout or mapping version is changed. Validation runs again, and an open approval request on the old batch version ends as Superseded (`PRD-ACS-007`; access-and-approvals 9.6) |
| Validated | Published | Every document chosen for publishing has posted. The outcome lists those excluded, refused as duplicates or refused as conflicts |
| Staged or Validated | Failed | The file cannot be read, or the preparer withdraws the batch, for example when every document is excluded, a duplicate or a conflict. The outcome is kept (`PRD-IMP-012`) |

- A publish attempt that fails, or a publish job that fails, posts nothing; its outcome is kept, and the batch stays Validated so it can be corrected and published again. A retry of a job follows access-and-approvals 9.8 and stock-ledger 10.6: the same approval decision is used only while the batch version is unchanged.
- A batch whose publish job is queued shows Validated with the job's state beside it.
- A Published or Failed batch is never edited. A correction is a new batch (7.3).

### 3.3 Where the work runs

- Steps 1 to 8 run outside any business transaction. Reading, staging and validating a large file run as a pg-boss job on the `worker`, never inside a counter request (`PRD-PRF-003`; module-map section 10). The preparer sees progress through live updates that carry identifiers only.
- **As built** (`S1-F06-T01`, `S1-F06-T03`): reading and staging still run in the Start an import request, and validation in the Validate request; no job kind is added. The job of this section comes with the 10,000-line measurement of `S2-F13` (test 27). **As built** (`S1-F06-T02`): every read of a workbook, at intake and again at Start an import and Detect a layout, runs the safety checks and the XLSX reader in a worker thread of its own under the caps of 9.3, so a large or hostile file cannot hold the request's process past the memory and time caps; the worker is no job, and the request waits for it.
- Step 9 is one transaction per document, in the shape of module-map 6.1, under the handler's own module interface (`PRD-MOD-006`). **As built** (`S1-F06-T04`): Publish runs each document chosen as a command of its own, with its audit record and its event, under an idempotency key derived from the request's key and the document (a UUID of version 8 from SHA-256), which its audit record carries as the key of the command that wrote it (numbering-and-audit 4.1 "Request"; S1-F06 review), then the batch's own command, under the request's key, writes the attempt's outcome (7.4) and the batch's state; so the request sent again is answered once (`PRD-INT-002`). The handler's Maintain operation runs in the document's transaction; the rows it would lock are offered by the handler and locked with the batch at step 1 in one call (code-house-rules 8.2), and the catalogue's Maintain operation then finds them held and does not lock them again. Publishing still runs in the request; the queued job of 10.6 comes with large documents.
- The PRD performance table sets a target: parse, map and validate a 10,000-line structured PT import in under 1 minute. It is measured under `PRD-PRF-001`, and reported apart from human review and any AI extraction (`PRD-PRF-002`), in stage 2 with `S2-F13` (test 27; DEC-115).
- A failed job, a stuck batch and a file that could not be read are shown to authorised operators (`PRD-SEC-013`).

## 4. Batch kinds

### 4.1 The five kinds

A batch has exactly one kind, chosen when it starts and fixed for life (`PRD-IMP-010`; domain-model 3.9).

| Kind | What it does | May create | Never creates | First targets |
| --- | --- | --- | --- | --- |
| Create | Adds master records | New master records through the owner's Maintain operation; product and vocabulary proposals (structure-and-masters 4.2, section 7) | Stock, money or a tax document | `organisation`, `merchandise` (stage 1) |
| Update | Changes existing master records | New versions through the owner's Maintain operation, starting today or later (structure-and-masters 2.2) | An edit of a version in force; a back-dated version; stock, money or a tax document | `organisation`, `merchandise` (stage 1) |
| Opening balance | Brings a unit's opening stock, dues, advances and deposits at its switch (section 10) | A reviewed opening manifest and reviewed opening balances in the Store's opening record; at the switch, opening count movements and financial opening balances | A supplier delivery, booking, invoice, purchase liability or automatic journal for opening stock (`PRD-LIF-008`) | `site-lifecycle` (stage 4); a stage 1 test handler on synthetic data (section 12) |
| Historical reference | Keeps past or outside facts for reports and checks only, such as historical sales (`PRD-LIF-010`) and the earlier POS's daily sales report and SOH (`PRD-LIF-013`) | Reference records in the target's read model, keeping their source identities | Live stock, a receivable or a tax document (`PRD-IMP-010`); any stock movement (`PRD-LIF-014`); a sale or a tax invoice for an externally issued bill (`PRD-LIF-016`) | `ebo-imports` for earlier-POS imports: a minimal module in stage 1 holding only the historical-reference handler, for synthetic SOH and daily sales, which stage 2 (`S2-F12`) extends (section 12; DEC-116); `site-lifecycle` for historical sales (module-map 11.1) |
| Transaction | Brings documents from an outside system that have their own effect under the owner's rules | What the owner's rules allow: a draft PT revision from a supplier file (stage 2), an EBO report applied once (stage 4, `PRD-EBO-005`), bank statement lines (stage 5) | Anything the owner's own workflow would not create; an official PT without PT approval (`PRD-REC-017`) | `merchandise` · PT, `ebo-imports`, `finance` · operations |

- Opening balances, historical reference and live corrections stay distinct (`PRD-LIF-011`). A correction found after a unit's cutover is a live correction in the owning module, such as a count difference or a journal; it is never a new opening batch (10.5).
- "Analytical-history import" in `PRD-IMP-010` means the historical-reference kind here. **Design choice.**

### 4.2 How the kind is enforced

- A handler registers the kinds it accepts and the effects it may have: none, master records, stock, money (13.2). Start an import refuses a kind the target's handler does not accept. **Design choice.**
- The source reference a handler passes to the stock ledger or to Post in `finance` · books carries the batch kind. **Proposed** for the stock-ledger and books designs: both refuse a source whose kind is historical reference, as a last guard behind the handler's own rule (`PRD-LIF-014`, `PRD-IMP-010`).
- An opening-balance batch publishes only where the operation is available: policy 14 Signed and its real values validated (`PRD-SEC-017`; module-map 4.4), on production hosting, at the Store's approved switch (`POL-14.07`, `PRD-LIF-026`). On `dev`, with synthetic data, the path runs under the synthetic-data banner (DEC-071).
- Test 18 of section 17 proves that a historical-reference load leaves every stock quantity and value unchanged, the stage 2 exit check of [phases.md](../../phases.md), rehearsed in stage 1 on synthetic data.

## 5. Where each value came from

Every staged value carries one origin (`PRD-IMP-006`):

| Origin | Meaning | Kept with it |
| --- | --- | --- |
| Supplied | Read from a cell of the file, after only the transforms the mapping names: trim, type, date format, decimal to paise, sign | Sheet, row, column, raw value, cell type and displayed text |
| Calculated | Worked out by a named deterministic function from other values, such as several columns joined or summed (6.2). Money and tax arithmetic uses `packages/calculations` ([shared-calculations.md](../calculations/shared-calculations.md)) | The function, its version and its inputs |
| Mapped | Turned into an approved value by a confirmed mapping rule (6.3) | The mapping rule version and the original word |
| AI suggestion | A draft from the AI gateway (stage 2 onwards) | The AI request record (`PRD-SEC-002`) |
| Entered by a person | Typed by a person, or chosen by a person from a suggestion | Who, when, the reason, and the suggestion it came from |

- **Entered by a person** is the fifth origin. **Design choice:** `PRD-IMP-009` asks for manual selection, and the PT grid already shows "typed" as an origin ([design-language.md](../ui/design-language.md) 10.10).
- The original cell is never overwritten. A calculated value never replaces a supplied one: both are kept, and a disagreement is a row issue (section 8). In the KDPS template, BASIC, P RATE and MARGIN may each be supplied, calculated or both ([pt-file-layouts.md](../../data-notes/pt-file-layouts.md) 1.6, 1.7).
- **Suggestions.** Exact or close matches are offered for manual selection. The target module's handler finds them in its own records (13.2): a code through `merchandise` Resolve a code, a word through trigram search over the approved vocabulary (PRD Stack: Search). `files-imports` sits at tier 1 and never calls those modules itself (module-map section 3). Identity and commercial facts are never filled from a suggestion nobody accepted (`PRD-IMP-009`). A word matched by a confirmed mapping rule is Mapped, not a suggestion.
- A word with no confirmed rule stays as its source word, its target is Unknown, and anything that needs it is blocked. An unapproved mapping proposal changes no operational data (`PRD-IMP-008`).
- **AI in stage 1:** none. Stage 1 imports use the manual route only (DEC-105, module-map MM-14). From stage 2 an AI draft enters only as AI-suggestion values that a person must accept, and AI never posts stock, money or tax (`PRD-SEC-003`, `PRD-SEC-004`).
- Every published record keeps the batch, document and staged row it came from. The audit record's source names the import batch and row ([numbering-and-audit.md](numbering-and-audit.md) 4.1).
- **As built** (`S1-F06-T01`): a staged value is held in its staged row as `{kind: 'supplied', value, origin}` or `{kind: 'unknown'}`; the origin keeps the sheet, row, column letters, cell reference, raw value, cell type and displayed text. The tracer's one transform, `text`, trims the cell's text; an empty cell, blank text or an error cell is Unknown, never zero or text (`PRD-MOD-015`; J-1). A product proposal published from an import keeps its batch, document and staged rows in its own columns (migration 0056), and its audit record's source is `import`, with the batch's code as the reference and the document's first staged row number as the row. **Design choice:** a master create document of several rows has one audit record, which names its first row; the proposal names every row.
- **As built** (`S1-F06-T03`; schema `stagedValueSchema` in `packages/schemas`): a staged value is Supplied (`{kind: 'supplied', value, origin}`, with `calculated` beside it where the mapping names a calculation that never replaces it), Calculated (`{kind: 'calculated', value, calculation: {name, version, inputs}}`, the inputs being the cells' origins), Mapped (`{kind: 'mapped', value, word, origin, rule: {ruleId, ruleVersionId}}`), or Unknown, with `because` where a cell was there to read: `error-cell` (J-1), `not-a-number` (C-1), `not-read` (A-11), `finer-than-paise` (C-2), `ambiguous-rules` (naming the rules) or `input-unknown`. The named calculations are `join` (with a separator the mapping states) and `sum` (exact decimals, or paise), version 1, in `packages/calculations` (`sumDecimals`, `rupeesToPaise`). **Entered by a person** is a `staged_value_entry` row (who, when, the reason, the suggestion accepted, the batch version it made); the latest entry of a field stands for the staged value, which the read shows beside it (`{kind: 'entered', value, entry, staged}`), and the cell is never overwritten. The AI-suggestion origin is refused as `files-imports.ai-suggestions-unavailable`, naming the capability `ai-gateway.drafts`, since the gateway is off (DEC-105; the gateway's design names its capability). Suggestions are the handler's (13.2), read with Suggest values for one field of one staged row.

## 6. Layouts, mappings and mapping rules

### 6.1 Layouts

- A layout has a code unique in the Organisation, a source (a supplier, a brand, an earlier-POS Store report, a bank, or the Organisation's own template), a document type and the kinds it serves. Its content lives in versions (`PRD-IMP-003`).
- A layout version records the structure, never data:
  - the container format and sheet selector, by name, with names trimmed and spaces collapsed;
  - the header row or rows, or a positional layout for a sheet without one; the data start row; a leading-column offset as a hint only;
  - every column: its header name, its type, its accepted formats, and whether it is required, mapped or explicitly ignored;
  - fixed cells that hold document-level values, such as an invoice number in one cell above the table;
  - the structure rules of 6.6;
  - whether zero rows are present, and how control totals appear;
  - which columns form the document reference and the scope of its source identity (7.1);
  - the restricted field class of each column (section 11).
- A version is never edited. A change is a new version; each batch keeps the version it used (`PRD-IMP-003`, `PRD-MOD-010`).

### 6.2 Mappings

- A mapping fills one target's fields from one layout version. Its versions record, for each target field: the source column or fixed cell, or a set of them; the transform; and the mapping rules that apply to it (`PRD-IMP-003`).
- A set of columns becomes one value only through a named calculation, such as an invoice prefix joined to its number, or CGST plus SGST percentages summed into one rate; the value's origin is Calculated (section 5).
- Money becomes integer paise by exact decimal arithmetic (`PRD-MOD-014`). A spreadsheet number is a binary floating-point value; it is read as the shortest decimal that reproduces it. **Design choice.** A value with more decimals than paise is flagged, and it gets a paise value only from the named rounding rule that the mapping names for that column; until a rule is named it stays Unknown (`PRD-MOD-015`; class C-2 in 8.3). Which rule each money column uses is OPEN (GC6-13).
- A target field the mapping does not fill stays Unknown. Nothing gets a default (`PRD-MOD-015`).

### 6.3 Mapping rules

- A mapping rule turns one source word into one approved value for one attribute, in one scope: a layout, a supplier, a brand or the whole Organisation. The target is an identifier: a vocabulary value, brand, size, category or party of `merchandise`, a Site, Store or business unit of `organisation`, or a line class (6.8). The module that owns the target checks it through its handler (13.2). Rules are versioned with validity dates (`PRD-IMP-003`).
- Matching compares the word after trimming and collapsing spaces; whether case matters is part of the rule. The original word is always kept beside the value (`PRD-IMP-003`).
- Two rules in force for the same attribute, scope and word with different targets are refused when the second is confirmed. A layout-scope rule wins over any wider rule, since it belongs to one file structure. Rules of the supplier, brand and Organisation scopes that match one word with different targets make the word ambiguous: it is not mapped, and the row issue names the rules. **Design choice**, in the spirit of `PRD-MER-007` and the external-code rule of structure-and-masters 4.3.
- Source-to-Store maps are mapping rules: a bill-series prefix such as `DEO`, a `Store Name` value, a dealer-site tag, a file-name tag ([stores-and-codes.md](../../data-notes/stores-and-codes.md) 3.1 to 3.4). A file name or title is a claim shown to the reviewer; it maps a Store only through a confirmed rule.
- KDPS's seed lists ([item-master-vocabulary.md](../../data-notes/item-master-vocabulary.md) 1) enter as proposals through a create batch, never as approved values (structure-and-masters 4.2, `PRD-MER-013`).
- **As built** (`S1-F06-T03`): a rule's attribute is `<target>.<field>`, such as `merchandise.brandCode`; its target is the value that field takes, as the target's handler reads it (a brand's code), which the handler checks at proposal and again at confirmation. The rule's identity (attribute, scope, normalised word, whether case matters) is kept once; its versions carry the target and the dates (`[from, to)`). A mapping field maps through rules only where its mapping says `rules: true`. Staging reads the Confirmed versions in force on the business date, in the batch's scopes: its layout, the supplier or brand the preparer names at Start an import, and the Organisation. A word no rule matches stays Supplied as its source word, for the handler's reference check to block with suggestions; a word confirmed rules map to different targets is Unknown (`ambiguous-rules`). A batch already staged keeps its values when a rule is confirmed later: a rule, like a version, changes no staged batch.
- **A rule's versions** (S1-F06 review 2, 11 Oct 2026; code-house-rules 7.3): a rule's Confirmed versions never overlap, whatever their targets, as every effective-dated master's Approved versions never do; the exclusion constraint of 15.1 holds them apart, and the register marks the table `versions`. So a rule's target is corrected by a new version from a date: confirmed, it ends the version in force before it on its own start date (moving that version's end earlier, to today or later), and, where it is open-ended and a Confirmed version starts after it, it ends where that one starts. A version starting on the same date as a Confirmed one, or one whose own end runs into a later Confirmed version, is refused as `files-imports.rule-conflict`, since a start never moves. No version starts on a past date: Propose a mapping rule refuses one, and so does its confirmation once the date has passed (`files-imports.starts-in-past`; GC2-7, DEC-105). The rule's trigger admits only these changes (`files_imports.guard_version_change`). This replaces the earlier "different targets" form of the constraint, which let two Confirmed versions with one target overlap and left an open-ended version impossible to correct: code-house-rules 7.3 was right, and this section and 15.1 are amended to match it. "Two rules in force ... with different targets" above speaks of rules of different identities, such as a case-sensitive and a case-blind rule of one word; within one rule, versions follow each other.
- The `Color` tags `PREMIUM`, `MEDIUM`, `ECONOMY` and `ASSO.` stay source words. No rule writes them to colour until the product owner decides how the product treats them (OPEN, parked by the product owner; class E-1).

### 6.4 Proposal and confirmation

- A mapping rule is proposed, then confirmed by a different person from its proposer. An unconfirmed proposal changes no operational data (`PRD-IMP-008`, `POL-02.07`, `POL-02.08`).
- Baseline (DEC-112, GC6-4): each new or changed layout and mapping version is confirmed by a separate authorised person before it is published, reading "mapping rules" in `PRD-IMP-008` as covering them. Drafting and validation may come first. An unchanged confirmed version needs no confirmation for each file. The PRD already asks for "saved approved layouts" for earlier-POS and EBO imports (`PRD-LIF-013`, `PRD-EBO-001`). Who may confirm is KDPS's to name (KDPS Owner).
- States are those of a proposal: Proposed, Confirmed, Rejected (DM-4, DEC-105). A confirmation is a decision in `access` under the approval rule for mapping-rule confirmation (access-and-approvals section 8), and emits `files-imports.mapping-confirmed`.
- A staged batch may use a Proposed layout and mapping to show its preview. Publishing needs Confirmed versions. **Design choice.**
- **As built** (`S1-F06-T03`): Propose a layout version (a new layout with version 1, or the next version of one), Propose a mapping version (a new mapping of a layout version and target, or its next version) and Propose a mapping rule version each write the version Proposed and request approval in `access` under the rules `files_imports.layout.confirm`, `files_imports.mapping.confirm` and `files_imports.mapping_rule.confirm`, on the record types `files_imports.layout`, `files_imports.mapping` and `files_imports.mapping_rule` (create proposes, approve decides), independent, with no value limit and no decision-evidence class; the proposer is the one preparer, so `access` refuses their own decision (`access.self-preparation`), and each version table's `*_independent` constraint refuses it behind. A later proposal of the same layout, mapping or rule supersedes the open request of an earlier version (access-and-approvals 9.6); that version stays Proposed. The decision effect confirms or rejects the version once, under a lock on the version (on the rule's identity row for a rule), and confirming emits `files-imports.mapping-confirmed` (13.3). A mapping is checked when proposed: every field is one its target's handler has, every column one its layout version names and does not ignore, and no column of an encrypted class (section 11). A Rejected version never starts a batch (`files-imports.layout-version-rejected`).

### 6.5 Detecting a layout

- Detection compares the grid with each layout version's structure: the sheet, the header names at their row, the required columns, the column count and the distinctive names. A version is compatible only when every required column is found (`PRD-IMP-004`).
- A source hint (the supplier or brand the uploader names, or a word in the file name) narrows the candidates and orders them. It never selects a version that is not compatible (`PRD-IMP-004`).
- One compatible version: it is proposed, and the preparer accepts it for this file. Several: the preparer chooses. None: the preparer proposes a new layout version (6.4). **Design choice.**
- **As built** (`S1-F06-T03`): Detect a layout reads a stored file the preparer handed in and compares it with every layout version not Rejected: compatible when the sheet is there, every required column is at the header row, and no labelled header cell names a column the layout does not know (A-4); each incompatible version is listed with what it misses. A hint matches a version when its code or source is within the hint or the hint within them, case ignored; where any compatible version matches, the list narrows to those. Exactly one left is proposed. The answer also gives each sheet's first row, from which the screen fills a new version's columns. Start an import refuses an incompatible version as `files-imports.layout-not-matched`, naming each missing or unknown column.
- From the sample files, families F2 to F6 and the Peter England CSV can be told apart by their header names; F1, F9 and the headerless CSV need a layout per source ([pt-file-layouts.md](../../data-notes/pt-file-layouts.md) 3). Earlier-POS layouts differ by Store and report, so a layout is per Store and per report ([pos-exports.md](../../data-notes/pos-exports.md) 5.4). KDPS Owner question 57 asks whether the earlier POS can give one fixed daily export per Store instead.

### 6.6 Structure rules a layout can state

Each rule below is a field of the layout version, so the same file always reads the same way. The class codes are those of [data-quality-and-import-rules.md](../../data-notes/data-quality-and-import-rules.md); section 8 lists them all.

- **Headers.** The header row is recorded; a two-row header joins its rows into one name per column; a sheet with no header has a positional layout that a person confirms, and its first row is never taken as a header (A-2, A-5). Columns are found by name; an offset is only a hint (A-3).
- **Every column accounted for.** A column with no header text is mapped or explicitly ignored in the layout. A column the layout does not know makes the layout incompatible (A-4; `PRD-IMP-007`).
- **Every row read.** Hidden sheets, hidden rows and rows hidden by a filter are read like any other and shown to the reviewer (A-7). Only the sheets the layout names are imported; the others are listed with their row counts (A-8).
- **Row roles.** A row is data only when the layout's key columns are filled. Other rows are header, total, filler, note or ignored, and each is counted (A-10, G-1). A free-text note row is shown to the reviewer.
- **Control totals.** A total row is parsed as a control total and compared with the sum of the lines; it is never imported as a line (G-1, K-1; `PRD-IMP-013`).
- **Bill-level fields.** Where a report prints bill fields on a bill's first line only, a line belongs to the nearest bill header above it, inside the same file. A line with no header above it is refused with the correction needed; no date, bill number or tender is filled from neighbouring lines (H-1; `PRD-IMP-009`). In the repeat variant the date and bill number are read from each line ([pos-export-layouts.json](../../data-notes/pos-export-layouts.json): `bill_level_fields_on_first_line_only`, `bill_fields_repeated_on_every_line`). Two header lines for one bill number are reported (H-10).
- **Brand cuts.** A file that holds one brand's lines of whole bills is detected, by a filter on brand or by bill totals that do not add up; its bills are marked partial, and tenders are not reconciled against them (H-2).
- **Signs.** Each signed column states its convention; one value is never recomputed from another (H-6).
- **Zero rows.** The layout says whether zero-quantity rows are listed. A barcode missing from a file that lists only positive rows is "not listed", not zero (I-1). Whether "not listed" may be read as zero is OPEN (GC6-16).
- **Documents in one file.** Rows are grouped into documents by the document-reference columns. A file that holds several invoices or bills becomes several documents ([pt-file-layouts.md](../../data-notes/pt-file-layouts.md) 5). Rows for other customers, as in the Madura extract, stay in the stored original; whether they are staged at all is OPEN (GC6-12).

### 6.8 Earlier-POS sales lines: sales, returns and transfers

The earlier POS's daily sales report is a historical-reference import (4.1). Nothing in it moves stock (`PRD-LIF-014`) or makes a sale or a tax invoice (`PRD-LIF-016`). Its lines still need a class so that comparison reports do not count a transfer as a sale.

- Each line gets a line class: sale, return, transfer keyed as a sale, or unclassified.
- A negative-quantity line is a return line of the same bill. No link to an original bill is inferred, because no field gives it (H-5; `PRD-IMP-009`).
- A transfer keyed as a sale is recognised only by a confirmed mapping rule with the line class as its target: a reason text such as `Stock Transferr` or `STOCK TRANSFER TO …`, or a bill-series pattern such as the zero-tender `S-` series ([transfers.md](../../data-notes/transfers.md) 3.3; [store-close-cash-and-bank.md](../../data-notes/store-close-cash-and-bank.md) 2). Which texts and series these are is KDPS's answer: OPEN (GC6-14).
- A line so classed is reported apart: never in sales totals, never a transfer document of the app, and no destination is inferred from free text. Any tender recorded on it is shown as reported. The PRD keeps transfers and sales distinct (`PRD-TRF-003`).
- A zero-tender line that no rule classifies is flagged and counted apart. It is never guessed.
- Carry bags and free gifts stay sales lines, and reports can leave them out by item; how they are classed in the masters is OPEN (KDPS Owner, Accounts; E-7, H-7).
- The Store of each bill comes from a confirmed source-to-Store rule on its bill-series prefix (6.3). A bill whose series maps to no Store blocks its document.

## 7. Duplicates, conflicts and corrections

### 7.1 Source identity

- Each document has a source identity: the target, a scope key and the document reference. The layout names the reference columns or cells; the handler names the scope (13.2). **Design choice.**

| Source | Scope | Document reference |
| --- | --- | --- |
| Earlier-POS bill | Store, from the confirmed series rule | Series as printed and bill number (H-10) |
| Earlier-POS SOH or daily report file | Store and report kind | Business date or date range |
| Supplier PT file (stage 2) | Supplier party | Invoice number; invoice numbers repeat across suppliers ([prd-fit.md](../../data-notes/prd-fit.md) 2.19) |
| Master create or update | Target record type | Business code of the record |
| Opening balance | Business unit and opening kind | The Store's switch record |

- A document with no reference cannot be published as a transaction or opening-balance document until a person enters the reference from evidence, with the origin Entered by a person (section 5). Six of the sample PT files have no invoice number ([pt-file-layouts.md](../../data-notes/pt-file-layouts.md) 4).
- The source identity is the idempotency key of publishing (module-map 6.2 flow B; stock-ledger 10.1; `PRD-INT-002`).

### 7.2 Same file, same document, changed document

- **Same file.** A file whose content hash is already stored is linked to the stored copy, and the earlier batches that read it are shown. It starts a new batch for the same target and layout only if every earlier such batch Failed; one workbook may still feed two batches, such as its sales sheet and its stock sheet. **Design choice.**
- **Same document, same content.** A document whose source identity and content were already published is a duplicate. It has no effect; the outcome counts its quantities and values as duplicate (`PRD-IMP-011`, `PRD-IMP-013`).
- **Same identity, different content.** A conflict. It is refused, unless the handler supports a governed revision and the reviewer chooses one (7.3) (`PRD-IMP-011`).
- **Checked three times.** At the start, for the document reference the uploader claims: a published source identity is refused there unless the batch is a governed revision of it (13.1). At validation, for each document the file holds; one already published with the same content is counted as a duplicate. And again under the lock at publishing. A unique index on the source identity of published documents is the last guard, so two publishes at once give one effect (`PRD-INT-002`, `PRD-INT-005`; domain-model invariant 20).
- **Overlapping exports.** Bills that appear in an earlier and a later export are duplicates when their content agrees. A bill present in one export and absent from a later export of the same period is listed for review and never dropped silently (H-10).
- **Stale copies.** A file whose content equals the last accepted file of the same layout and Store under a new period is flagged as a possible stale copy (I-4).
- **Two sheets with the same keys.** Only the sheet the layout names is imported; the other is compared and the differences shown. An import never overwrites approved data silently (I-2; `POL-03.02`).
- **Retries.** An adapter that sends the same request again gets the first result (`PRD-INT-002`).

### 7.3 Corrections and governed revisions

- A published document is never edited (`PRD-MOD-011`). A correction is a new batch whose document names the one it revises.
- A governed revision publishes once: the handler reverses the earlier document's effects and posts the new ones in one transaction, as stock-ledger 10.1 says (`PRD-IMP-011`, `PRD-ACP-012`). Each handler declares whether it supports revisions and what reversing means for its records.
- The original stored file, its staged rows, its outcome and every downstream link stay, and the revision links to them (`PRD-IMP-013`).
- For a master, a correction is simply a new version (structure-and-masters 2.2). For a historical-reference document, the revision replaces the reference set as its current version and keeps the earlier one. **Design choice.**

### 7.4 Reconciling an import

- Every outcome holds, per document and for the batch: rows read; rows ignored as header, total, filler or note; quantities and values accepted, rejected, pending and duplicate; control totals reported by the file, summed from the lines, and accepted (`PRD-IMP-013`).
- The counts close: rows read equal rows ignored plus rows accepted, rejected, pending and duplicate. A batch whose counts do not close cannot be published. **Design choice.**
- A total the source reports is kept apart from what the app verified (`PRD-EBO-004`).
- An outcome is written for every publish attempt, including one that failed (`PRD-IMP-012`).

**As built** (`S1-F06-T04`; migration 0059):

- **Source identity** (7.1): each document keeps its target and the scope key its handler names, set at the start, with its reference. The stage 1 handlers name a master's record type: `merchandise.style` for products, `organisation.store` for Stores. A published document keeps the SHA-256 of its content: its rows' values for the handler's fields, whatever their origin (a person's entry standing for the staged value), Unknown kept apart from an empty text, in no row order. **Design choice.** A document published before 0059 has no content hash, so another with its identity is a conflict, never a duplicate (`PRD-MOD-015`). The partial unique index `import_document_published_identity` holds one published document per identity that no revision replaced.
- **Checked three times** (7.2): at the start, a file read by a batch for the same target and layout (by layout, any version) that has not Failed is refused (`files-imports.file-already-imported`, naming the earlier batches the person may see), and so is a document reference the uploader claimed at the hand-in that is already published (`files-imports.document-already-published`), unless the batch is an update of a handler that supports revisions; both are checked through narrowly authorised functions that see every scope (`files_imports.file_in_open_batch`, `files_imports.published_document`; code-house-rules 6.2), since an identity is one across the Organisation. Two Starts of the same file at once queue: each locks the stored file at step 1 and checks again under the lock that no open batch reads it, so the second is refused (`files-imports.file-already-imported`; RR-503 closed, S1-F06 review 2). The refusal of a published reference names the published document only to a person who may view its batch; to anyone else it names nothing, since the document is found whatever their scope sees (section 11). At validation each document is checked against the published one: a duplicate is a Note of the class `duplicate` and is neither previewed nor checked, a conflict is Blocking of the class `conflict`, and a governed revision a Note of the class `revision` (**Design choice:** these three classes stand beside the 60 of 8.3). A batch whose every document is excluded or a duplicate stays Staged, to be withdrawn. Under the lock at publishing the check runs again, and the document is marked Published, with its content hash, before its handler writes anything, under a savepoint: a publish that loses the race on the unique index rolls back to it and is answered as a duplicate, or as a conflict (`files-imports.document-conflict`), so two publishes at once give one effect (`PRD-INT-005`; 17 test 15, on separate connections).
- **Governed revisions** (7.3): the preparer chooses one by starting an update batch; the reviewer reviews it as the batch. Both stage 1 handlers declare revisions as `new-version`: an update document publishes the record's next version starting today through the owner's Maintain operation (Prepare a Store version; Prepare a SKU version for each SKU of the style, with the row's stock unit and purpose), and, in the same transaction, the published document it revises names it as `replaced_by_document_id`, once; the revision names it as `revises_document_id`. The original file, rows, outcome and links stay. A handler that declares `none` gets a conflict instead.
- **Outcomes**: each attempt keeps the batch version, rows read (the reader's own count of the imported sheet) and ignored, rows accepted, rejected (refused by the handler, a conflict, or excluded), pending and duplicate, each document's result with the records it made or its refusal, the sums of the measures the handler names by result (stage 1 handlers name none; null is Unknown), and the control totals of the last validation as reported, summed and accepted. Every row the reader read is staged, the rows above the data the layout reads as `ignored` (6.6), so the counts close unless a row was lost: Submit and Publish refuse a batch whose staged rows differ from the rows read (`files-imports.counts-do-not-close`). **Design choice.** An attempt that leaves a document refused or in conflict is `failed`, the others published and the batch still Validated (3.2); when every document chosen has posted or is a duplicate it is `published` and the batch Published. Its answer is the outcome, not a refusal.

## 8. The validation report

### 8.1 What it holds

One report per batch, split by document and by Store where the documents name Stores ([data-quality-and-import-rules.md](../../data-notes/data-quality-and-import-rules.md) 9):

- the real format found, the sheets read and ignored with their row counts, the header row and offset, and the choice recorded for each unlabelled column;
- hidden sheets, hidden rows and active filters;
- rows read, ignored, refused and flagged, each with its reason;
- control totals found against the sums of the lines;
- dates outside the file's period, dates that contradict their order, and a period claimed in a title or file name against the data;
- barcode classes, rounded barcodes, and barcodes with two prices in one snapshot;
- source words with no confirmed rule, per column;
- bills with no header, with two headers, partial bills, header totals against lines, zero-tender bills;
- bills seen in an earlier file and missing now, overlapping bills, duplicates and conflicts of identity;
- accepted, rejected, pending and duplicate quantities and values (`PRD-IMP-013`);
- the fields masked or left out (section 11).

### 8.2 Row issues and severities

- A row issue holds: its class (8.3), its severity, its place (file, sheet, document, row, column), the original value, what is wrong, the correction needed, and the rule it applies (`PRD-IMP-007`).
- **Blocking**: the row, or the document it belongs to, cannot be published until corrected. **Warning**: publishable once the person who submits or approves the batch marks it seen; marking is recorded and may cover all issues of one class in one action. **Note**: information. **Design choice**, including the severity each class gets below.
- A required field that is missing, unreadable or of the wrong type is Blocking. Unknown is never read as zero (`PRD-MOD-015`).
- A correction is made in the source file and the file uploaded again, or entered in the staged row by a person (section 5). The original cell stays.

- **As built** (`S1-F06-T03`): Validate works out the report of the batch's current version and keeps it: its row issues (`row_issue`, with the class, severity, place, original value, the code of what is wrong, the code of the correction needed, the rule applied as text, and the class of the column the original comes from, for masking) and its control totals (`control_total`). The checks built: A-4 (a column holding data with no header text, Blocking), A-7 (a hidden data row, or the imported sheet hidden, Warning), A-8 (each other sheet with its row count, Note), A-10 (a note or filler row, Note), A-11, C-1 and J-1 (Blocking where the field is required, else Warning), C-2 (Warning), K-1 (a control total that differs from the sum of the lines or cannot be read, Warning), `required` (a required field Unknown, Blocking), `rule` (confirmed rules that disagree, Warning), `calculation` (a calculated value beside a supplied one that differs, Warning) and `handler` (what the handler's preview finds, Blocking). The batch is Validated when no Blocking issue is found and a document is left to publish. A Warning is marked seen, by issue or every one of a class, while the batch is Validated and not yet submitted, by the person who submits it: the mark names who made it, a later mark by another person replaces it (each mark is audited), and Submit for review counts a Warning seen only when the submitter marked it, so a mark by anyone else with edit does not count (product owner, 11 Oct 2026). Submit refuses Blocking issues and Warnings the submitter has not marked seen. Marking by the approver of a batch whose handler requires an approval is not built: the approver decides on the report the submitter marked. An excluded document is neither previewed nor checked. The report split by Store waits for documents that name Stores (stage 2). **Design choice:** the classes `required`, `rule`, `calculation` and `handler` stand beside the 60 of 8.3, which name the file's problems, not these.

## 9. Format readers

### 9.1 The neutral grid

Every reader produces the same grid, so detection, mapping and validation never depend on the format. **Design choice.**

- Sheets with their names, order and hidden state; merged ranges; active filters and the rows they hide; hidden rows and columns.
- Cells with their raw value, cell type (text, number, date, boolean, error, empty), displayed text where the format gives it, and, for a formula, its cached value only (A-10).
- Error values such as `#N/A` or `#REF!` as errors, never as text or zero (J-1).
- Notes for anything the reader skipped or could not read, cell by cell (A-11). One bad cell never stops the file.
- **As built for XLSX** (`S1-F06-T01`; ExcelJS, code-house-rules 10.6): every sheet in workbook order with its state (visible, hidden, very hidden); every row that holds a cell, with its hidden mark; each cell with its column, reference, type, raw value and text. A number is kept as the reader gives it and written as its shortest decimal; a date as its ISO instant; a formula by its cached value only, and one with no cached value is empty with the note `formula-without-cached-value`; a rich text by its text; a hyperlink by its text only, its target never kept, so it stays inert (GC6-17); an error by its code. A cell the reader cannot read is empty with the note `cell-not-read`. A merged range's followers are not repeated: its first cell holds the value. Merged ranges and filters as records arrive with the checks that read them (`S1-F06-T03`, `S2-F13`). The notes are kept on the batch.

### 9.3 Safety at intake

Evidence files (PDF, JPEG, PNG) get their type check, active-content refusal and size limits with the first upload ticket, `S1-F06-T05`, before workbook intake exists (product owner, 6 Oct 2026, `DEC-117`).

- Intake refuses, before anything is stored: a type not allowed; a file over a cap; a container that expands past its cap; content that holds macros, active scripts, embedded objects or unapproved links; and a workbook that depends on data in another workbook (module-map 4.7; `PRD-SEC-011`; DEC-112, GC6-3). That refusal explains the problem and asks for a self-contained copy: no dependency is stripped silently and no stale linked value is trusted (A-9).
- The dependency rule alone refuses no ordinary hyperlink and no reference inside the workbook, and it approves no external link (DEC-112). An ordinary external hyperlink in a sheet, such as a link to a shared drive, is not refused: it is kept as inert text, never followed, fetched or rendered as a live link, and the file is accepted (product owner, 6 Oct 2026; GC6-17, RR-201; DEC-116). The cross-workbook dependency refusal (GC6-3) is unchanged. A reference inside the workbook is read. No link in an imported file is ever followed or fetched (`PRD-SEC-011`).
- The caps at intake cover the uploaded and expanded size, rows, parser memory and processing time. The builders choose, document and tune them within these safeguards and test them with representative synthetic files; excess is refused clearly and never truncated silently; a cap that blocks a required workflow is reported to the product owner (DEC-112, GC6-5). No number is fixed here. Product rules, acceptance criteria and permission for live data stay the product owner's, and real data also needs KDPS's agreement first (D-4).
- A refusal names its reason. Logs carry the file's hash and size, never its content (`PRD-SEC-014`).
- **As built for evidence files** (`S1-F06-T05`; `DEC-117`; builders' choices, documented as 9.3 asks, tuned by measurement, none a KDPS value):
  - The type is found from the first bytes: `%PDF-` at offset 0, `FF D8 FF` for JPEG, the eight-byte PNG signature. Anything else is `files-imports.type-not-allowed`, whatever the name or the declared type says.
  - **The size limit is 10 MiB (10,485,760 bytes)** for each of the three formats, checked on the decoded bytes. A file of exactly the limit is accepted; one byte over is `files-imports.file-too-large`, naming the limit, and nothing is stored or truncated. The store-file request body may hold up to twice the base64 form of the limit plus 8 KiB, so a file over the limit by an ordinary amount reaches the check that names the limit; a body beyond that is refused by the body parser as an invalid request without the limit named. Only a request whose cookie names an open session is read up to that larger size: before the body is read, a read-only probe (no activity moves, nothing ends) checks that the session exists and is In force or Locked, and the body stays unread until it answers; Authenticate still runs in full on the route afterwards. Any other request, including a cookie that names no session, keeps the ordinary body limit and is refused as an invalid request when over it, so someone not signed in cannot make the server hold a full-size body.
  - **Active content in a PDF** is refused as `files-imports.active-content`, naming the first found of `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile`, `/EmbeddedFiles`, `/RichMedia`, `/SubmitForm`, `/ImportData`, `/GoToR` and `/GoToE`, matched as whole names after undoing `#xx` name escapes, in the file and inside its zlib-compressed streams (so inside object streams). Each stream is inflated up to 32 MiB and all of them up to 64 MiB together; a PDF that goes past that, or carries `/Encrypt`, whose streams cannot be read, is refused as `files-imports.pdf-not-inspectable` rather than trusted. This is a content check, not a PDF parser. **Hardened** (`S1-F06-T02`; RR-434): a stream behind a filter the check does not open is refused as `files-imports.pdf-not-inspectable` rather than trusted. The filters looked behind are zlib (`FlateDecode`, `Fl`), which is inflated, and the image filters (`DCTDecode`, `DCT`, `JPXDecode`, `CCITTFaxDecode`, `CCF`, `JBIG2Decode`), whose streams hold image data and never PDF objects; any other (LZW, ASCII85, ASCIIHex, run-length, `Crypt`), alone or in a chain, refuses the file. The evidence size limit stays the 10 MiB above; the workbook caps below are for import files.
  - A JPEG or PNG is checked for its type and size only; neither carries active content a reader runs here.
- **As built for import files** (`S1-F06-T01`): an import upload has its own route, Store a file for an import, which takes the same request as Store a file and stores the same way (encrypted, hashed before encryption, keyed by Organisation, written once). Its type is found from the content: a zip container (local header signature at offset 0) whose central directory, read without inflating anything, names the workbook part `xl/workbook.xml`, which is the part ExcelJS opens. Anything else, PDF, JPEG and PNG included, and a zip container without that part (another office document, or XLSB with its binary workbook part), is `files-imports.type-not-allowed` before anything is stored. The workbook's own refusals and caps follow (`S1-F06-T02`).
- **As built for workbooks** (`S1-F06-T02`; `PRD-SEC-011`; DEC-112 GC6-3, GC6-5; DEC-116 GC6-17). After the type, Store a file for an import checks, on the bytes in memory and before anything is stored, in this order; the first failure is the reason, and nothing is stored, staged or truncated:
  1. **Uploaded size**: over the cap is `files-imports.over-intake-cap` naming `uploaded-size` and the limit in bytes. The import upload shares the store-file body limit, so the cap may be at most 10 MiB (`IMPORT_UPLOAD_CEILING_BYTES`), which lets a file over it by an ordinary amount reach this check; a higher cap stops the service at start.
  2. In a worker thread of its own (3.3), whose V8 heap (old generation) is limited to the parser-memory cap and which is ended at the processing-time cap; a worker that runs out of heap is `files-imports.over-intake-cap` naming `parser-memory` and the limit in MiB, one ended for time names `processing-time` and the limit in milliseconds:
     - **The container.** The zip's central directory is read; an entry encrypted inside the container, another compression method than stored or deflate, a zip64 container (never needed within the caps) or a broken directory is `files-imports.file-unreadable`. The sizes the entries declare are added up before anything is inflated, and a total over the expanded-size cap is `files-imports.over-intake-cap` naming `expanded-size` and the limit in bytes. Each entry is then inflated never past what it declares and checked against its size and checksum: a mismatch (a damaged file, or a decompression bomb hiding behind a small claim) or an entry that does not inflate is `files-imports.file-unreadable`. The parts are not kept, except the content types, the relationship parts and custom XML parts, which the checks read, each found by its name whatever its case. **As built with the S1-F06 review:** those parts are read by a minimal XML tokenizer in the safety check (not a validating parser, and no dependency), never by pattern matching: it reads a part as UTF-16 where its byte order mark or first character says so (a Power Query part is written so), otherwise UTF-8; it skips the declaration, processing instructions, comments and CDATA sections, so no tag inside them counts; it reads each quoted attribute value whole, so a `>` inside one ends nothing, and resolves its character and predefined references, so an encoded word is read as itself; and it refuses a document type declaration, so no entity of the file's own is expanded. A kept part that is not well formed (an end tag that closes no open element, an unclosed tag, comment or section, an undefined reference, an attribute twice) is `files-imports.file-unreadable` naming `part-not-well-formed`, rather than read in part. A relationship's target is outside the file when its `TargetMode` is anything but `Internal`.
     - **Active content**, `files-imports.workbook-active-content`, naming `macros` (a `vbaProject.bin` part, a macro or dialog sheet, a macro-enabled content type or a VBA relationship), `active-controls` (ActiveX parts) or `embedded-objects` (any part under `xl/embeddings/`).
     - **A dependency on another workbook** (A-9, GC6-3): an external link part or relationship is `files-imports.workbook-depends-on-another`, naming `self-contained-copy`; nothing is stripped and no cached linked value is trusted.
     - **Unapproved links**: any relationship whose target is outside the file, except an ordinary hyperlink (GC6-17), such as an externally linked picture or object, is `files-imports.workbook-unapproved-link` naming the relationship's type; so is a data connection (`xl/connections.xml`, query tables, or a Power Query part), named `data-connection`. **Design choice:** every external relationship but a hyperlink counts as an unapproved link, since no external link is approved (DEC-112). A hyperlink is kept as inert text (9.1). A reference inside the workbook, such as a formula naming another cell, is read by its cached value (A-10).
     - **The read**: ExcelJS reads the workbook into the grid (9.1), counting the rows that hold a cell, every sheet together; more than the row cap is `files-imports.over-intake-cap` naming `rows` and the limit, never a part of the file. A workbook ExcelJS cannot open is `files-imports.file-unreadable`.
  3. On `kdps-test`, the customer-contact check of section 11.

  A damaged or unreadable file's refusal names the reader's error as a word (`reader-error`: such as `entry-checksum-mismatch`, `entry-size-mismatch`, `entry-not-inflated`, `not-a-zip`, `workbook-not-read`), never the reader's message, which may quote the file (`PRD-SEC-014`). Start an import and Detect a layout read the stored file again the same way under the caps in force, so a file stored under looser caps is refused there naming the cap.
- **The caps** (`S1-F06-T02`; DEC-112 GC6-5; RR-036; code-house-rules 12.14 "Technical settings"). Each is an environment variable of `app`, read at start through one schema; a missing, malformed or out-of-range one stops the service at start, naming the variable and never its value, and nothing falls back to a value in code ([deployment.md](deployment.md) section 9). They are technical settings the builders choose, never KDPS values. **The values for local work, tests and `dev`** are SYNTHETIC: development and test values only, never KDPS values and never a default for another environment; the product owner accepted them for local work, tests and `dev` on 10 Oct 2026. - **S1-F06 review 2** (11 Oct 2026; `PRD-SEC-011`, `PRD-SEC-014`): a container holding two entries of one name, whatever its case (part names compare so), is refused as unreadable (`entry-name-twice`), since a reader keeps one of the two and the part checked could differ from the part read; a Power Query part is known by its `DataMashup` element, read by the tokenizer, never by the word appearing in a value or a comment; and the reader's worker writes to no stream of the server: both its standard output and its standard error are piped and drained, so nothing it prints reaches the log (code-house-rules 12.11).

Until Accounts and the CA answer, no value in a KDPS file is taken as evidence ([prd-fit.md](../../data-notes/prd-fit.md) 6).
- Piece IDs are never imported. At the switch count every piece of a piece-tracked profile with no piece ID is labelled and every piece ID verified; piece rules start from that count (`PRD-LIF-025`, `PRD-MER-017`).
- Billed-retained items carried across the switch are a separate section of the opening batch with their earlier-POS bill reference. They are not opening stock (`PRD-LIF-028`, `POL-14.04`, DEC-090).
- When a season is established later, the opening rows and every snapshot taken from them stay as they were; the change is a new style version (`PRD-LIF-007`; structure-and-masters 2.2).

### 10.3 Reconciling opening stock

The reconciliation tools `POL-14.07` asks for are comparison runs (section 2), built in stage 1:

| Run | Left | Right | Key |
| --- | --- | --- | --- |
| Manifest against last SOH | The staged manifest | The earlier POS's last SOH, a historical-reference batch | Barcode, then SKU |
| Count against manifest | The switch count, from the stock module's read model | The staged manifest | SKU and location |
| Count against last SOH | The switch count | The earlier POS's last SOH | Barcode, then SKU |

- Every difference is listed and reported (`PRD-LIF-027`). None is closed by editing a number ([phases.md](../../phases.md), "Testing and switch-over"). Variances are authorised as `PRD-LIF-004` requires; who authorises them, and how, is the stage 4 switch design's, with KDPS Owner question 28.
- A counted row with no valuation evidence is not opening stock. It is held as excess, with owner, coverage and cost Unknown, until the evidence and an opening PT arrive (stock-ledger section 9; `PRD-STK-014`).
- A comparison run keeps both sides' batch versions and its result, and never changes either side. **Design choice.**

### 10.4 Opening dues, advances and deposits

Each is its own layout and its own opening kind, imported separately (`PRD-LIF-009`). The fields below are **Proposed**, for Accounts and the CA to confirm (GC6-10):

| Opening kind | One row is |
| --- | --- |
| Supplier dues | One open supplier document: party, legal entity and book, document reference and date, original and open amounts, due date |
| Customer dues | One open customer amount: customer, document reference and date, open amount, due date |
| Advances given and received | One advance: party, purpose, amount, evidence |
| Deposits given and received | One deposit: party, agreement reference, amount, evidence |
| Outstanding commercial stock | Named by `PRD-LIF-009`; its fields are OPEN (GC6-10) |

- Every row carries the legal entity and book through a business unit's mapping (`PRD-ORG-005`), amounts in paise, and the cutoff date. Deposits and advances stay apart from expenses (`PRD-PAY-008`).
- Accounts verifies the values against the last closed books, with a reconciliation through the cutoff that prevents omissions and double counting (`POL-14.03`). A comparison run (section 2) compares each kind's totals per party and per account with the closed-books balances. The form of those balances, such as a Tally export, is OPEN (GC6-10).
- A row that is also open as a live document in the app is a double count and is Blocking (`PRD-LIF-011`).
- KDPS's data holds no advance or deposit, two dues sales, and supplier balances in two ledger PDFs, a tracker summary and Tally that disagree ([prd-fit.md](../../data-notes/prd-fit.md) 2.17). Opening dues come from the last closed books, not from these sheets.
- Financial opening balances post at the switch under a `site-lifecycle` posting event kind (books-and-posting 7.3), declared by the stage 4 design. Tally remains KDPS's official book (`POL-11.01`). Where the open items sit between the stage 4 switch and the stage 5 payables and receivables is GC6-11.
- Customer names on customer dues are personal data (section 11).

### 10.5 What opening data never does

- Opening stock creates no supplier delivery, booking, invoice, purchase liability or automatic journal (`PRD-LIF-008`; books-and-posting 7.2).
- Only the switch count creates stock. A manifest, an SOH or an `Audit Diff` line never does (`PRD-REC-008`; I-5).
- Opening balances, historical reference and live corrections stay distinct (`PRD-LIF-011`; 4.1).
- A later correction cannot rewrite past bills or labels (`PRD-ACP-014`).

### 10.6 Large openings

A Store's opening holds tens of thousands of pieces: 13,354 at Deoghar, 27,695 at Hazaribagh and 21,771 at Banka in KDPS's data ([prd-fit.md](../../data-notes/prd-fit.md) 2.17). Its posting is a large document under stock-ledger 10.6.

- **Before any lock:** reading, staging, validation, identity resolution, matching to the count, and the inflow values from the valuation evidence. `files-imports` does this and hands the switch posting a validated set.
- **The posting:** a queued job, one at a time per accounting book. The approval click records the decision and a request to post naming the batch version; the job locks, rechecks, writes the opening count movements and records the decision's use, all in one transaction (access-and-approvals 9.8, DEC-097; `PRD-INT-004`). One document posts whole or not at all (`PRD-IMP-012`).
- **A failed job** posts nothing and leaves the decision unused; the batch shows the failure (3.2).
- **Measured** with stock-ledger 10.6: a full Site opening while counters sell at the reference workload (`PRD-PRF-001`, `PRD-PRF-003`).

## 11. Restricted and personal data

- Each layout column carries a restricted field class where it holds one: salary, identity documents, bank details, customer contact, cost and margin (`PRD-ACS-008`), and employee photos, location evidence and payroll data (`PRD-SEC-010`), the classes of access-and-approvals section 6. In previews, validation reports, read models and exports, a value of a class the reader's assignment does not grant is masked or left out (access-and-approvals section 6). Logs, errors and live-update events never carry it (`PRD-SEC-006`, `PRD-SEC-014`).
- A column of an encrypted class (bank details, identity documents, salary and payroll data) is left out of staging unless the mapping fills a target that holds that class, such as a party's bank details, which then wait for independent approval (structure-and-masters 5.1). A staged value of that class is encrypted like the master's (access-and-approvals section 6). **Design choice.**
- The stored original holds every column (`PRD-IMP-002`). Every stored file is encrypted by the application with the Organisation's key before it reaches file storage, so the bucket and its backups hold only encrypted files, as for encrypted fields in PostgreSQL (`PRD-SEC-006`, `POL-18.02`; access-and-approvals section 6). **Design choice:** all files, because a file's classes are known only after its layout is confirmed. The content hash is taken before encryption. A file is therefore served through the app, which decrypts it for an authorised reader, never by a link straight to the bucket. It is served only to a reader whose assignment covers the batch's scope and every restricted class its layout marks; a file waiting for its layout counts as holding every class until the layout is confirmed. A file kept only as evidence, such as a photograph or PDF attached to a record, has no layout: it is served to a reader authorised for the record it is attached to, and carries the restricted classes the attaching module declares for that kind of attachment. **As built for evidence** (`S1-F06-T05`): a file is read through its attachment, never by the stored file. The read finds the attachment under row-level security, which shows it only where an effective grant on the attached record's own type covers its scope facts, so a file outside the reader's scope answers `files-imports.attachment-not-found`, the same as one that does not exist; then Authorise checks view on the attached record's type with its facts and a grant of every restricted class the attachment carries (7.1 step 3), and a missing class answers `access.not-authorised` naming it. **As built for the owning module's readers** (S1-F08 review; product owner, 9 Oct 2026, RR-452; module-map section 3, rule 6): a module whose records admit people without any grant on their type registers a reader for those types with `files-imports` at start (`AttachedRecordReaders`, `mayRead`), as `exceptions` does for `exceptions.exception`, whose owner, holder of the owning role and escalation recipient act with no grant (access-and-approvals 12.4). The read first finds the attached record's type and identifier through `files_imports.attached_record`, a narrowly authorised internal function that answers those two only (code-house-rules 6.2), and asks that record's reader whether the actor may read it. When it answers yes, `files-imports` names the record for the rest of the transaction in `aos.admitted_record`, and the attachment's policy admits that record's rows beside those a grant covers (migration 0039); Authorise then checks the restricted classes alone, one assignment covering the record's facts and granting every class (`authoriseFieldClasses`), so a class still needs its permission. Attach asks the same reader, so whoever the owning module admits may also attach to the record. The download asks the reader and checks the classes again in its own transaction, in place of rechecking a grant on the type. Where no reader is registered, or it answers no, the read is as above. The route is of the access kind `attached-record`: the guard Authenticates only and the command authorises, since the record type is known only from the attachment. An attachment with no restricted class is read with a `GET`. One that carries a class is an export (code-house-rules 12.1): the `GET` refuses it and the download command, a `POST` under an idempotency key, serves it, for a restricted file with a fresh authenticator code (below), after writing one `sensitive-access` record for each class in its own transaction, rechecking the authority under the locks; its answer is never kept, so an identical replay is refused as not repeatable (for a restricted file the replay carries a used code, so it is refused as a refused code first). The object is fetched, decrypted and checked against its hash before that transaction (code-house-rules 8.3) and given only after it commits. The file travels as base64 in the JSON body of the answer and of the store request, because the route table carries JSON only. **The download is a protected action** (`S1-F06-T06`; product owner, 8 Oct 2026, RR-432; `PRD-SEC-001`; access-and-approvals 3.3). The body of the download command takes `totpCode`, a secret field like the others, and a file that carries a restricted class is served only with a fresh authenticator code, checked as every protected action checks one (access-and-approvals `checkFreshCode`: the person's confirmed authenticator, a step later than any it has given before). The code is checked first, in the authorising read, so a missing, wrong or already used code is refused as `access.authenticator-code-refused` (or `access.enrolment-not-started` for a person with no authenticator) before the object is fetched; it is checked again and taken in the command's own transaction, after the authority is rechecked and before any access record, so a code used by another request in between is refused and no record is written. How long a code stays fresh is OPEN (GC3-6; KDPS Owner): no duration is chosen, so every restricted download asks anew. A file with no restricted class is read, or downloaded, without a code. A refused download serves nothing and writes no access record. **The receipt's name and reference are encrypted** (`S1-F06-T06`; RR-433; `PRD-SEC-006`): the receipt's original file name and claimed document reference are encrypted by the application with the Organisation's key, under their own subkey purpose and bound to the receipt and the field, before the receipt row is written, and decrypted only when a reader authorised as above is served the file; the answer then carries one receipt, the one the attachment was made from, with the name and reference in the clear (null reference: none claimed). It never carries another receipt of the same bytes, which may come from another scope: the attaching module names the receipt it got back from Store a file, and the attachment links that receipt, which must be a receipt of the stored file attached. Logs, errors and audit records never carry them. Two kinds of sensitive access in [numbering-and-audit.md](numbering-and-audit.md) 5.1 apply to stored files, and each writes an access record. Downloading a file that holds any restricted class is an export that includes a restricted field. Showing the columns of an encrypted class on screen is showing an encrypted field unmasked. **Design choice**, including reading a download as an export. **Evidence on exceptions and decisions** (`S1-F08-T03`): `exceptions` declares the classes per exception type, and `access` per approval rule, both in code with no default; as built none declares any (RR-453). Their attachments and who reads them are in access-and-approvals 9.5 and 12.4.
- **As built for import files** (`S1-F06-T01`; `PRD-SEC-005`): Start an import attaches the stored file to its batch, record type `files_imports.import_batch`, as the evidence kind `import-original`, from the receipt the batch was started with and with the batch's scope facts; the attachment carries the classes the batch holds, which are every class while the batch's layout version is not Confirmed, and once it is Confirmed the classes its columns declare. So an import file is read through Read a file of `S1-F06-T05`: only by a reader whose grant on `files_imports.import_batch` covers the batch's scope, and, since it carries a class, only by the download command with a fresh authenticator code, each class recorded as an export. The batch keeps those classes too, and reading the batch, which shows its staged rows and so the file's cells, authorises view on `files_imports.import_batch` with the batch's facts and every class it holds. **Design choice:** the rows count as holding what their file holds. Masking a column of a class the reader lacks, and leaving encrypted classes out of staging, are built with `S1-F06-T03` (below). A batch is started only on a file the starting person handed in, under the receipt named, so nobody stages another person's upload (confirmed by the product owner, 10 Oct 2026).
- **As built: masking and encrypted columns** (`S1-F06-T03`; `PRD-ACS-008`, `PRD-SEC-005`, `PRD-SEC-006`): reading a batch needs view on it with its facts, no longer every class. The classes the batch holds that the reader's assignment does not grant (`restrictFields`) are masked: while the batch's layout version is not Confirmed, every cell and value of every row is masked, the document reference too, and the preview is not shown; once it is Confirmed, the cells of the columns of a masked class, the values read from them and the original values of their issues and control totals. The read names the masked classes. A column of an encrypted class (bank details, identity documents, salary and payroll data) is left out of staging: its cells are not kept in the staged row. No stage 1 handler has a field that holds such a class, so a mapping that reads one is refused (`files-imports.mapping-encrypted-column`); encrypting a staged value of one arrives with the first handler that has such a target (parties' bank details).
- **As built: masking what is worked out from a masked column** (S1-F06 review 2; `PRD-ACS-008`): a value calculated beside a supplied one counts as read from the columns its calculation reads, so a calculation over a masked column is masked with it, and so is an issue of it; a control total of a masked column is masked in the report (its sums null, naming the class), and its K-1 issue's original value and sums with it; an issue's calculated value is masked as its original is. An outcome's control totals of a masked column and its measures of a masked field are masked in the batch's read and in the import outcomes report, naming the class, and every one while the layout version is not Confirmed (7.4, 14).
- **On the test setup.** Until KDPS answers question 37, imports keep no customer name or phone number (DEC-052; [deployment.md](deployment.md) section 9). A file whose layout holds such a column cannot then be stored without breaking either that rule or `PRD-IMP-002`. Baseline (DEC-112, GC6-6): on `kdps-test`, intake refuses a file with customer-contact columns before storing it, even when they hold synthetic contacts. The refusal says why and offers a clean upload again; intake never removes the columns itself. Synthetic contact tests run in isolated development tests, not on `kdps-test`. Permission for real data stays separate (D-4).
- **How intake finds customer-contact columns** (RR-203; `S1-F06-T02`; approved as built by the product owner, 10 Oct 2026). Layout detection (6.5) runs after storing, so on `kdps-test` intake detects in memory instead, against the Confirmed layout versions of the Organisation, before the object is written (3.1 step 1). The file is read under the caps (9.3); then each sheet that holds a cell must be the sheet of a Confirmed layout version the file fits as 6.5 says (its required columns at the header row, and no column the version does not know, A-4). Where a fitting version marks a column the sheet's header holds with the class customer contact, the file is refused as `files-imports.customer-contact-columns`, naming each such column and its sheet; the refusal says why and asks for the file again without them, and intake never removes a column itself. Where a sheet that holds a cell fits no Confirmed version, its columns' classes cannot be known, so the file is refused as `files-imports.layout-needed-on-test-setup`, naming the sheet: its layout is proposed (6.4, from its header written by hand, since no file of it is stored) and confirmed by a different person first, then the file uploaded again. Proposed and Rejected versions count for nothing, since a Proposed version's classes are not yet confirmed by a second person (6.4). Nothing is guessed from a column's name. An unknown column, such as a phone column added to a known layout, makes the sheet fit no version, so it is refused too. In local work, tests and `dev` the check does not run, so synthetic contact tests run there. **Design choices**, approved by the product owner, 10 Oct 2026: a sheet no Confirmed version recognises refuses the file (rather than letting an unchecked sheet be stored), and every sheet holding a cell is checked, a notes sheet included. If KDPS's answer to question 37 lets customer contacts in, that is a new decision (DEC-052, DEC-112).
- Which other fields are left out on the test setup, such as salesperson names, supplier bank details and tax numbers, and who may see cost columns, is OPEN (GC6-7; data-quality L-1).
- Purpose, consent and retention follow `PRD-SEC-009` and `PRD-SEC-010`. Retention periods are set with backup, restore and export (module-map MM-15); until they are set, nothing is deleted (`POL-18.05`).

### 13.1 Operations

The operations of module-map 4.7, made concrete. Every call goes through the checks of access-and-approvals 7.1: available, authorised, scoped.

| Operation | Takes | Refuses when |
| --- | --- | --- |
| Store a file | Bytes, source system, document reference claimed | 9.3; on the test setup, 11 |
| Attach, read a file | Stored file, record and version | The reader lacks the scope or a restricted class the file holds (section 11) |
| Start an import | Stored file, kind, target, scope facts | The target's handler does not accept the kind (4.2); the same file is in a batch for the same target and layout that is not Failed, or a document with the same source identity (target, scope key and document reference, 7.1) is already published, unless the batch is a governed revision of it (7.2, 7.3) |
| Map and stage | Layout and mapping versions; values entered by a person; documents excluded or put back | An incompatible layout version (6.5); a value of a field the preparer may not write |
| Validate and preview | The batch | — (it reports) |
| Propose or confirm a mapping rule, layout or mapping version | The proposal | For a mapping rule, the confirmer is the proposer (`PRD-IMP-008`). For a layout or mapping version, the same check (6.4; GC6-4, DEC-112) |
| Submit for review | The batch version | It is not Validated; Blocking issues remain; counts do not close (7.4) |
| Publish | The batch version and its approval decision, where one is required | The review is missing; the layout or mapping version is not Confirmed (6.4); a document is a duplicate or a conflict; the handler refuses under its locks |
| Withdraw | The batch | It is Published |
| Run a comparison | Two sets and a key | — |

**As built for the tracer** (`S1-F06-T01`; the routes and codes are in `packages/schemas`, the record type `files_imports.import_batch` declares view, create and edit with legal-entity and place facts):

- **Store a file for an import** (create on `files_imports.stored_file`): 9.3 "As built for import files". Its answer names the batches that read the same bytes before, as the reader may see them (7.2).
- **Start an import, with Map and stage** (create on the batch, with its scope facts): takes the stored file and the receipt it was handed in under, which must be the starting person's own (section 11), the kind, the target, and a layout version and a mapping version of that layout and target. Refused, before anything is written, when no handler of the target accepts the kind (`files-imports.no-import-handler`, 4.2), when the file does not match the layout (`files-imports.layout-not-matched`, naming the sheet or the required columns missing at the header row) and when the workbook cannot be read. The object is fetched, decrypted and checked against its hash, read and staged before the transaction (code-house-rules 8.3); the transaction holds the authority, takes the batch code series at step 8 and allocates the code (15.1), writes the batch Staged with its documents and staged rows, attaches the file (section 11) and writes the audit record. While no Open series of the kind `files-imports.import-batch` exists, or it is Paused, starting is unavailable naming it (`files-imports.no-import-batch-series`, `files-imports.import-batch-series-paused`). As built, staging runs in the request; a large file staged as a job on the worker (3.3) comes later. The duplicate refusals of this row are built with `S1-F06-T04` (7.4 "As built").
- **Validate and preview** (edit on the batch): the batch locked at step 1 and rechecked Staged (`files-imports.batch-not-staged`); each document is checked for every field its handler requires, an Unknown one being the issue `files-imports.required-value-unknown` with its field and row, then previewed by the handler. When every document previews without an issue the batch becomes Validated; otherwise it stays Staged and its read shows the issues. **Design choice** for the tracer: the issues are worked out again at each read rather than kept as row issues, which arrive with the validation report (`S1-F06-T03`), as does Submit for review.
- **Publish** (edit on the batch, and the permission the handler declares for its records, both held at step 0): refused unless the batch is Validated (`files-imports.batch-not-validated`). The handler publishes each document not yet published; a refusal of one is `files-imports.document-refused`, naming the document and the handler's reason, the attempt rolls back and its outcome is written after it in a transaction of its own; on success the documents and the batch become Published and the outcome is written with them (7.4). From `S1-F06-T04` each document publishes in a transaction of its own (3.3 "As built"), the request carries the batch version read (`kernel.stale-version` otherwise; code-house-rules 12.7), and the batch's command writes the outcome; its answer names each document's result.
- **As built with `S1-F06-T03`**: Detect a layout (a read, needing create on the batch type); Propose a layout, mapping or mapping rule version (6.4 "As built"); Enter a value (edit on the batch: a value, a reason and the suggestion accepted, for a field of a data row) and Exclude or put back a document, each making a new batch version (`import_batch.version_id`), Staged, and superseding the open approval request on the version submitted where the handler requires one, through `access`'s Supersede a request (access-and-approvals 9.1a); Mark Warnings seen; Submit for review, which records the version submitted (`submitted_version_id`) and, where the handler's review is an approval, requests it bound to the batch version with the batch's facts and every user who started it, entered a value or submits it as preparers. Validate now keeps the report (8 "As built"). Publish refuses `files-imports.review-missing` unless the current version was submitted, and, where the handler requires an approval, unless the decision named verifies under the lock for that version (access-and-approvals 9.7; its use recorded); `files-imports.version-not-confirmed`, naming the versions, unless the layout and mapping versions are Confirmed; an excluded document is not published. The batch's guard trigger allows only these moves (migration 0057), so a Published batch always had its version submitted.
- **The publishing limit** (product owner, 6 Oct 2026; `PRD-SEC-017`, `PRD-UXP-003`): Publish ran only where the environment is `local` or `dev`, answering `files-imports.publishing-limited` elsewhere and naming the publishing controls still missing: intake refusals and caps (`S1-F06-T02`), confirmed layouts and mappings with the validation report (`S1-F06-T03`) and duplicate control (`S1-F06-T04`). **Lifted** with `S1-F06-T04`, the last of the three to close (its Notes): publishing outside local work, tests and `dev` now depends only on those controls and the other gates in force, and the code is retired. Lifting it enables no real data: real masters on `kdps-test` still need KDPS's agreement (RR-180, D-4) and the confirmers of RR-197.
- **The version token on every batch step** (S1-F06 review 2; code-house-rules 12.7; `PRD-ACS-007`): Enter a value, Exclude or put back a document, Mark Warnings seen and Submit for review each carry the batch version the screen read, as Publish and Withdraw do, and refuse another as `kernel.stale-version`, naming the current version, under the batch's lock. So a Submit binds the version the person saw, and a version they did not see is never submitted.
- **Authorise first** (S1-F06 review 2; code-house-rules 8.1; module-map 6.1): Start an import authorises create on the batch with its scope facts before it reads the file, the layout and mapping versions or what is published, and before any fetch, decryption, parse or duplicate check; a person who may not start a batch at that place learns nothing else. In its transaction it locks the stored file exclusively and the layout and mapping versions shared at step 1, then checks again that no open batch reads the file for the target and layout, that neither version is Rejected, and the classes the file is held to carry by the layout version's state then (RR-503). Store a file for an import is authorised by the route's guard (create on `files_imports.stored_file`, a type with no scope facts) before its handler runs the workbook checks.
- **Withdraw** (edit on the batch, with the batch version read; `S1-F06-T04`): a Staged or Validated batch becomes Failed (3.2), emitting `files-imports.import-failed`; a Published or Failed one is refused (`files-imports.batch-not-open`). What it published before stays. Entering a value in a row of a published document is refused (`files-imports.document-not-staged`; `PRD-MOD-011`).
- **Reads**: the saved layout versions with their mapping versions, for whoever may view any batch (a layout holds no data); and one batch with its documents, staged rows, preview and outcomes (section 11).

### 13.2 The import handler contract

`files-imports` never writes another module's records (`PRD-MOD-002`; module-map section 3, rule 6). A target module registers a handler that declares:

- the record type it fills, the kinds it accepts and the effects it may have (4.2);
- the shape of a staged row, as a shared Zod schema (PRD Stack: API);
- the scope of its source identity (7.1), and whether it supports governed revisions (7.3);
- reference checks, run through its own interface and refusing what its own operations would refuse;
- suggestions: exact or close matches for codes and words, from its own records (section 5);
- the check of a mapping rule whose target it owns (6.3);
- a preview that works out, without writing, what each document would create or change;
- the review it requires: the preparer's submission after preview; an approval rule in `access`, independent where a source requires it (`PRD-ACS-006`); or the approvals of the records it creates, such as a master version Awaiting approval (structure-and-masters 2.3);
- whether a document is large and posts through a queued job (10.6);
- publish: writes its records in the transaction it is given, idempotent on the source identity (`PRD-INT-002`), whole or not at all (`PRD-IMP-012`).

**As built** (`S1-F06-T01`): a target module registers its handler at start with the `ImportHandlers` registry `files-imports` defines (`IMPORT_HANDLERS`; module-map section 3, rule 6), one per target. A handler declares its target, the record type it fills, the kinds it accepts, its effects, the fields of its staged row with which are required, and the permission its publish needs, which Publish holds at step 0 beside the batch's, so the records arrive under the same checks as a person's change (structure-and-masters 7; module-map section 3, rule 8); it previews a document without writing and publishes it in the transaction it is given. The first is `merchandise` · catalogue's create handler for products: a document is one style, its reference the style code, each data row one SKU; the brand and category are found by their exact codes, the stock unit and purpose must be values the catalogue accepts, every row must name the document's style, brand and category, and the preview runs Propose a product's own checks without writing; publishing calls Propose a product, so the style and its SKUs arrive as a product proposal a different person confirms (`PRD-MER-013`, DM-5). **As built with `S1-F06-T03`**: a handler also declares its review (the preparer's submission, or an approval rule in `access`), its suggestions for a field from its own records, and the check of a mapping rule's target for each field that takes rules. The registry `IMPORT_HANDLERS` is provided by the composition root, since `files-imports`' own decision effects check a rule's target through the handler that owns it. The `merchandise` handler: submission; suggestions for the brand and category codes, exact by code or close by trigram similarity (pg_trgm, migration 0058; at least 0.3, at most five). **Design choice:** the similarity 0.3 and the five suggestions are technical tuning of a suggestion a person still accepts, never business values, accepted as builder values by the product owner, 10 Oct 2026; the five is shared by every handler (`MOST_SUGGESTIONS`, with the option and close suggestions every handler offers the same way, `files-imports/domain/suggestions.ts`) over the codes and approved names, and for the stock unit and purpose from the values the catalogue accepts; rule targets: a brand or category code that exists, or an accepted stock unit or purpose. It has no attribute value field yet, so no vocabulary word is searched. The `organisation` create handler for Stores (target `organisation.store`): a document is one Store from one row, its reference the Store's code; its Site is found by code among the Sites in force today, its format and operating model must be accepted values, and its version starts today; publishing calls Prepare a Store, so the first version waits for a different authorised person (structure-and-masters 7). Publish authorises the handler's own permission on each document at the document's own place (below; S1-F06 review). **As built with `S1-F06-T04`**: a handler also declares the scope key of a document's source identity (`sourceScope`), whether it supports governed revisions (`revisions`: `none` or `new-version`), the permission its publish needs (create for a create; edit on `merchandise.sku` or `organisation.store` for an update), the fields an outcome sums as quantities and values (`measures`), and the rows its publish locks, which Publish locks with the batch at step 1 (`lockTargets`); a document carries the batch's kind. Both stage 1 handlers accept the update kind (7.4 "As built"). **The review by kind** (product owner, 11 Oct 2026; `PRD-ACS-006`, `PRD-ACS-007`): a handler names its review for each kind (`review(kind)`). The `organisation` handler's review is the submission for both kinds, since each Store version it prepares waits for a different person. The `merchandise` handler's is the submission for a create batch, whose products arrive as proposals another person confirms, and an independent approval for an update batch, whose SKU versions take effect when Prepare a SKU version records them: Submit requests the approval `files_imports.import_batch.approve` (declared by `files-imports`, on `files_imports.import_batch`, independent, with no value limit, no effect of its own and no decision-evidence class), bound to the batch version with every preparer of it, and Publish verifies a decision of that version by a different person under its locks and records its use (3.1 step 8; access-and-approvals 9.7, 9.8). So the preparer's own submission never makes a SKU version take effect. An update document of products is one style whose rows are its SKUs by code: the style, its brand and category and each SKU's size must be as created, since they are fixed then, and a new SKU arrives only through a product proposal (structure-and-masters 4.2). An update document of Stores is one Store in force today: the file's name, format, operating model, Site and opening date, with the aliases, classifications and closing date of the version in force.

**Publishing at each document's own place** (S1-F06 review; product owner, 10 Oct 2026; `PRD-SEC-005`; access-and-approvals 7.1 step 3; structure-and-masters 6.1, 7). A handler names the permission publishing one document needs with the scope facts of the place the document changes (`publishNeeds(context, document)`), exactly as a person's change of the same record is authorised on screen: a new Store with its Site, which a selected Site covers (structure-and-masters 5.2); the next version of a Store with the Store's facts today and the Site it moves the Store to, one assignment covering both. Products and SKUs belong to no place, so their need names no facts. Publish authorises that need for each document, a need asked for several documents once, and holds each at step 0 beside the batch's edit (RR-444). Before any document runs, every document to publish is authorised so: when one is outside the preparer's scope, nothing is published and Publish answers `not-authorised` naming what is missing and the document (`import-document`), so a Store-scoped preparer publishes Stores only within their scope. Each document's run authorises its own again in its own transaction, and the batch's run authorises every document still to publish. **Decided** (proposed as a design choice, 10 Oct 2026; confirmed by the product owner, 11 Oct 2026): one document outside the scope refuses the whole Publish up front, rather than failing alone, because a refusal for authority is the preparer's to resolve before anything is published, not a document's error. As built, a document's audit record cites the assignment that granted the handler's permission on it, as the handler's own records do (numbering-and-audit 4.1), and a conflict names the published document it conflicts with, never itself.
